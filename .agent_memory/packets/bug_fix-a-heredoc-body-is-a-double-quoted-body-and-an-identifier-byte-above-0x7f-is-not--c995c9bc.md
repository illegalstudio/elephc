# A heredoc body IS a double-quoted body, and an identifier byte above 0x7f is not a source error

> The interpreter's own lexer crates/elephc magician/src/lexer, used for eval strings and files included at run time re…

The interpreter's own lexer (crates/elephc-magician/src/lexer, used for eval strings and files included at run time) refused two shapes that PHP accepts, and a sweep of the Symfony vendor tree found fifteen refused files between them.

Fourteen were heredocs that interpolate. One routine served heredoc and nowdoc: it copied the body verbatim and then, for a heredoc, answered UnsupportedConstruct if the body contained a dollar sign anywhere. The correct model is that PHP defines a heredoc body AS a double-quoted body, so the fix hands the extracted body to the very scanner a quoted literal runs through, after the opener, the closing-marker search and the flexible-indentation strip that both forms already shared. Sharing one routine is the point: it is what keeps the two string kinds from drifting apart again, and it made simple offsets, arrow property reads, braced expressions and the legacy dollar-brace form work in a heredoc for free, because the code that already handled them is the code that now runs.

The two bodies diverge in exactly two measured ways, and both are now one parameter of that shared scanner rather than two copies of a table. A double quote ends a quoted literal but is ordinary text in a heredoc. And a backslash-escaped quote yields a bare quote in a quoted literal while it KEEPS its backslash in a heredoc, because a heredoc has no quote to escape. That second one is easy to get wrong by symmetry, and the AOT lexer in src/lexer/literals/strings.rs still has it wrong today: its scan_heredoc calls the same scan_double_quoted_escape a quoted literal uses, whose table maps the escaped quote to a bare quote, so a COMPILED heredoc prints a bare quote where the reference prints backslash-quote. That is a separate one-line fix in the compiler-side lexer with its own test, and it is still open.

Copying the body verbatim also meant a heredoc expanded no escape at all, so a tab escape stayed two characters where the reference writes a tab. That was invisible for as long as any dollar sign refused the whole construct.

The numeric escapes (hex, octal and braced code point) had been a declared, documented debt in this table for both string kinds. Implementing them is what the shared scanner makes cheap, and two facts there are not guessable: PHP accepts both letter cases for the hex form but only the lowercase letter for the braced code-point form, and PHP ENCODES a lone surrogate rather than refusing it. Rust's char type cannot hold a surrogate, and a byte named by a hex or octal escape need not be valid UTF-8 at all, so those bytes have to travel as the private-use markers the parser already decodes into a bytes constant. An overflowing octal sequence keeps only its low byte and the reference also emits a compile-time warning, which this scanner has no channel for and still does not emit.

The fifteenth file names a class with a raw high byte. PHP's identifier rule is a BYTE rule, not a Unicode one: every byte from 0x80 up is a name character. Two things had to change. The identifier predicate stopped at underscore and the ASCII letters, and — the part that actually blocked it — the byte-to-marker substitution ran only inside quotes and treated a high byte outside one as an invalid-UTF-8 source error, so the byte never reached the scanner at all. Marking every high byte wherever it sits, and letting one range test admit both a real non-ASCII character and a marker, covers a name written in UTF-8 and one written in a single-byte encoding without knowing which is which. The substitution moved out of the parser entry point and into the lexer, where the scanner that depends on it lives and where a second source entry point can reach it. Worth noting as a corroborating signal that the interpreter was the outlier: the AOT lexer's identifier predicate has admitted every non-ASCII character all along, and the tag scanner's heredoc-label predicate already accepted bytes from 0x80 up.

One consequence to know about: an identifier that arrives as markers KEEPS them as its name. That is self-consistent, so a declaration and a later fetch in the same source agree, which is what makes the reduced case run. It is not decoded back, because a Rust String cannot hold the arbitrary byte, so such a name would print as marker characters rather than as the original byte if it ever reached output. That only happens for a file whose bytes are not valid UTF-8 at all.

A trap worth recording for anyone editing this scanner next: the closing-marker search used to step past the label by its BYTE length using a per-character advance. That was harmless only while labels were ASCII; the moment a label can hold a multi-byte character the cursor lands mid-character. Step per character, or per byte, but do not mix the two.
Evidence: Oracle is php -n 8.5.6 on reduced probes. The heredoc reducer prints v=X where the lexer answered UnsupportedConstruct reported at end of file. The identifier reducer, a class named by a single raw high byte with a constant of 5, prints 5 where the parser answered invalid UTF-8. A heredoc line reading backslash-quote prints backslash-quote, while the same source inside a quoted literal prints a bare quote; a heredoc line reading a tab escape prints a real tab. bin2hex of the numeric escapes gives 41, 04, 047a, 4134, 41, 5c785a5a, 5c78 for the hex forms; 41, 01, 08, 4131, 00, ff, 00, 5c38 for the octal forms; 41, f09f9880, 41, f48fbfbf, eda080, 5c753431, 5c557b34317d for the code-point forms. The four malformed braced forms are parse errors reading Invalid UTF-8 codepoint escape sequence, the out-of-range one adding Codepoint too large. Interpreter crate filters before then after: lexer 39 passed 0 failed then 64 passed 0 failed; parser::tests 244 passed 11 failed then 255 passed 11 failed, the same eleven property_mutations and static_members names, none of which touch lexing. Both sets were measured in the same worktree by reverting to the base tree and re-running, not inferred. The five rustc warnings in the crate's test build all sit in interpreter and context files untouched by this change, and cargo clippy cannot reach this crate at all because elephc-builtin-contract fails an approx_constant deny that predates this work.
