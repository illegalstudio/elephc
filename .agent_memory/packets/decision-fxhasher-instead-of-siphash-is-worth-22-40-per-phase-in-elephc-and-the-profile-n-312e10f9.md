# FxHasher instead of SipHash is worth 22-40% per phase in elephc, and the profile names the hasher but not which map: the class map bought type-check nothing, ClassInfo's method maps bought it 40%

> Swapping SipHash for FxHasher across the compiler's internal keying is worth far more than a hasher change usually is…

Swapping SipHash for FxHasher across the compiler's internal keying is worth far more than a hasher change usually is, because elephc keys almost everything on `String` and `(String, String, bool)`. Measured on the Symfony `--web` build in three commits, each gated on a BYTE-IDENTICAL linked binary (108,317,352 bytes, 631 class-name symbols, unchanged throughout):

- reachability maps: pruning 14.59 s to 11.30 s (−22.5 %)
- the CLASS map (`Checker::classes` = `CheckResult::classes` = `Module::class_infos`): lowering 7.90 s to 6.14 s (−22.3 %), type-check UNCHANGED
- `ClassInfo`'s eight METHOD maps: type-check 16.50 s to 9.82 s (−40.5 %), lowering 6.14 s to 5.52 s

THE ORDER OF THOSE THREE IS THE LESSON. The profile said SipHash was the top leaf in the type-check window, and the obvious target — the class map the checker probes by name — bought type-check NOTHING. The cost was one level down: `infer_method_call_type` and `mixed_receiver_method_return_type` probe `ClassInfo`'s OWN maps once per candidate class per call site. A profile that names a HASHER does not name WHICH MAP; only swapping one and measuring does.

SWAP A MAP TOGETHER WITH EVERYTHING THAT BUILDS IT, or the gain is spent at the boundary. `ClassInfo`'s method maps had to move with the class-schema builder's own fields and the enum path's locals so that `ClassInfo { methods: self.method_sigs, .. }` still MOVES the map; leaving the builder std-hashed would have rebuilt a large map per class. The same argument forced the class map to move as a unit across checker, lowering and codegen — those three names are one table handed along the pipeline, and splitting the commit by phase would have inserted a full rebuild.

MAKE SHARED HELPERS GENERIC OVER THE HASHER, not pinned. `retain_keys`, `method_is_live`, `normalize_method_map_for_eir`, `retain_function_keyed_map`, `check_result`, `sorted_keys`, `collect_program_declared_names`, `method_visible_from_class_string` and `property_visible_from_class_string` all receive fast-hashed maps from one caller and std-hashed maps from another; a `<S: std::hash::BuildHasher>` parameter serves both and stops the ripple dead. Pinning them instead made the error count GROW, because it broke the other direction.

WHY THE BYTE-IDENTICAL GATE SURVIVES A HASHER CHANGE, which is the objection to answer first: std's `HashMap` uses `RandomState`, seeded per PROCESS, so iteration order ALREADY differs between two runs of today's compiler — and the emitted assembly is identical across runs anyway (six invocations of one fixture, all sha256 76cf50e5…). That proves the output does not depend on map order, so a deterministic hasher can only replace a random order with a fixed one. The one output known to depend on order is the "Unused variable" stderr sequence, which was already nondeterministic; gates here sort stderr for that reason.

`rustc-hash` was already in `Cargo.lock` transitively, so none of this pinned a new dependency version. Aliases live in `src/fast_hash.rs`; there is no `new()`, so constructions become `FastMap::default()`.
Evidence: Three paired Symfony `--web --heap-size=1073741824` measurements from the worktree root, cache off, each against the immediately preceding commit: pruning 14.59 to 11.30 s; lowering 7.90 to 6.14 s with type-check unmoved at 16.08 to 16.50; then type-check 16.50 to 9.82 s and lowering 6.14 to 5.52 s. The linked binary is 108,317,352 bytes with 631 `_class_name_` symbols in every one of them. In the last measurement every phase the change cannot touch moved UP (pruning 11.55 to 11.94, codegen 27.49 to 28.69, assembling 36.20 to 38.11), so the 40 % is a floor rather than a flattering reading. `cargo test -p elephc --lib` gives 1648 passed / 19 failed at each of the four commits, with `comm` of the sorted failing-name lists empty in both directions every time.
Verified by: cargo test -p elephc --lib compared by name across four commits; three paired Symfony --web builds with the linked binary byte-identical; sha256 identity of the emitted assembly across six fixture invocations; sample -mayDie profile at 1 ms

## Verification

Three paired Symfony `--web --heap-size=1073741824` measurements from the worktree root, cache off, each against the immediately preceding commit: pruning 14.59 to 11.30 s; lowering 7.90 to 6.14 s with type-check unmoved at 16.08 to 16.50; then type-check 16.50 to 9.82 s and lowering 6.14 to 5.52 s. The linked binary is 108,317,352 bytes with 631 `_class_name_` symbols in every one of them. In the last measurement every phase the change cannot touch moved UP (pruning 11.55 to 11.94, codegen 27.49 to 28.69, assembling 36.20 to 38.11), so the 40 % is a floor rather than a flattering reading. `cargo test -p elephc --lib` gives 1648 passed / 19 failed at each of the four commits, with `comm` of the sorted failing-name lists empty in both directions every time.
