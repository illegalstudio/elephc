# OPEN: the interpreter's parser accepts only plain variables as array-destructuring targets, so `[$this->a, $this->b] = $v;` fails to parse and silently costs the whole class

> Short array destructuring in the interpreter the parser used by eval and by every file included at run time accepts O…

Short array destructuring in the interpreter (the parser used by `eval()` and by every file included at run time) accepts ONLY plain variable targets. parse_array_destructure_stmt in crates/elephc-magician/src/parser/statements/assignments.rs matches each slot against the dollar-identifier lexeme and returns EvalParseError::ExpectedVariable for anything else, so `[$this->keys, $this->values] = $values;` — a real line of Symfony's PhpArrayAdapter — does not parse. Because the failure happens while the interpreter is DECLARING the class, the cost is not one statement: the class the statement lives in never becomes usable, and the symptom you actually see is far away (a class that "should" be loadable answering as missing, reached in that campaign through class_exists on PhpArrayAdapter). Two consequences when you work here. First, when a vendor class is mysteriously unavailable through the bridge, check whether its body contains a construct the interpreter's own parser refuses before you look at the autoloader or at class metadata. Second, when you widen this, widen it to the same target set PHP allows — property targets, array-element targets, nested patterns and keyed destructuring — not just the one shape that unblocked your case; the AOT parser and the interpreter parser are separate implementations and only the second one is at issue here.
