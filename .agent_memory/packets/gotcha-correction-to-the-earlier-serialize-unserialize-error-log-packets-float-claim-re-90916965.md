# CORRECTION to the earlier serialize/unserialize/error_log packet's float claim: reusing va

> CORRECTION to the earlier serialize/unserialize/error log packet's float claim: reusing values.string bytes for seria…

CORRECTION to the earlier serialize/unserialize/error_log packet's float claim: reusing values.string_bytes() for serialize()'s float formatting was WRONG in production, confirmed via the compiled probe (scratchpad/r200/gate.php lotc_ser, --with-regex build), not just the FakeOps fixture. The FakeOps test fixture's string_bytes for a float is Rust's f64::to_string() (shortest round-trip, matching php's serialize_precision=-1), but the PRODUCTION runtime's string_bytes on a float answers php's precision=14 echo/string-cast rule instead (serialize(1/3) gave "0.33333333333333", 14 threes, where php's real serialize() gives "0.3333333333333333", 16 threes) -- the fake and the real implementation of the SAME trait method diverge on this specific conversion, so a fake-only test cannot catch it. Fixed in crates/elephc-magician/src/interpreter/builtins/core/serialize.rs by reading the raw IEEE-754 bits via values.raw_value_word() (bypassing string_bytes entirely) and formatting with f64::to_string() directly. LESSON: for any future builtin needing serialize_precision=-1 (shortest round-trip) float formatting, do NOT reuse values.string_bytes()/eval_float_value() (which round-trips through cast_float+string_bytes+parse and inherits the same precision=14 lossiness) -- read raw_value_word() and use f64::from_bits()+to_string() instead. json_encode()'s own float branch (crates/elephc-magician/src/interpreter/builtins/json/json_encode.rs, eval_json_encode_append_float) still reuses values.string_bytes() the same lossy way and very likely has the IDENTICAL bug for any non-terminating fraction (php's json_encode also uses serialize_precision=-1) -- this is an existing, separate, unverified-by-me finding worth a dedicated probe and fix. Separately, unserialize()'s allowed_classes=false path still fails in the compiled runtime after a stdClass fallback attempt (values.new_object("__PHP_Incomplete_Class") has no such native class registered at all) -- exact root cause not isolated (something in the property_set/new_object FFI boundary specifically for this code path); the allowed_classes=true path is confirmed byte-identical against the compiled binary and is the one PLAN.md's own priority citation (the warm-cache Mg payload) exercises.
Verified by: scratchpad/r200/gate.php lotc_ser now IDENTICAL after the raw_value_word fix; lotc_unser still DIFFERS on the allowed_classes=false path only

## Verification

scratchpad/r200/gate.php lotc_ser now IDENTICAL after the raw_value_word fix; lotc_unser still DIFFERS on the allowed_classes=false path only
