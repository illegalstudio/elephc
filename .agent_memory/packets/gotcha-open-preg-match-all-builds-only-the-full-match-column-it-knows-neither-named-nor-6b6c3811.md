# OPEN: `preg_match_all` builds only the full-match column — it knows neither named nor NUMBERED groups, and PREG_SET_ORDER is flattened the same way

> preg match has been brought to parity with PHP delimiters, named groups written before their numeric keys, PREG OFFSE…

`preg_match` has been brought to parity with PHP (delimiters, named groups written before their numeric keys, PREG_OFFSET_CAPTURE), but `preg_match_all` has NOT, and its gap is silent rather than diagnosed. The runtime emitter in src/codegen_support/runtime/system/preg_match_all.rs asks PCRE2 for a single pair of offsets ("request only the full-match pair") and builds exactly one outer column ("one outer pattern-order column: capture group zero"), so a pattern with capture groups returns only `$matches[0]`: not just the named groups are missing, the NUMBERED ones are too. PREG_SET_ORDER is flattened by the same shortcut. A program that reads `$m[1]` after preg_match_all therefore gets nothing back with no error raised, which is the classic shape that makes a parser silently produce empty values downstream. When you take this on, take the whole thing: the fix is the same three pieces the preg_match work needed — ask PCRE2 for the real group count and the name table rather than counting parentheses, keep the compiled pattern alive while the arrays are built, and write each group name immediately before the numeric key it doubles — plus the offset-capture pair shape if the flag is set. Do not treat "the checker accepts it" or "no error" as coverage: assert the full `$matches` structure against `php -n`.
