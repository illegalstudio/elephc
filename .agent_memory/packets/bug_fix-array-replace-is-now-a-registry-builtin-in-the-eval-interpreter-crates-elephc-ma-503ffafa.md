# array_replace() is now a registry builtin in the eval interpreter (crates/elephc-magician/

> array replace is now a registry builtin in the eval interpreter crates/elephc magician/src/interpreter/builtins/array…

array_replace() is now a registry builtin in the eval interpreter (crates/elephc-magician/src/interpreter/builtins/array/array_replace.rs). Key insight: the shared BuiltinContract for array_replace declares exactly two fixed Mixed params with no `variadic` spec (catalog_data.rs), matching the compiled/AOT side's hard-coded arity-2 check and lowering — but the INTERPRETER'S direct-call path (eval_declared_builtin_direct_call -> hook.call(spec.name, args, ...)) does NOT enforce contract arity for a plain positional call; it hands whatever args were written straight to the hook. So the interpreter hook can and does implement php's real variadic signature (array_replace(array $array, array ...$replacements)) directly, accepting 1..N arguments with php-exact TypeError/ArgumentCountError wording, without touching the shared contract or the compiled/AOT side at all. This is the general pattern for any other "declared as fixed-arity but really variadic in php" builtin still in EVAL_IMPLEMENTATION_PENDING: check whether the interpreter's own arity is contract-derived (it usually is not) before assuming a contract edit is required. Also fixed a real bug in the shared eval_given_type_spelling() (crates/elephc-magician/src/interpreter/return_values.rs): it said "bool" for a rejected boolean argument in every TypeError message it feeds (extract(), scalar/common.rs's declared-string/int coercion, method_binding.rs's argument binding, and return_values.rs's own return-type coercion) where php -n 8.5.6 ALWAYS says "true"/"false" instead, verified across strict_types param coercion, return-type coercion, and internal-function arguments (array_replace's own TypeError needed this). The ONLY place the old "bool" spelling was pinned in a test is the separate compiled-backend suite at tests/error_tests/type_system.rs (test_error_strict_types_rejects_bool_into_int_parameter and its two siblings), which is itself measurably wrong against the same php run and was left untouched (out of interpreter scope) — a future wave fixing the compiled backend's own int/float/string TypeError formatting should fix those three tests too, mirroring the E_ALL=32767 pattern already documented for error_reporting.
Verified by: cargo test -p elephc-magician --lib builtins_array_replace (10/10 green) and cargo test -p elephc-builtin-contract --lib (16/16 green); every php output re-measured with php -n 8.5.6
