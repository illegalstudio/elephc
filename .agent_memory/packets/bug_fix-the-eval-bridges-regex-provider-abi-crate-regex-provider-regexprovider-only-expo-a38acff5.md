# The eval bridge's regex provider ABI (crate::regex_provider::RegexProvider) only exposed c

> The eval bridge's regex provider ABI crate::regex provider::RegexProvider only exposed compile/exec/free, so preg mat…

The eval bridge's regex provider ABI (crate::regex_provider::RegexProvider) only exposed compile/exec/free, so preg_match() named groups ((?P<name>...), (?<name>...), (?'name'...)) matched correctly but never surfaced their names in $matches — even though the native PCRE2 shim already had elephc_pcre2_v1_name_count/elephc_pcre2_v1_group_name (added in pcre2 recipe revision 4, unused until now). Fixed by extending RegexProvider with name_count/group_name callbacks, registering them from codegen's register_eval_regex_provider (now 5 symbols, not 3), adding Regex::name_count()/group_name() in crates/elephc-magician/src/interpreter/builtins/regex/engine.rs, and having eval_preg_capture_array in captures.rs build an ordered hash (assoc_new + array_set: name key written immediately before its own numeric twin, in ascending PCRE2 capture-group order) whenever regex.name_count() > 0, instead of always emitting a plain indexed array. preg_match() and preg_replace_callback() both call eval_preg_capture_array so both gained named-group support for free; preg_match_all() does NOT call this function (it builds rows via eval_preg_capture_value directly) so it still has zero named-group support — a separate, still-open gap. Verified against php -n 8.5.6: for /(a)(?P<mid>b)(c)/ against 'abc', key order is 0,1,mid,2,3 (an unnamed group ahead of a named one keeps its own plain numeric slot; the name-before-number rule is per-group, not array-wide).
Evidence: crates/elephc-magician/src/interpreter/tests/builtins_regex_named_groups.rs green; sentinel revert (if true || regex.name_count() == 0) reproduced the exact pre-fix output; php -n 8.5.6 gate.php probes p12/p13/p14 IDENTICAL after the fix.
