# A test of a gate is meaningful only in the gate's default state: two tests going red under ELEPHC_IR_VALIDATE=0 is the gate working, not failing

> Commits cd7a8426ee 08, debug IR validation gate and 00424db8b4 01, dominator bitsets , both landed 2026 09 05 and bot…

Commits cd7a8426ee (08, debug IR-validation gate) and 00424db8b4 (01, dominator bitsets), both landed 2026-09-05 and both BILLED AT ZERO for release.

08 gates the driver's per-pass IR re-validation behind ELEPHC_IR_VALIDATE. It is worth EXACTLY ZERO on a release compiler and that is the design, not a disappointment: the call sits under #[cfg(debug_assertions)], so release never compiles it. The gate defaults to ON and only `0` and `off` disable it, so a typo keeps the check — a gate defaulting the other way turns a loud malformed-IR panic into a silent miscompile.

THE READING THAT MATTERS, because the runbook gets it wrong. The runbook says to run the narrow filters with the gate explicitly ON and explicitly OFF and that "both must be green". TWO TESTS ARE GREEN ON AND RED OFF, AND THAT IS THE GATE WORKING:
- `validation_gate_tests::the_gate_reads_its_environment_variable` asserts validation is on when the variable is UNSET; exporting ELEPHC_IR_VALIDATE=0 for the whole run makes its own precondition false by construction.
- `ir_passes::tests::driver_test::malformed_ir_pass_trips_validation_in_debug` feeds a pass deliberately malformed IR and expects the panic "produced invalid IR"; with validation off it does not fire and the driver instead hits the fixed-point cap ("did not reach a fixed point ... after 64 iterations").
Those two failing under `=0` is the PROOF the gate genuinely controls the validation, and their passing by default is the proof the default is on — exactly the safety property the change exists for. Everything else is green both ways: ir_passes:: 147 other tests and codegen:: 77 tests. Generalise the rule: a test OF a switch is meaningful only in the switch's default state; do not demand it be green in every configuration.

01 replaces `dominator_bitsets_to_map` (an O(blocks^2) HashMap/HashSet materialisation per validated function, taken UNCONDITIONALLY in release by validate_lowered_module) with a direct bitset membership query on the bitsets the fixed point already produced. It is landed on its identity gate (assembly, linked binary, stdout, nm, sorted stderr all byte-identical) and on `dominator_bitset_tests`, which compares old against new for EVERY ordered pair of blocks on a four-block diamond and a four-block loop with a back edge plus pinned dominance facts, so both sides cannot be wrong the same way. NO TIMING IS CLAIMED FOR IT: its phase, "Lowering program to EIR", read 8.88 / 10.06 / 10.53 / 12.88 / 13.11 s across five runs of otherwise-unchanged code as machine load moved, a spread wider than the change is worth, and a load-normalised comparison (the ratio of lowering to a phase the change cannot touch) moved 0.298 to 0.303, i.e. no resolvable effect either way. Landing a safe change and reporting "not separately measurable here" is the honest outcome; inventing a number from one confounded pair is not.
Evidence: cargo test -p elephc --lib with ELEPHC_IR_VALIDATE unset, =1 and =0: validation_gate_tests 2 passed unset; ir_passes:: 149 passed with =1 and 147 passed / 2 failed with =0, the two named above, with the captured panic messages "per-pass validation must be on when ELEPHC_IR_VALIDATE is unset" and "EIR pass driver did not reach a fixed point ... expected substring: produced invalid IR"; codegen:: 77 passed both ways. For 01: cmp exit 0 on assembly, binary, stdout, nm and sorted stderr; five Symfony --timings runs giving the quoted lowering-phase spread.
Verified by: Crate-wide --lib 1645 passed / 19 failed after 08 and 1643 passed / 19 failed after 01, failing set exactly the pre-existing 19 in both, passed counts rising by exactly the tests each change adds (2 and 3)
