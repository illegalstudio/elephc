# An eval-declared closure (`function(){}`/`fn()=>1`) is NOT tagged EVAL_TAG_CALLABLE (10) i

> An eval declared closure function {} / fn = 1 is NOT tagged EVAL TAG CALLABLE 10 in the interpreter. eval closure obj…

An eval-declared closure (`function(){}`/`fn()=>1`) is NOT tagged EVAL_TAG_CALLABLE (10) in the interpreter. `eval_closure_object_expr()` (crates/elephc-magician/src/interpreter/expressions/evaluation.rs:634) materializes it as an ordinary tag-6 object built with `values.new_object("stdClass")`, and the SAME object identity is registered separately via `context.register_closure_object_target()`. The only correct way to resolve its PHP-visible class name ("Closure") is `context.dynamic_object_class_name(identity)` (crates/elephc-magician/src/context/classlike_objects.rs:469), which checks `closure_objects.contains_key(&identity)` FIRST before falling back to a declared eval class or the runtime's own class name. `get_class()` (builtins/symbols/get_class.rs) already uses this route correctly. A naive object-arm implementation that reads `values.object_class_name()` directly (or that trusts EVAL_TAG_CALLABLE to catch eval-declared closures) will report "stdClass" for a closure instead of "Closure" -- this bit get_debug_type() during implementation, caught only because the interpreter's own FakeOps test harness has no separate closure representation either (FakeValue enum has no Closure/Callable variant; closures always end up as FakeValue::Object), so the bug was reproducible even in unit tests once the right assertion was written. EVAL_TAG_CALLABLE does exist and is used elsewhere (sprintf's numeric coercion, dynamic_functions.rs, calls.rs first-class-callable checks), so it is presumably real for SOME closure representation crossing the eval bridge from compiled/AOT code, just not for closures created directly inside eval() via function(){} syntax.
Evidence: FakeOps unit test get_debug_type_names_a_closure failed with actual \"stdClass:stdClass\" against a naive object-arm implementation using EVAL_TAG_CALLABLE + eval_debug_object_class_name (print_r.rs's context.dynamic_object_class, missing the closure_objects check); switching to context.dynamic_object_class_name (the exact route get_class.rs uses) fixed it, and the same probe was byte-identical to php -n through the real --web gate.php harness afterward.
Verified by: cargo test -p elephc-magician --lib builtins_get_debug_type (8/8 green) and php -n gate.php probe_gdt : IDENTICAL against the compiled main binary
