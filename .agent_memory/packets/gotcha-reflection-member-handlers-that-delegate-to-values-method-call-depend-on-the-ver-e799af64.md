# Reflection member handlers that delegate to values.method_call depend on the very AOT bodies the pruner drops

> Échelon 57 exists because ReflectionMethod::getParameters/getNumberOfParameters/getReturnType/getAttributes and the r…

Échelon 57 exists because `ReflectionMethod::getParameters/getNumberOfParameters/getReturnType/getAttributes` and the real `ReflectionParameter` members are AOT bodies the declaration-reachability pruner drops (nothing compiled names them), so a DI compiler's `getParameters()`/`getType()` dies. The interpreter is supposed to answer them itself.

THE ROOT REASON, and the thing to fix first: the `ReflectionParameter` handlers already on the branch -- `eval_reflection_parameter_legacy_type_predicate_result` and `eval_reflection_parameter_to_string_result` in interpreter/reflection/callable_api.rs -- answer by calling `values.method_call(object, "getType", ...)`. They DELEGATE to the AOT-compiled ReflectionParameter bodies, which are precisely the bodies the pruner drops. Any interpreter answer for those members must stop delegating and read the reflector's own slots, or it re-creates the dependency the échelon exists to remove. Converting those two handlers off `values.method_call` onto slot reads is a prerequisite, not a cleanup.

THE METADATA PREMISE IS ALREADY TRUE -- no compiler publication is needed. Both variants of `EvalReflectionFunctionMethodTarget` (interpreter/reflection.rs) already carry `parameters: Vec<EvalReflectionParameterMetadata>`; `eval_reflection_method_metadata` (reflection/member_metadata.rs) already assembles required-parameter count, flags, return-type and declaring-function metadata; `eval_reflection_parameter_object_result` (reflection/owner_materialization.rs) already builds a full ReflectionParameter through `reflection_owner_new`; and `eval_reflection_slot_string` + `eval_with_native_bridge_scope` (statements/class_resolution.rs) provide the class-scoped slot read. The work is handlers only.

TRAP, measured: adding `getparameters` / `getnumberofparameters` / `getnumberofrequiredparameters` to the TOP of `eval_reflection_function_method_metadata_result` works for ordinary methods (probe went from failing at the first member to matching php on `n:3;req:1;count:3`) but makes that dispatcher claim the name for EVERY function/method target, shadowing the property-HOOK path that answered it correctly further down. Two tests catch it and should be used as the guard:
  builtins_class_metadata::property_values::execute_program_reflection_property_gets_eval_hook_metadata
  builtins_class_metadata::callable_types::execute_program_reflection_property_get_settable_type_uses_set_hook_parameter
The members must run AFTER the hook path, or exclude hook targets.

Oracle for the surface, php -n 8.5.6 on a method `handle(int $id, ?string $name = null, Svc ...$rest): string`:
  n:3;req:1;count:3;[id,0,req,int][name,1,opt,?string][rest,2,opt,Svc];ret:string;attrs:0

PROCESS NOTE: the slot-getter mechanism (`eval_reflection_slot_getter_result`) was sitting in ANOTHER lane's scratchpad, unlanded. Writing a second copy would have collided with that lane's pick instead of composing with it. Wait for the pick; do not re-implement a mechanism you can see in another lane's working files.
Evidence: php -n 8.5.6 oracle measured; elephc fails at the first member through a runtime include. The three method-level members were implemented, measured correct on the probe (n:3;req:1;count:3 matching php), then reverted when they turned the two named property-hook tests red. Inventory of existing metadata verified by reading each file.
Verified by: cargo test -p elephc-magician --lib -- 1501 passed, 0 failed after reverting; the two hook tests are the guard. Findings written to exec-lane/red/echelon57-findings.md with the probe.
