# Four introspection switches gated emission but named no runtime-cache key bit, so two programs shared a runtime object — and `--lib runtime_cache` tests none of it

> Commit c481a522c8 cherry picked as 7becac7791 . RuntimeFeatures::cache key bits packed 12 bits while the struct carri…

Commit c481a522c8 (cherry-picked as 7becac7791). `RuntimeFeatures::cache_key_bits` packed 12 bits while the struct carries 16 `bool` fields. The four missing ones — const_introspection, class_introspection, class_relation_introspection, class_methods_introspection — gate real emission in codegen_support::runtime::emitters exactly the way `regex` does, but named no bit. So a program that needs `__rt_class_exists` and one that does not named the SAME cache entry: whichever compiled first published its runtime object and the other one LINKED IT, getting a missing symbol or dead weight depending which way round the cache happened to be filled. Widening the key can only cause more misses, never fewer, so the fix is safe by construction.

`CACHE_KEY_BIT_COUNT` is now tied to the struct by `const _: () = assert!(size_of::<RuntimeFeatures>() == CACHE_KEY_BIT_COUNT)`. Every field is a bool so size_of counts them: adding a 17th field without giving it a bit now FAILS TO COMPILE rather than silently reintroducing the collision.

OBSERVED, not merely argued: on a private empty runtime cache the same program named runtime-v0.26.5-macos-aarch64-rtce68ba90dd4da2ca-heap8388608.o before the fix and ...-rtb858886489f540f2-heap8388608.o after, so the key genuinely moved, while the emitted assembly, linked binary, stdout, nm and sorted stderr stayed byte-identical — the change stayed in the cache identity and did not leak into codegen.

THE TESTING TRAP, which is the part most likely to bite the next person. `mod runtime_cache` is declared in src/main.rs ONLY, not in src/lib.rs. So `cargo test -p elephc --lib runtime_cache` — which the perf hand-over explicitly prescribed for this patch, listing runtime_cache among the "lib modules" — compiles NONE of it and reports "0 passed; 1662 filtered out". It passes the patch vacuously. The correct target is `cargo test -p elephc --bins runtime_cache`, which runs 9 tests. This is the SAME trap already documented for src/linker and src/pipeline, so treat any claim about which modules are lib-testable as unverified and check `grep -n "mod <name>" src/lib.rs src/main.rs` first. I only caught it because the crate-wide passed count did not move when the patch supposedly added test coverage — a good habit: a patch that claims to add tests must move the passed count.

To probe the runtime cache without disturbing other agents, point XDG_CACHE_HOME at a private directory — but the cache root ALSO holds downloaded native artifacts (pcre2 and friends), so an entirely empty root fails with "native integrity error: native artifact is missing or corrupt". Symlink the `native` subtree back to the shared cache and only the runtime objects are absent.
Evidence: Cache entry names observed before and after the change on a private XDG_CACHE_HOME with the native subtree symlinked; cmp exit 0 on emitted assembly, linked binary, stdout, nm -n and sorted stderr against the same compiler without the change; `cargo test -p elephc --lib runtime_cache` reporting 0 passed / 1662 filtered out while `--bins runtime_cache` reports 9 passed
Verified by: cargo test -j 2 -p elephc --bins runtime_cache 9 passed 0 failed; crate-wide --lib 1643 passed/19 failed and --bins 1845 passed/19 failed, failing set exactly the pre-existing 19
