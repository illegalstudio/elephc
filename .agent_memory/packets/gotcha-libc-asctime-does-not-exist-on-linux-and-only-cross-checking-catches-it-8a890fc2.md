# libc::asctime does not exist on Linux — and only cross-checking catches it

> The libc crate exposes asctime on macOS but NOT on Linux, so libc::asctime compiles cleanly on a darwin dev machine a…

The `libc` crate exposes `asctime` on macOS but NOT on Linux, so `libc::asctime` compiles cleanly on a darwin dev machine and fails on every Linux target with `error[E0425]: cannot find function 'asctime' in crate 'libc'`. This broke `elephc-magician` on linux-x86_64 and linux-aarch64 when `crates/elephc-magician/src/script_cache/accel_log.rs` was first wired into `mod.rs` (it had sat in the tree unreferenced, so nothing had ever compiled it).

The blast radius is much wider than the crate: because `elephc-magician` is a dev-dependency of the docs exporter example and of the PDO live-suite tests, the single error also took down `Builtins docs in sync`, `Curl feature contract coverage`, `PDO core live suites` and `PDO optional-driver live suites`. When several unrelated-looking CI jobs go red at once, check for one compile error in a shared crate before triaging them separately.

The fix: keep libc's `localtime` (it is the zone-aware half, and the half that could drift from reference PHP) and spell `asctime` out by hand. This is safe because the C standard fixes `asctime` to exactly one format — `"%.3s %.3s%3d %.2d:%.2d:%.2d %d\n"` over C-locale day/month abbreviations — so it is locale-INdependent. `script_cache::accel_log::format_asctime` does this and was checked against the system `asctime` over 200,000 timestamps (1000 consecutive days plus a random sweep across ~1938..2096) with zero mismatches. Two details are easy to get wrong and still look plausible: the day of month is `%3d` (SPACE-padded, giving two spaces before a single-digit day) while the time fields are `%02d`, and php-src's `char time_string[24]` truncates a 5-digit year rather than widening the line.

PREVENTION: a darwin-only toolchain cannot check this class of bug at all. Run `rustup target add x86_64-unknown-linux-gnu aarch64-unknown-linux-gnu` once, then `cargo check -p <crate> --all-targets --target x86_64-unknown-linux-gnu` before pushing anything that touches libc. Note that a WORKSPACE-wide cross-check is not available on darwin: `ring`'s build script needs an `x86_64-linux-gnu-gcc` cross compiler that is not installed, so it fails before reaching the workspace crates. Per-crate cross-checks of the pure-Rust crates still work and are what caught this.
Evidence: CI run 34711224206 job 103600286925 (linux-x86_64) line 802: `error[E0425]: cannot find function 'asctime' in crate 'libc'`, line 824: `error: could not compile 'elephc-magician' (lib)`. The same error appears in PDO run 34711224155 at both failing jobs. After the fix, `cargo check -p elephc-magician --all-targets` passes on x86_64-unknown-linux-gnu and aarch64-unknown-linux-gnu.
Verified by: Cross-compilation against both Linux targets, a 200,000-timestamp differential test against the system asctime, and 6 new unit tests in accel_log.rs pinning the format (all passing, 1274 magician lib tests green).
