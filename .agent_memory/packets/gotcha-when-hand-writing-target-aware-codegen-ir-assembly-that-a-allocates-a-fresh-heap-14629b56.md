# When hand-writing target-aware codegen_ir assembly that (a) allocates a fresh heap object

> When hand writing target aware codegen ir assembly that a allocates a fresh heap object into abi::int result reg x0 o…

When hand-writing target-aware codegen_ir assembly that (a) allocates a fresh heap object into `abi::int_result_reg` (x0 on AArch64, rax on x86_64) and then (b) needs to reload a previously-parked (pushed) value's registers to store into that object's fields, NEVER reuse `abi::string_result_regs` as the reload target. On AArch64, string_result_regs = (x1, x2), which never collides with int_result_reg = x0. On x86_64, string_result_regs = (rax, rdx) — rax IS int_result_reg, so popping a parked pair into string_result_regs silently clobbers the freshly allocated object pointer before its fields are stored, corrupting every TypeError-like heap object built this way. The established safe pattern (mirrored from `objects::reflection::emit_reflection_class_argument_type_error_throw`) is to reload into DEDICATED scratch registers instead: x9/x10 on AArch64, r10/r11 on x86_64 — never string_result_regs — whenever the reload happens after the object pointer is already sitting in int_result_reg. This bug is invisible when testing only on macOS-aarch64 (the native dev target) since ARM64 has no collision; it only manifests on x86_64. Found and fixed while implementing SPEC I2 (checked-downcast-on-return TypeError construction) in src/codegen_ir/lower_inst/objects/return_type_guard.rs.
Evidence: Hand-traced the x86_64 register choreography instruction-by-instruction: abi::int_result_reg(X86_64) == \"rax\" and abi::string_result_regs(X86_64) == (\"rax\", \"rdx\") per src/codegen/abi/registers.rs:72-95, while the AArch64 pair (x0 vs x1/x2) never collides. Fixed by introducing a message_scratch_regs() helper returning (x9,x10)/(r10,r11), matching objects/reflection.rs's existing pop_reg_pair(\"x9\",\"x10\") convention. All 14 codegen_tests::oop::checked_downcast_return tests still pass on macOS-aarch64 after the fix (unaffected, since the bug was x86_64-only).
