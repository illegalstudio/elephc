# elephc spawns cargo from inside a compile to rebuild a stale bridge archive, and the wait is billed to the link phase — it silently corrupts timings and binary comparisons

> linker::bridges::BridgeStaticlib::sources are newer than walks crates/<bridge and, if any file there is newer than th…

`linker::bridges::BridgeStaticlib::sources_are_newer_than` walks `crates/<bridge>` and, if any file there is newer than the archive in target/<profile>/, `archive_path()` SPAWNS CARGO to rebuild that staticlib — from inside an ordinary elephc invocation. The wait is charged to the "Linking native output" phase of `--timings`, and the rebuilt archive changes the linked binary.

Measured 2026-09-05: while another agent was editing crates/elephc-magician, a freshprobe2 link reported 21.57 s where the same link minutes later reported 164 ms, and a Symfony link reported 24.94 s against a true ~1.17 s. Worse, a HEAD-vs-patched binary comparison came back "8,941,957 bytes differ" with the user .s byte-identical: every differing symbol was a `GCC_except_table*` landing pad from the Rust archive, `Section __text` +1080 and `__eh_frame` -412. The patch under test (a linker change) was innocent; libelephc_magician.a had been rebuilt between the two captures (29,775,704 -> 29,809,848 bytes).

Two consequences. First, "one cargo at a time on this target/" cannot be enforced by agent discipline alone, because the product spawns its own. Second, ANY compile-time measurement or binary-identity gate is invalid unless the bridge archives are pinned.

The fix is supported: `archive_path()` short-circuits on a per-bridge environment variable and never consults source mtimes when it is set. Copy target/<profile>/libelephc_*.a to a frozen directory and export all twelve — ELEPHC_TLS_LIB_DIR, ELEPHC_PDO_LIB_DIR, ELEPHC_CRYPTO_LIB_DIR, ELEPHC_BCMATH_LIB_DIR, ELEPHC_ICONV_LIB_DIR, ELEPHC_PHAR_LIB_DIR, ELEPHC_TZ_LIB_DIR, ELEPHC_IMAGE_LIB_DIR, ELEPHC_PROBE_LIB_DIR, ELEPHC_INSTR_LIB_DIR, ELEPHC_WEB_LIB_DIR, ELEPHC_MAGICIAN_LIB_DIR. `touch target/<profile>/libelephc_*.a` also works but only until the next edit under crates/. Freeze the archives of the SAME worktree whose compiler will link them: an archive from another worktree carries that worktree's crate state.

With archives frozen, the binary IS reproducible: two compiles of freshprobe2 with the same compiler produced byte-identical binaries, twice. Binary-identity gates are sound once this is done, and unsound before.
Evidence: Archive mtime moved to 13:44 and 13:52, matching my own compile timestamps, while I ran no cargo; size changed 29,775,704 -> 29,809,848. `find crates/elephc-magician -type f -newermt '2026-09-05 13:40'` returned 19 files. nm diff of the two binaries: every added/removed name a GCC_except_table*. size -m: Section __text 8277024 vs 8278104. After `touch target/release/libelephc_*.a`, two consecutive N=1 compiles compared byte-identical (cmp exit 0). Env-var short-circuit read at src/linker/bridges.rs:435.
Verified by: cmp of two freshprobe2 binaries before and after freezing the archives; ls -la mtimes; find -newermt; nm -n and size -m diffs
