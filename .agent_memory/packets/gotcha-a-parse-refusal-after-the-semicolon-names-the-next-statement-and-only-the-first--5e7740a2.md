# A parse refusal after the semicolon names the next statement, and only the first failure position survives

> Two properties of the eval parser make its refusals point at innocent code, and they compound. FIRST: several stateme…

Two properties of the eval parser make its refusals point at innocent code, and they compound. FIRST: several statement parsers consume the terminating semicolon BEFORE they decide whether they can lower the target, so a refusal is reported while the cursor already sits on the NEXT statement's first token. That is how a broken increment on line 179 got reported as UnexpectedToken at the return on line 181, and how a broken append got reported at the following if or unset. SECOND: Parser keeps error_pos, the FIRST failure position seen, and does not overwrite it on later attempts, so with backtracking the reported line can belong to a completely different statement than the one that actually failed. Chasing the named token sends you into the return, if or unset parser where nothing is wrong. When a diagnostic names a keyword that opens a statement, suspect the statement BEFORE it and reduce that one in isolation rather than reading the parser for the named token.

The concrete gap this exposed: prefix ++ and -- on an array ELEMENT had no statement lowering. parse_prefix_inc_dec_stmt and parse_prefixed_property_inc_dec_stmt both hand their parsed target to property_inc_dec_stmt, which knows only property shapes, so plus-plus on a-bracket-k-bracket-c and plus-plus on this-arrow-m-bracket-k were refused outright. They now share one inc_dec_stmt_for_target: a property target keeps its dedicated statement, any other assignable target becomes the same CompoundAssign read-modify-write that parse_prefix_inc_dec_expr already builds, so the statement and expression spellings agree by construction.

The STATIC spellings needed the DISPATCHER relaxed, not the lowering extended. current_starts_prefixed_static_property_inc_dec matched the prefix plus self-colon-colon-dollar-t without looking at what followed, so an indexed target was routed to EvalStmt::StaticPropertyIncDec, which cannot express an element write, and then demanded a semicolon it could not find. Both static guards now decline when a bracket follows the property.

MEASURED, NOT ASSUMED: the POSTFIX statement spelling already worked. Only the prefix form was missing, which is why the gap was invisible from the suite. Pin the working half in the same file as the broken one: with the fix disabled it is the single test that stays green, which is what tells a later reader which half the fix actually bought.
Evidence: php -n 8.5.6 prints 2 / 2;n / 4 / 13;2;11 / 1;1 on the five fragments and elephc now prints the same. Sentinels: disabling the element fallback fails four of the five tests and leaves the postfix one green; reverting the static dispatch guard fails exactly the property-and-static test. Symfony measurement: KernelTrait.php moves from a refusal at line 181 to one at line 547 on a different construct; the reducer corpus goes from 23 refusals of 37 to 22.
Verified by: cargo test -p elephc-magician --lib with no skips: 1377 passed, 0 failed, 0 filtered (commit f7046c2be2)
