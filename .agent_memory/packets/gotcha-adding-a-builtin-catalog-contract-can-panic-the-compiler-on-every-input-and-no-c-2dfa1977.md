# Adding a builtin catalog contract can panic the compiler on every input, and no cargo gate sees it

> Adding register tick function / unregister tick function to crates/elephc builtin contract/src/catalog data.rs so the…

Adding `register_tick_function`/`unregister_tick_function` to `crates/elephc-builtin-contract/src/catalog_data.rs` so the interpreter could bind them made the elephc COMPILER panic at startup on every input: `shared builtin contract register_tick_function requires an AOT registry binding`, from `validate_shared_aot_coverage` in src/builtins/registry.rs. Not on some program -- on all of them; `elephc anything.php` died before reading the file.

WHY NO GATE CAUGHT IT, which is the reusable part:
- `cargo check --workspace --all-targets` type-checks and never runs, and this is a runtime assertion inside a lazily-built map;
- `cargo test -p elephc-magician --lib` (1484 tests) never touches the compiler's registry;
- `cargo test -p elephc-builtin-contract` PASSED, because the three census assertions had just been updated to agree with the new counts -- the census guards catalog SIZE, not catalog coverage;
- the codegen tests would have caught it, but they take hours and were not run.
The only cheap thing that catches it is compiling one PHP file with the built binary. After any `catalog_data.rs` edit, run `cargo build --bin elephc` then `target/debug/elephc --quiet --output-dir DIR some.php` before believing any other green.

THE RULE: every `BuiltinKind::Function` contract in the shared catalog must have an AOT registry binding, or `aot_support()` must declare its absence with a reason. Adding a contract is therefore a two-sided commitment, never an interpreter-only one.

THE FIX SHAPE: when the interpreter grows a surface the compiler has no machinery for, declare the absence rather than fake a binding. `UnsupportedReason::AotImplementationPending` (added here) is the mirror of the existing `EvalImplementationPending`, with the names listed in `AOT_IMPLEMENTATION_PENDING` so the gap is auditable. A registry binding that did nothing would have compiled and reported a tick handler installed that is never called -- worse than refusing. Do NOT file such names under the pre-existing `EvalOnlyReflection` escape just because it is the only one that exists: a one-line fix that makes the reason lie is worse than a new variant. `declare(ticks=N)` genuinely has no AOT counterpart because the compiled backend emits no per-statement hook.

Census bookkeeping when adding a catalog entry: `contracts().len()` in registry.rs, plus `eval_registry` / `aot_registry` / `aot_unsupported` / `interpreter_adapter` in support.rs. An eval-only contract raises `aot_unsupported`, not `aot_registry`.
Evidence: Reproduced by running target/debug/elephc on a two-line runner.php: panic at src/builtins/registry.rs:125 before any compilation. cargo check --workspace --all-targets, cargo test -p elephc-magician --lib (1484 passed) and cargo test -p elephc-builtin-contract (16 passed) were all green at the same commit. After adding UnsupportedReason::AotImplementationPending the same command compiles and runs.
Verified by: target/debug/elephc --quiet --output-dir DIR runner.php compiles and the produced binary runs; elephc-builtin-contract 16/0; magician --lib 1484/0. Regression introduced by 891dec3a5e, fixed by 12ec45f0cf.
