# Ternary EXPRESSIONS (ExprKind::Ternary, lowered by lower_ternary in src/ir_lower/expr/mod.

> Ternary EXPRESSIONS ExprKind::Ternary, lowered by lower ternary in src/ir lower/expr/mod.rs have a static type vs run…

Ternary EXPRESSIONS (ExprKind::Ternary, lowered by lower_ternary in src/ir_lower/expr/mod.rs) have a static-type-vs-runtime-representation divergence bug for locals mutated ASYMMETRICALLY across branches — a THIRD gate in the "static type vs runtime repr" bug family (alongside if/elseif, which IS fixed with restore-at-split + join-tail record-sticky; and switch/try/match, which are documented as open). Repro: `$a=[0]; $c=false; $c ? $a[]="x" : 0; var_dump($a);` — the THEN branch pushes a Str into `$a` (array<int>), triggering array_to_mixed + store_local(slot, array<mixed>). The ELSE branch (`0`) never touches `$a` at all. ir_lower's pre-pass has already decided the POST-merge type of $a is array<mixed> and retypes EVERY read of slot[0] within BOTH branches to array<mixed> (confirmed via --emit-ir --no-ir-opt) — but because the untaken... wait taken (c=false) ELSE branch does nothing to slot[0], the runtime bytes stay the ORIGINAL native array<int> layout from array_new/array_push at entry, while merge-point codegen reads it as array<mixed>. Result: var_dump prints `array(1) { }` (empty body, but correct count=1) — silent representation corruption, NOT a refcount leak (--heap-debug reports clean in both branch directions). The corruption ONLY appears when one branch does not touch the variable at all; if BOTH branches touch it (e.g. `$c ? $a[]="x" : ++$a[0];`), array_get/array_set/mixed_numeric_binop apparently handle the representation transparently and var_dump is correct in both branch directions (verified with c=true and c=false). This means the newly-added expression-position array-append feature (parser: src/parser/expr/pratt.rs LBracket empty-index handling + src/parser/expr/assignment_targets.rs build_append_assignment_expression) is safe for the required/tested shapes (both branches touch the same array) but can silently corrupt reads when only one ternary branch mutates a shared array and the other branch skips it entirely. Fixing lower_ternary to insert branch-tail coercion for asymmetrically-widened locals (mirroring the if/elseif fix) is a separate, larger EIR task, not part of the expr-position-assignment feature.
Evidence: --emit-ir --no-ir-opt on /tmp/g13.php and /tmp/g14.php on macOS-aarch64; --heap-debug confirms no refcount leak, only representation mismatch; PHP cross-check via php -r / php file.php
Verified by: Manual compile+run comparison against PHP 8.5.6 CLI for g13 (corrupts), g14/g15/g16 (both directions correct)
