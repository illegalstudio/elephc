# The eval parser had no (object) cast keyword while the AOT parser did

> elephc has TWO PHP parsers and they did not agree about casts. The AOT parser's peek cast in src/parser/expr/calls.rs…

elephc has TWO PHP parsers and they did not agree about casts. The AOT parser's peek_cast in src/parser/expr/calls.rs has always recognised object and produces CastType::Object. The eval/interpreter parser's peek_cast_type in crates/elephc-magician/src/parser/expressions/precedence.rs listed only int, float, string, bool and array, so (object) fell through to the ordinary parenthesised-expression rule and parsed as the constant named object. The refusal then landed on whatever token followed the closing paren, which is why one missing keyword produced two unrelated-looking diagnostics: ExpectedSemicolon at the variable in (object) $output, and UnexpectedToken at the => inside (object) ['mark' => 0]. Reading either diagnostic literally sends you into the array-literal or statement parser, where nothing is wrong. When an eval-only construct is refused, compare against the AOT parser first: a construct that compiles in a normal build but is refused inside eval means the gap is in the magician parser, not in the language support.

PHP's (object) cast is four rules, not one, and a test covering only the associative-array case passes against three wrong answers. An object casts to ITSELF, so (object) $p === $p is true, writes through the result reach the original, and get_class stays the original class rather than becoming stdClass. An array becomes a stdClass keyed by its own keys with integer keys included, so (object) [10, 20] has properties named "0" and "1" and json_encode prints {"0":10,"1":20} rather than a JSON array. Null becomes an EMPTY stdClass rather than one holding a null property. Every other scalar becomes a stdClass with the single property named scalar, which is php's own choice of name. All four measured with php -n 8.5.6.

Implementation rule that keeps the result visible to every reader: write the array arm through eval_property_set_result, the same entry point $o->k = v uses, not through the raw values.property_set op. That keeps the ElephcEvalContext dynamic-property overlay and the object's own slots in step, which is what get_object_vars, json_encode, print_r and the (array) cast back all depend on. Ownership: array_iter_key allocates the key and array_get boxes the element, both OWNED handles, and the property write retains what it keeps, so the casting frame still owes a release on each.
Evidence: php -n 8.5.6 on the same fragments prints stdClass;a=1;b=two;n=2 / {"0":10,"1":20};10;20 / hello;42;0;stdClass / same;9;P / 3;0;7;{"regexMark":3,"regex":[],"mark":7}, and elephc now prints the same. Sentinels: removing object from the cast keyword list fails all five interpreter tests; making the object arm build a fresh stdClass and renaming scalar to value fails exactly the identity and scalar tests; prefixing property names fails exactly the three array tests. Symfony measurement: yaml/Inline.php goes from refused to fully parsed, and routing/Matcher/Dumper/CompiledUrlMatcherDumper.php moves from a refusal at line 260 to one at line 365 on the next construct.
Verified by: cargo test -p elephc-magician --lib with no skips: 1362 passed, 0 failed, 0 filtered (commit 16e7663746)
