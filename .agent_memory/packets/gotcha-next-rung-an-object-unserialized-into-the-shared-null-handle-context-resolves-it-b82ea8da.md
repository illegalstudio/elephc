# Next rung: an object unserialized into the shared null-handle context resolves its class in the ASKER's table, and fixing only that uncovers a class with no methods

> Symfony's compiled web binary serves the 404 welcome page on the FIRST request and kills the worker on the SECOND, al…

Symfony's compiled `--web` binary serves the 404 welcome page on the FIRST request and kills the worker on the SECOND, alternating forever. Measured cause, traced end to end with ELEPHC_EVAL_TRACE=1:

Request 1 writes the routing-cache `.meta`, which now contains a real `O:72:"...ContainerParametersResource"` fragment (the serialize hook works). Request 2 reads it back, so `ResourceCheckerConfigCache` runs `ContainerParametersResourceChecker::supports()` -- which now answers TRUE where it used to answer false on a bare `O:8:"stdClass":0:{}` -- and then `isFresh()`, which dies at `ContainerParametersResourceChecker.php:35` on `$resource->getParameters()` with `unsupported MethodCall expression`. So the serialize fix is what made this rung reachable: correct data, newly exercised path.

The trace line that decides it: `phase=method_dispatch method="getParameters" identity=4495953216 dynamic_class=None runtime_class=Some("stdClass")`. The object has no declared class in the asking context, so dispatch falls back to the runtime header's stdClass and the native call is fatal.

Mechanism: `ffi/unserialize_objects.rs` hydrates into `crate::ffi::context::shared_null_handle_context()`, never into the context that later reads the object. `ElephcEvalContext::dynamic_object_class` then takes its owner branch, reads the owner's class KEY, and resolves it with `self.classes.get(class_key)` -- against the ASKER's table. That is precisely the failure the doc comment on the neighbouring `dynamic_object_declaring_class` already describes; the accessor next to it was never fixed.

DO NOT fix that one line alone. Changing it to `owner.classes.get(class_key)` was tried and measured: the class then resolves, `unsupported MethodCall` disappears, and the error becomes `Call to undefined method ContainerParametersResource::getParameters()` -- because the method is looked up with `context.class_method(name, ...)` on the ASKING context (`eval_dynamic_method_for_call` in interpreter/statements/reflection_instantiation.rs:326), which holds a different, method-less declaration of that name. Observably it is WORSE: before, request 2 killed the worker and request 3 got a fresh one that rendered the page (50% success); after, request 1 renders and every later request is a 500. The change was reverted.

The complete fix dispatches the method against the DECLARING context, the way the generator work publishes owner contexts: resolve `(owner, class)` through `dynamic_object_declaring_class`, look the method up in the owner's table, and execute the body with the owner's context for property, static and constant access.
Evidence: ELEPHC_EVAL_TRACE=1 over two requests against the compiled examples/symfony-app/public/index: `phase=unserialize_declared_object name="...ContainerParametersResource" hydrated=true payload_tag=5 payload_len=1` followed by `phase=method_dispatch method="getParameters" ... dynamic_class=None runtime_class=Some("stdClass")` and `phase=native_method_error stage=invoke class="stdClass" method="getParameters" status=RuntimeFatal`. Six consecutive requests before the experiment: 404, dead, 404, dead, 404, dead. After it: 404 then 500 for every later request.
Verified by: two-request and six-request runs against the compiled Symfony --web binary at both an 8 MiB and a 1 GiB heap (identical, so not memory-related)
