# Never reload a parked register pair into string_result_regs: on x86_64 it aliases int_result_reg

> When hand writing target aware codegen assembly that allocates a fresh heap object into abi::int result reg and then …

When hand-writing target-aware codegen assembly that allocates a fresh heap object into abi::int_result_reg and then reloads a previously parked (pushed) pair of registers in order to store into that object fields, NEVER reload into abi::string_result_regs. The register table is src/codegen_support/abi/registers.rs (it moved there from src/codegen/abi/registers.rs): int_result_reg at lines 81-86 returns x0 on AArch64 and rax on x86_64; string_result_regs at lines 99-104 returns (x1, x2) on AArch64 but (rax, rdx) on x86_64. On AArch64 there is no collision, so the bug is invisible on the native macOS dev target; on x86_64 the first element of the pair IS int_result_reg, so popping into it silently clobbers the freshly allocated object pointer before any field is stored and corrupts every heap object built that way. Reload into dedicated scratch registers instead - x9/x10 on AArch64, r10/r11 on x86_64 - whenever the reload happens after the object pointer is already sitting in int_result_reg. The same trap applies to float_result_reg only on AArch64 (d0) versus x86_64 (xmm0), which do not collide. Historical note: this was found while implementing SPEC I2 (checked-downcast-on-return TypeError construction) in src/codegen_ir/lower_inst/objects/return_type_guard.rs, and fixed there with a message_scratch_regs() helper. Neither that file nor that helper exists any more - not in the merged tree, not at the pre-merge branch tip 8da22fe141, not in origin/main - so treat the SPEC I2 story as history and the register rule as the durable part. The convention it mirrored still exists as pop_reg_pair into x9/x10 in the reflection lowering, now at src/codegen/lower_inst/objects/reflection.rs and its submodules.
Evidence: Read src/codegen_support/abi/registers.rs:81-111 on the merged worktree: int_result_reg returns x0/rax, float_result_reg returns d0/xmm0, string_result_regs returns (x1,x2)/(rax,rdx). git grep for return_type_guard and for message_scratch_regs returns nothing in the worktree, in HEAD 8da22fe141 or in origin/main. kage reverify refused the predecessor packet with "All cited paths are gone - reverify would rubber-stamp dead evidence".
