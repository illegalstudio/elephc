# Bisection of the "secrets.local_vault" ServiceNotFoundException (Symfony --web fixture, wo

> Bisection of the "secrets.local vault" ServiceNotFoundException Symfony web fixture, worker crashes with ServiceNotFo…

Bisection of the "secrets.local_vault" ServiceNotFoundException (Symfony --web fixture, worker crashes with ServiceNotFoundException for secrets.local_vault during cold container compile): the destructor-timing and hash-bucket fixes in commit 8600e6af6b do NOT fix it — rebuilt the --web binary after that commit and the request still fails identically (HTTP=000, same ServiceNotFoundException, 5 worker restarts). Two layers were isolated and BOTH work correctly under elephc, ruling them out: (1) loading vendor/symfony/framework-bundle/Resources/config/secrets.php standalone via a real PhpFileLoader (probe used examples/symfony-app/vendor/autoload.php + Symfony\Component\Config\FileLocator + Symfony\Component\DependencyInjection\Loader\PhpFileLoader) registers all 4 checked ids (secrets.vault/env_var_loader/decryption_key/local_vault) identically to php -n immediately after $loader->load() returns — no reference-cycle or destructor-timing issue here, because the REAL Symfony ServicesConfigurator/ServiceConfigurator classes do NOT hold a parent->current-child back-reference (verified by reading vendor/symfony/dependency-injection/Loader/Configurator/ServicesConfigurator.php and AbstractServiceConfigurator.php); registration happens via ServiceConfigurator::__destruct() -> $this->container->setDefinition(), triggered by the NEXT ->set() call in the chain or by the whole statement's discarded-temporary release at statement end (the already-working d16_symfony_exact shape in the destructor corpus). (2) The Symfony Config-tree default resolution for FrameworkExtension's 'secrets' node (Symfony\Bundle\FrameworkBundle\DependencyInjection\Configuration + Symfony\Component\Config\Definition\Processor, processing an empty [[]] config to force pure defaults) resolves local_dotenv_file to the correct non-empty default string '%kernel.project_dir%/.env.%kernel.environment%.local' (truthy), matching php exactly. The actual removal happens in FrameworkExtension::registerSecretsConfiguration() (vendor/symfony/framework-bundle/DependencyInjection/FrameworkExtension.php, ~line 1941): `if ($config['local_dotenv_file']) { ...replaceArgument... } else { $container->removeDefinition('secrets.local_vault'); }` — under default config this branch should take the truthy arm (as isolated testing shows), so the divergence must be somewhere in the FULL FrameworkExtension::load() pipeline (bundle registration, kernel parameter bag setup via Kernel::getKernelParameters()/initializeContainer(), and/or how $configs gets merged across bundles before reaching registerSecretsConfiguration) that was NOT reproduced by the two isolated probes — reproducing that requires a much heavier probe (real kernel boot up to but excluding $container->compile(), or hooking Kernel::initializeContainer()) that was not completed this session for budget reasons. Separately, found and verified a REAL, independent bug: elephc's reference-cycle collector (__rt_gc_collect_cycles in src/codegen_support/runtime/arrays/gc_collect_cycles.rs, a full 4-pass mark-and-sweep that DOES correctly invoke __destruct via __rt_call_object_destructor during its free pass) is only ever triggered by lowering an explicit PHP unset() statement (src/ir_lower/expr/unset.rs calls ir_lower::ownership::collect_cycles) — there is no automatic trigger at function-frame teardown, at script/request shutdown, or via a callable gc_collect_cycles() builtin (calling gc_collect_cycles() in PHP source hits 'Call to undefined function', it is not registered in the checker's builtin table). A standalone reproduction (two classes with a mutual back-reference held only by a private nullable property, no unset() anywhere) leaks forever under elephc while php reclaims it at request shutdown. This is confirmed to correspond to 3 pre-existing failing tests already in the suite: codegen::runtime_gc::cow_and_cycles::test_gc_collect_cycles_reclaims_object_self_cycle / test_gc_collect_cycles_reclaims_array_object_cycle / test_gc_collect_cycles_reclaims_mixed_object_hash_cycle (these fail even on unset()-based reproductions relying on PHP's threshold/GC path, not just my no-unset variant), part of the 35 known-failing runtime_gc baseline. This gap is real but was NOT proven to be the specific secrets.local_vault blocker (the real Configurator classes don't form a cycle for that particular closure), so fixing it is not expected to resolve the --web request on its own — a next session should either (a) reproduce the full kernel boot pipeline up to registerSecretsConfiguration to find the true divergence, or (b) wire gc_collect_cycles automatically at request/script shutdown and function-frame teardown as a separate, independently-valuable fix.
Verified by: Two isolated probes (examples/symfony-app/probe_secrets.php, examples/symfony-app/probe_config_tree.php, both untracked, deleted binaries after running) compiled with elephc and compared byte-for-byte against php -n output from the same directory; standalone cycle-leak probe compared allocs/frees under --heap-debug; rebuilt examples/symfony-app/public/index after commit 8600e6af6b and re-ran the HTTP request, same ServiceNotFoundException.
