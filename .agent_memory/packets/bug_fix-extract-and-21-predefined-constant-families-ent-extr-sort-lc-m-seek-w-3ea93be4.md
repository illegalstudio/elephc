# extract() and 21 predefined constant families (ENT_*, EXTR_*, SORT_*, LC_*, M_*, SEEK_*) w

> extract and 21 predefined constant families ENT , EXTR , SORT , LC , M , SEEK were undefined in the tree walking inte…

extract() and 21 predefined constant families (ENT_*, EXTR_*, SORT_*, LC_*, M_*, SEEK_*) were undefined in the tree-walking interpreter (eval bridge used for runtime includes/eval()), fataling Symfony's HtmlErrorRenderer 404 template. Both are now implemented. Key architectural finding: crate::ffi::extract (the compiled backend's own eval-bridge FFI for extract()) is entirely cfg(not(test))-gated, so it cannot be reused directly by interpreter code that must compile under `cargo test`. The fix was extracting the truly shared, dependency-light pieces (EXTR_* mode constants and the extract_target_name collision/prefix policy, which only need ElephcEvalScope and the generic RuntimeValueOps trait, never the concrete ElephcRuntimeOps runtime-hook bridge) into a new always-compiled crate::extract_policy module at the crate root, imported by both crate::ffi::extract and crate::interpreter::builtins::array::extract. This is the general pattern for sharing logic between an FFI module and interpreter code in this crate: check whether the FFI module is cfg(not(test))-gated before assuming direct reuse is possible, and if so, hoist the test-safe subset to an ungated sibling module rather than trying to lift the cfg gate (which exists for a reason, likely ElephcRuntimeOps unavailability in test builds). Also found: elephc's eval bridge `echo` on a float prints the full round-trip decimal instead of PHP's default precision=14-truncated form (a pre-existing, general, interpreter-only divergence unrelated to any specific builtin -- the compiled/AOT backend's float-to-string DOES match php's precision=14 correctly); tests that need to verify a float CONSTANT's value against php should use `round($x, N)` rather than raw `echo` to sidestep this. Also found: extract()'s first parameter is by-reference in real PHP (`array &$array`) and even a `call_user_func('extract', ...)` indirection still writes into the calling PHP scope (verified empirically) -- elephc's interpreter only supports the direct/syntactic call form (via the EvalDirectHook path, which threads `scope`); named-args, spread, and reflective invocation of extract() are unimplemented since the "values" hook dispatch path in this codebase never receives `scope` at all. Also found: the compiled (AOT) backend has its own, narrower predefined-constant surface than the eval bridge now has for ENT_DISALLOWED, SORT_ASC/DESC, LC_ALL/COLLATE/MONETARY/TIME/MESSAGES, ten of the M_* family, and all of SEEK_* -- confirmed via direct AOT compilation probes, not fixed (out of scope, would require touching src/types/ent_constants.rs, src/types/array_constants.rs, src/codegen_support/prescan.rs in the main elephc crate).
Evidence: php -n gate.php x1 x2 x3 v9 all report IDENTICAL after the fix (previously all 4 DIFFERED); cargo test -p elephc-magician --lib shows 1551 passed / 2 failed (the 2 pre-existing failures, unchanged names, in interpreter::tests::core, unrelated to this change) both before and after; revert sentinels on both commits reproduced the exact original fatal/mismatch text.
Verified by: cargo test -p elephc-magician --lib (19 new tests passing); php -n $R/gate.php x1 x2 x3 v9 ep1 ep2 ep3 vet vct mfam aot_known aot_new against the rebuilt release probe binary
