# method_exists/property_exists on a class-string now resolve through the autoloader like new and class_exists; reflected method names keep their declared case; an unreadable classmap file warns instead of vanishing

> Commit b7ad5cb0d7 tests in 35c0b2fa98 . Three generic fixes. 1 method exists and property exists answered from whatev…

Commit b7ad5cb0d7 (tests in 35c0b2fa98). Three generic fixes. (1) `method_exists()` and `property_exists()` answered from whatever class metadata happened to be loaded already; PHP resolves their class-string argument with zend_lookup_class, the same resolution `new $name` and `class_exists($name)` use, so a registered autoloader runs first. On the real vendor shape a Composer autoloader registered from inside a class method survives into the binary, the interpreter defines the class on demand for `new $cls` and `new ReflectionClass($cls)`, and only the member probes refused to look — they now resolve the target the same way (crates/elephc-magician/src/interpreter/builtins/symbols/method_exists.rs, the reflection method-members lowering under src/codegen/lower_inst/objects/reflection/, src/codegen_support/runtime/data/user.rs). (2) Method names lost their case on the way out: method tables are keyed by php_symbol_key and four places handed the key back as the answer, so ReflectionMethod getName, ReflectionClass getMethod then getName, and every entry of getMethods reported the lowercased spelling; the lookup is case-insensitive, the answer is not — the declared spelling was already in reach at each site (method_decls for classes and interfaces, the declared-name list for traits, the generated name table for the interpreter's AOT path, matched by the runtime scanners with a case-insensitive compare). (3) A classmap file the autoload index cannot read, lex or parse contributed no classes and said nothing, so every class it declared went undefined with a diagnostic pointing at the use site; src/autoload/index.rs now warns, naming the file and the reason. CAVEAT measured right after: the Symfony --web request verdict did NOT change (still `Invalid service router.default: method Router::setConfigCacheFactory() does not exist`), so in the real chain something else still keeps the parent class's method from the container — next suspects: the interpreter's own parser failing on the same `new $this->prop[...]()` form in vendor/symfony/routing/Router.php, the parent or interfaces not resolved before the probe answers, or inherited methods missing from an interpreted class's table.
Evidence: php -n vs elephc on a class reached only through a runtime-registered autoloader (true vs false before), reflected method case (CamelCaseOne vs camelcaseone before), tests pinned in 35c0b2fa98; Symfony rebuild from 35c0b2fa98 + curl: verdict unchanged.
Verified by: commit b7ad5cb0d7 and 35c0b2fa98; php -n; Symfony --web rebuild + request
