# A method declared `self`/`static` (or any type, including a plain class name and `?self`/`

> A method declared self / static or any type, including a plain class name and ?self / ?static that returns $this , ca…

A method declared `self`/`static` (or any type, including a plain class name and `?self`/`?static`) that returns `$this`, called as a discarded statement (`$o->add("a");`) or via `$this->m();` inside another method, was refused with a bare `unsupported MethodCall expression`. Root cause: `eval_method_call_with_temporary_receiver_cleanup` in crates/elephc-magician/src/interpreter/expressions.rs only retained the returned value when it aliased the receiver (`result == receiver`) IF the receiver was "temporary" (a `new`/`clone`/chained-call expression per `eval_method_receiver_is_temporary`). For an ordinary variable receiver (`$o`, a `LoadVar`, not "temporary"), no retain ever happened anywhere on the return-of-`$this` path (the callee binds `this` as `ScopeCellOwnership::Borrowed`, and `LoadVar` reads are aliases per `eval_expr_result_aliases_storage`). But `EvalStmt::Expr`'s discard path unconditionally calls `eval_release_value` on a `MethodCall` result (it is not on `eval_expr_result_aliases_storage`'s exemption list), so it released a reference `$o` still needed. The first discarded call destructed the object a call early (observable via `__destruct()`); the second discarded call or next use of the receiver then failed against an already-freed object, surfacing as the generic `unsupported MethodCall expression` label (the real refusal has nothing to do with `MethodCall` being unsupported -- something deeper failed silently and `eval_expr`'s first-writer-wins naming attached the OUTER expression kind because nothing inner described itself). Fix: move the `result == receiver -> retain` check out of the `if receiver_is_temporary` gate so it runs unconditionally; only the subsequent `eval_release_value(receiver)` stays gated on `receiver_is_temporary`. This fixes self/static/class-name/nullable return types, `$this->m()` calls inside another method, and chained calls whose final result is discarded while an intermediate is used as the next receiver -- all confirmed against `php -n` 8.5.6 (11/11 identical in $R/gate.php). Static factory calls (`Foo::make()` returning `new static()`) and a temporary-receiver-only discard (`(new Foo())->add("x");`) were already correct and remain unaffected. TDD proof lives in crates/elephc-magician/src/interpreter/tests/fluent_method_discard.rs, which uses the counted FakeOps fixture (support/mod.rs) -- an over-release there panics loudly ("released a fake cell nobody owned") instead of passing silently, which is what pinned this exact bug.
Evidence: cargo test -p elephc-magician --lib fluent_method_discard: 4 passed (0 before fix, 3 panicked with 'released a fake cell nobody owned'). php -n $R/gate.php on d1 d2 d3 d4 t24 plus 6 new family probes (fam1..fam6): 11/11 identical after the fix; d3/t24/fam2/fam3/fam4/fam5 differed before it (unsupported MethodCall expression, with fam2/3/4/5 also showing a premature destructor call).
Verified by: cargo test -p elephc-magician --lib (1665 passed / 2 pre-existing failures, same names as documented baseline); php -n /R/gate.php d1 d2 d3 d4 t24 fam1_static_call fam2_classname_return fam3_nullable_self fam4_nullable_static fam5_chain_intermediate fam6_temporary_receiver_only -> 11/11 identical; scripts/audit_php_text_parse.py --enforce -> no drift
