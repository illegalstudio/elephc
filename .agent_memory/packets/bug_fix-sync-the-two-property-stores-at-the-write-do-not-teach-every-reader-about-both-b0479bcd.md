# Sync the two property stores at the write, do not teach every reader about both

> An object in this interpreter has TWO property stores: the context's per object overlay, and the runtime object's own…

An object in this interpreter has TWO property stores: the context's per-object overlay, and the runtime object's own slots. Reads consult the overlay; almost everything that ENUMERATES walks the slots. A property that reaches only one of them is silently invisible to the other half, and because the plain read keeps working, each affected reader looks like its own unrelated bug. Seven failing tests across four files turned out to be this single split.

The write side was the asymmetry. Creating a property with an assignment on an interpreter-declared object put the value in the overlay only, because the slot write sitting right beside it is guarded on the property being DECLARED. Construction had the mirror problem: declared defaults went to the overlay alone. So an undeclared property was missing from the slots entirely, and a declared one was present by name but empty by value — which is exactly what the dump builtins printed.

The fix that generalises is to keep the two stores in step at the two points that WRITE, rather than teaching each reader about both. Once construction and the undeclared-assignment path write the slot as well as the overlay, every enumerator keeps reading one store and gets the right answer, and no future enumerator has to learn anything. Reads, the isset probe and the reflection existence checks keep the overlay as authoritative and consult it first, in the same alias-then-overlay-then-slot order the ordinary read path already used. The contrast with the previous echelon matters: there the right move was to teach the reflection READERS about the overlay, because only reflection was wrong; here, with six readers wrong, the economical fix moved to the writers.

Deleting is where a two-store design bites hardest, and it is worth knowing before starting. The value-ops trait has get, set and is-initialized for properties but NO removal primitive. So unsetting an undeclared property can null the slot and drop the overlay entry, but cannot take the name out of the slot list, and the name alone is enough to make an existence probe answer yes where the reference answers no. The way out without inventing a third store was the initialization marker that already existed: for an object the context owns, every live slot also carries one, so a slot without a marker is a property that was unset. Note the scope that keeps this honest — only UNDECLARED names reach that probe, so a declared-but-uninitialized typed property, which the reference does report as existing, is untouched. Adding a real removal primitive to the trait is the proper fix and reaches the ABI surface, which is why it was not done here.

One ordering caveat to record: the overlay is a hash map, so names drawn from it have no meaningful order. The reference reports dynamic properties in creation order. Sorting makes the answer deterministic rather than arbitrary, but matching creation order needs an insertion-ordered store in the context, and no amount of sorting will get there.

Two process notes. First, a change this broad has to be measured by reverting the working tree to the parent commit and re-running the same filters, not by assuming: doing that here showed two of the seven greens landed in dump-builtin fixtures the change was never aimed at, which is the kind of thing an assumption would have missed in both directions. Second, an intermediate state of this work traded one silent wrong value for another — the existence probe started answering yes after an unset — and the only reason that was caught before committing was a probe table that pinned several readers side by side against the reference in a single run. When a bug is "two readers disagree", the test that finds it has to exercise them together.
