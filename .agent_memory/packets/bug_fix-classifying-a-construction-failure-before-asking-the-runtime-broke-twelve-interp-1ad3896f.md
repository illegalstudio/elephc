# Classifying a construction failure before asking the runtime broke twelve interpreter tests: the autoload chain is an opportunity, not a verdict, and PHP never autoloads an internal class

> Échelon 45's first cut of eval new object result crates/elephc magician/src/interpreter/expressions/evaluation.rs mad…

Échelon 45's first cut of `eval_new_object_result` (crates/elephc-magician/src/interpreter/expressions/evaluation.rs) made an autoload-chain MISS the decision: no loader supplied the name, therefore the class does not exist, therefore raise PHP's `Class "X" not found`. That is wrong, and it cost twelve interpreter tests.

THE RUNTIME HAD NOT BEEN ASKED YET. `values.new_object` consults the generated AOT name table, which is a DIFFERENT table from the one `eval_autoload_target_exists` reads through `values.class_exists`. A class the runtime can allocate but whose name the autoload probe does not recognise was therefore condemned without a hearing. `new Box()` in the interpreter's own fixtures is exactly that shape — `FakeOps::class_exists` answers true only for `KnownClass` and `KnownFailingConstructor`, while `FakeOps::new_object` always succeeds — so twelve tests that had returned an object began failing `UncaughtThrowable`.

THE ORDER THAT IS CORRECT: reflection owners, then classes this context declares, then the autoload chain FOR ITS SIDE EFFECT ONLY (discard the boolean; it may declare the class, so re-ask the context afterwards), then `values.new_object`, and only when THAT fails classify the failure. Ask the authority, then classify — never the reverse.

PHP NEVER AUTOLOADS AN INTERNAL CLASS, and skipping the chain for catalog names is php-correct rather than an optimisation. `new Exception(...)` consults no loader in PHP because the name is already a class. Running the chain for it was also not side-effect-free: it allocates and releases cells of its own, which reordered the interpreter's release log and broke two further tests that assert the FIRST released handle is the thrown object (`execute_program_finally_return_overrides_uncaught_throw` and `execute_program_catches_throwable_without_variable_inside_eval`, both reading tag 1 where they expect tag 6). Gating the chain on `!eval_reflection_class_like_is_internal(class_name)` fixes the semantics and the side effect together.

ATTRIBUTION WAS MEASURED, NOT ARGUED. The same named tests were run on the same tree with only the four magician files reverted to 2a67991fda: 2 failed at base, 14 with the change, so 12 were mine and 2 (`execute_program_dispatches_spl_autoload_builtins`, `execute_program_foreach_iterates_eval_traversable_objects`) were pre-existing. After the reorder and the internal-class gate, only those 2 remain.

A SEPARATE, PRE-EXISTING OBSTACLE worth recording because it hides everything else: `cargo test -p elephc-magician --lib` cannot complete on this tree. `interpreter::tests::dynamic_calls::runtime_callables::execute_program_static_runtime_method_hook_binds_default_args` overflows its stack and SIGABRTs the whole process, taking the run's report with it; it does so at RUST_MIN_STACK=33554432 and at 134217728 alike, and it reproduces with the magician reverted to base, so it is infinite recursion rather than a stack-size setting. Skipping it only moves the abort to `execute_program_static_call_dispatches_runtime_method_hook`, then to `method_arguments::runtime_fallback::execute_program_writes_back_runtime_static_method_by_ref_before_fatal`. Until that family is fixed, the crate's failing set can only be sampled by name filters, not enumerated.
Evidence: Named-test runs on one tree with only the four magician files swapped: base 2a67991fda gave 2 failures, échelon 45 as first written gave 14, the reorder gave 4, and the reorder plus the internal-class gate gave 2 — the same 2 as base. Eight php -n 8.5.6 reducers all match exactly after the fix, including the two probes that separate the hypotheses: a catalog name the build HAS (`new DateTime('nonsense')` through a runtime include) prints `DateMalformedStringException;done` exactly as php, proving a build that owns the class still constructs it; a name the build has nowhere (`new Box()`) prints `Error: Class "Box" not found;done` exactly as php; and a catalog name the build LACKS (`new Fiber(...)`) reports `builtin class "Fiber" is not available in this build`. The codegen include_ filter is unchanged by the follow-up at 112 passed / 7 failed with the same seven names.
Verified by: cargo test -p elephc-magician --lib run under ten name filters on the fixed tree and on the same tree with the magician reverted to 2a67991fda; cargo test --test codegen_tests include_ before and after the follow-up; eight php -n 8.5.6 reducers

## Verification

The codegen include_ filter is unchanged by the follow-up at 112 passed / 7 failed with the same seven names.
