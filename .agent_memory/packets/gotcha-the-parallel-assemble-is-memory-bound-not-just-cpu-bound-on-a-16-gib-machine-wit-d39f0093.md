# The parallel assemble is memory-bound, not just CPU-bound: on a 16 GiB machine with swap full its speedup collapses from 3.21x to 1.21x, and the link does NOT grow with the cut count

> Measured 2026 09 05 while landing the compile time echelon. THE MACHINE IS 16 GiB AND SWAP RUNS FULL 4.76 of 5.12 GB …

Measured 2026-09-05 while landing the compile-time echelon. THE MACHINE IS 16 GiB AND SWAP RUNS FULL (4.76 of 5.12 GB used with several agents active). The Symfony --web `.s` is 861 MB and N=8 runs eight assembler processes over slices of it CONCURRENTLY, so the parallel path competes for memory as well as cores. Consequence: the SAME code, same compiler, measured an assemble phase of 54.22 s, 65.17 s, 80.74 s and 143.70 s on different runs of the same day. Against a paired N=1 control the split measured 3.21x on a quiet-ish window (load ~18) and about 1.21x when thrashing (load 22-35, swap full). Quote the RATIO from a paired window, never the seconds, and never compare two runs taken at different loads — on this machine unrelated phases move 20-30 % run to run, and "Lowering program to EIR" alone read 8.88 / 10.06 / 10.53 / 12.88 / 13.11 s across five runs of unchanged code, a spread wider than most individual patches are worth.

N CURVE, all four points back to back in ONE load window (contended: load ~30, swap full), Symfony --web release:
  N=1  assemble 138.14 s  link 1.39 s  total 235.97 s
  N=2  assemble 112.49 s  link 2.16 s  total 189.89 s
  N=4  assemble  71.65 s  link 1.53 s  total 155.85 s
  N=8  assemble  65.17 s  link 1.08 s  total 165.65 s
TWO CONCLUSIONS THAT TRANSFER EVEN THOUGH THE SECONDS DO NOT.
1. THE LINK DOES NOT GROW WITH THE CUT COUNT: 1.39 / 2.16 / 1.53 / 1.08 s shows no trend at all, just noise around ~1.5 s, even though N=8 publishes 46,843 cross-slice locals on this input. So the worry that finer cuts "buy back assembler time and hand it straight to the linker" is NOT observed at these cut counts, and an `ld -r` recombination step is unnecessary until the cut count grows by an order of magnitude.
2. RETURNS FLATTEN HARD AFTER N=4: N=4 to N=8 buys only 6.5 s of assemble. The data section is never cut, so it is a serial tail that bounds the speedup. Do not assume more slices is better.

TOOLING TRAP FOR ANYONE SAMPLING THE ASSEMBLER: /usr/bin/as on macOS is a SHIM THAT EXECS CLANG. A sampler matching process name `as` sees the process only for the instant before the exec and reports a few MB peak RSS for an 861 MB input, plus a peak concurrency lower than the slice count. Match `as|clang|cc1as` instead.
Evidence: Four Symfony --web --timings --keep-symbols runs at ELEPHC_ASM_JOBS=1/2/4/8 back to back on one release compiler with frozen bridge archives, uptime and sysctl vm.swapusage recorded before and after each point; plus a paired N=1/N=8 pair taken in an earlier, quieter window giving assemble 173.94 s -> 54.22 s. sysctl vm.swapusage showing 4756.62M of 5120.00M used; hw.memsize 16 GiB. `file /usr/bin/as` plus `as -arch arm64` reporting a clang diagnostic.
Verified by: Reproduced across seven Symfony --web runs and five freshprobe2 runs in one session; the non-assemble phases agree within noise inside each paired window, which is what makes the paired ratios trustworthy and the cross-window seconds untrustworthy

## Verification

Four Symfony --web --timings --keep-symbols runs at ELEPHC_ASM_JOBS=1/2/4/8 back to back on one release compiler with frozen bridge archives, uptime and sysctl vm.swapusage recorded before and after each point; plus a paired N=1/N=8 pair taken in an earlier, quieter window giving assemble 173.94 s -> 54.22 s. sysctl vm.swapusage showing 4756.62M of 5120.00M used; hw.memsize 16 GiB. `file /usr/bin/as` plus `as -arch arm64` reporting a clang diagnostic.
