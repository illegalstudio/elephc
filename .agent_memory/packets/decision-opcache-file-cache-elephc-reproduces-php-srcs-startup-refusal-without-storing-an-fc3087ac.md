# opcache.file_cache: elephc reproduces php-src's startup refusal without storing anything on disk

> elephc has no on disk opcode cache, so opcache.file cache was treated as inert and opcache is script cached in file c…

elephc has no on-disk opcode cache, so `opcache.file_cache` was treated as inert and `opcache_is_script_cached_in_file_cache()` returns a permanent `false`. That missed half the directive: reference PHP VALIDATES THE DIRECTORY AT STARTUP AND REFUSES TO RUN if it is unusable — observable behaviour independent of any caching. Implemented in crates/elephc-magician/src/script_cache/file_cache.rs, VERIFIED against reference PHP 8.5.10:

- THE VALIDATION IS GATED ON THE CACHE BEING ENABLED. `-d opcache.enable=0` and the CLI default `-d opcache.enable_cli=0` both run the script with NO validation at all, however broken the path. This is why the check drops into the existing `ScriptCacheConfig::enabled` gate rather than needing a new one.
- An EMPTY `opcache.file_cache` means unset (php-src's C NULL default) and validates nothing.
- A bad value fatals with `opcache.file_cache must be a full path of an accessible directory` and exits 254 (php-src's `exit(-2)`). "Bad" = not absolute (a bare `.` fatals despite existing), missing, not a directory, or failing `access()`.
- THE ACCESS MODE DEPENDS ON read_only: `R_OK|W_OK` normally, `R_OK` alone when `opcache.file_cache_read_only=1`. `/` is the discriminating fixture — readable, not writable: read-only runs, read-write fatals.
- `opcache.file_cache_read_only=1` with an empty/unset path is its OWN distinct fatal: `opcache.file_cache_read_only is set without a proper setting of opcache.file_cache`. 8.5-only directive.
- The fatal PRINTS EVEN AT `opcache.log_verbosity_level=0`: the gate is `level <= verbosity` and FATAL is level 0. php-src runs the error handling outside the verbosity guard, so the exit happens regardless.

TWO KNOWN POSITION DIVERGENCES, both from the check running where the runtime cache is configured (first run-time eval-bridge call) rather than before the first statement: a binary that never reaches the bridge never validates, and output written before that point is already flushed when the fatal lands. Message and exit status are identical; only position differs. See the companion packet on const-folded eval.

DELIBERATELY NOT IMPLEMENTED: an actual on-disk cache. php-src's file cache stores compiled opcodes keyed by a `system_id`; elephc has no serialized form of its EvalIR (no serde in elephc-magician). A cache storing something cheaper while answering `true` to `opcache_is_script_cached_in_file_cache()` would be the first place this model reports a cache state PHP does not mean, so the honest `false` is kept.

ABI CONSTRAINT worth inheriting: this could not be four more parameters on `__elephc_eval_configure_opcache`, which already spends all six integer argument registers x86_64 SysV provides — `abi::int_arg_reg_name` indexes a 6-entry table there and panics past it. Hence a second 6-arg bridge symbol, `__elephc_eval_configure_opcache_file_cache`, emitted immediately after the first because the validation reads the enabled flag the first call installs.
Evidence: Probed reference PHP 8.5.10 for every row (enable=0/enable_cli=0 run clean; `.`, /etc/hosts, /no/such/dir and `/` fatal; `/` with read_only=1 runs; read_only without a path gives the second message; verbosity 0 still prints; exit 254). Reproduced by tests/opcache_file_cache_tests.rs, 12 tests passing, including the two position divergences.
Verified by: cargo test --test opcache_file_cache_tests (12 passed) plus direct php 8.5.10 -d probes
