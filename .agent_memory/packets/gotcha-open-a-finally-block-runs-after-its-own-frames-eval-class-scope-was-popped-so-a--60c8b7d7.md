# OPEN: a finally block runs AFTER its own frame's eval class scope was popped, so a private property write inside it is refused with the wrong scope on top

> OPEN, measured and NOT fixed. This is the current stop of the Symfony web request, reached after the builtin Throwabl…

OPEN, measured and NOT fixed. This is the current stop of the Symfony `--web` request, reached after the builtin-Throwable inheritance fixes landed. Symfony's `EnvVarProcessor::getEnv` has `try { ... } catch (ParameterCircularReferenceException) {} finally { $this->loaders = $loaders; }`. An `EnvNotFoundException` is thrown at line 224, does NOT match that catch, and propagates. The `finally` then runs and its write to the PRIVATE `$loaders` is refused: `Fatal error: Uncaught Error: Cannot access private property Symfony\Component\DependencyInjection\EnvVarProcessor::$loaders`, worker exit 255 (an uncaught PHP-level Error, not a bridge fatal -- exit 1 is the bridge, 255 is an uncaught php report).

The refusal itself is correct code doing its job: `validate_eval_member_access` (crates/elephc-magician/src/interpreter/statements/reflection_instantiation.rs:330) compares `context.current_class_scope()` against the declaring class. The defect is the SCOPE, not the check.

WHAT THE INSTRUMENTED TRACE SHOWS, logging every push/pop of the class stack with its depth:
  906: push depth=14 EnvVarProcessor      <- the outer getEnv frame enters
  941: pop  depth=13 EnvVarProcessor      <- that frame's scope is torn down
  (throw propagates outward; 6 more frames pop: EnvVarProcessor x2, Container, getSecrets_VaultService, App_KernelDevDebugContainer, getSecrets_EnvVarLoaderService)
  969: property_access_error declaring=EnvVarProcessor property=loaders visibility=Private current_class_scope=Some("ContainerTvPT0Dp\App_KernelDevDebugContainer")
So the finally body executes SEVEN frames later than its own frame's scope teardown, with an unrelated class on top of the stack. The write is judged from the container's scope and refused.

DO NOT RE-DERIVE THESE FOUR REDUCERS -- each was built, run against php -n 8.5.10, and each PASSED, so none of them is the shape: (1) try/finally restoring a private property around a non-matching catch, all inside eval; (2) the same with a 3-level exception chain bottoming out in an SPL exception; (3) the same crossing eval -> AOT static method -> eval closure -> throw, so the unwind passes through the native bridge; (4) the same compiled with --web. `eval_with_native_bridge_scope` (class_resolution.rs:474) and `eval_dynamic_method_with_values_and_ref_mode` (dynamic_method_execution.rs:90) were both read and are BALANCED -- they pop on the error arm as well as the success arm -- so the leak is not in either.

WHERE TO START: the question is not "who forgot a pop" but "why is the finally body executed at a point where the frame that owns it has already returned". Look at `execute_try_stmt` (crates/elephc-magician/src/interpreter/statements/exceptions.rs:13) against the propagation path: note that its `Err(EvalStatus::UncaughtThrowable)` arm does `let Some(thrown) = context.take_pending_throw() else { return Err(...) }`, which SKIPS the finally entirely when there is no pending throw to take -- a second, separate divergence from php worth a reducer of its own. The fix likely has to bind the finally body to its frame's class scope rather than to whatever is on top of the stack when it happens to run.

A NOTE ON INSTRUMENTING THIS: the push/pop trace that produced the evidence above was deliberately NOT kept. `push_class_scope` runs on every eval method call, and an `env::var_os` on that path costs on every run even with tracing off. Re-add it temporarily when working this bug, then take it out. The targeted `phase=property_access_error` trace in property_validation.rs WAS kept -- it is low volume and it is what turns this error from a verdict into a diagnosis.
Evidence: Compiled examples/symfony-app/public/index.php with `--web --timings --keep-symbols --heap-size=1073741824` (exit 0, 61 s) and issued one cold request on 1 worker. Server stderr: `Fatal error: Uncaught Error: Cannot access private property Symfony\Component\DependencyInjection\EnvVarProcessor::$loaders`, `worker exited with status 255`, curl HTTP=000 curlexit=52. ELEPHC_EVAL_TRACE=1 run (616 lines) gives the push/pop depth ladder quoted above and the single `phase=property_access_error ... current_class_scope=Some("ContainerTvPT0Dp\\App_KernelDevDebugContainer")` line. Four reducers under scratchpad red4, each compared against php -n 8.5.10 which prints `caught:RuntimeException:x / restored:1 / after`: all four printed the same under elephc, exit 0, i.e. all four FAILED to reproduce. Balanced push/pop confirmed by reading class_resolution.rs:474-483 and dynamic_method_execution.rs:176-250.
Verified by: ELEPHC_EVAL_TRACE=1 on the compiled Symfony --web binary (relink verified by mtime against the compiler/magician build, per the runbook's stale-binary trap), plus four non-reproducing php -n reducers
