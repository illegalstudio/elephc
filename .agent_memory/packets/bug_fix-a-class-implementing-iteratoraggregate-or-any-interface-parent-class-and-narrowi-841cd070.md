# A class implementing `\IteratorAggregate` (or any interface/parent class) and narrowing `g

> A class implementing \IteratorAggregate or any interface/parent class and narrowing getIterator : \Traversable to the…

A class implementing `\IteratorAggregate` (or any interface/parent class) and narrowing `getIterator(): \Traversable` to the concrete native class `getIterator(): \ArrayIterator` failed to declare with "class X could not be declared" — this is the exact shape Symfony's ParameterBag, HeaderBag, and RouteCollection all use, and it blocked Request::initialize() on every request in the --web campaign. Root cause: `eval_return_class_type_is_a` in crates/elephc-magician/src/interpreter/return_type_compat.rs resolves a declared class-like return/parameter atom by walking eval-declared classes (context.has_class), eval-declared interfaces (context.has_interface), the eval-parent chain (context.class_parent_names), and finally a hard-coded builtin INTERFACE parent table (builtin_class_like_parent_names, reached through context.interface_parent_names). `ArrayIterator` is a native CLASS with no eval declaration at all, so none of those branches ever answered it — the builtin table only lists interface names (Iterator, IteratorAggregate, OuterIterator, RecursiveIterator, SeekableIterator, Generator), not concrete SPL classes. Separately, `eval_array_iterator_class_is_a` in crates/elephc-magician/src/context/classlike_objects.rs already answers this exact membership question (ArrayIterator/Iterator/Traversable/Countable/ArrayAccess/SeekableIterator) for `instanceof` via `dynamic_object_is_a`, and its own doc comment says "both the instanceof answer and the declared-return-type check need it" — but the declared-return-type/parameter resolver never called it. Fixed by adding an early branch in `eval_return_class_type_is_a` (after the has_interface check, before the eval-parent-class fallback): `if actual_resolved.eq_ignore_ascii_case("ArrayIterator") { return eval_array_iterator_class_is_a(&expected_resolved); }`, importing `crate::context::eval_array_iterator_class_is_a`. This is NOT the same validator fixed in 282bfca042 (which corrected ClassInfo.abstract_methods / the AOT reflection ABSTRACT-bit read for parent-abstract-method presence) — it is a sibling gap in the separate SIGNATURE COMPATIBILITY / return-type-covariance resolver, which never touches AOT reflection metadata for native classes at all. Because `class_method_signature_accepts` (parent-class path, both eval-parent and AOT-native-parent) and `class_method_satisfies_interface_signature_with_return_mode` (interface path) both bottom out in the same `method_return_type_signature_accepts`/`eval_return_type_accepts`/`eval_return_class_type_is_a` chain — and parameter contravariance reuses the identical chain with expected/actual swapped — one fix covers the interface case, the parent-class case (both eval- and AOT-native-parent), and parameter widening uniformly. Verified: 11 new tests in crates/elephc-magician/src/interpreter/tests/native_class_return_type_covariance.rs, each asserting an observed php -n 8.5.6 value (never "no error" alone) — 4 were RED before the fix (interface narrowing, two-interface narrowing, parent-class narrowing, parameter-widening contravariance — all sharing the same root cause) and 7 were already GREEN as regression guards (unrelated-return-type refusal, void narrowing both directions, parameter narrowing refusal, never-overrides-void, nullable-narrowing refusal, self/static covariance). Differential gate probes ia1..ia4 went from 2/4 to 4/4 identical against php -n. After the fix, the real Symfony `--web` request (examples/symfony-app via $R/sf404.php) progresses past `stage:kernel` to a NEW, unrelated blocker: `unsupported ClassConstantFetch expression` in vendor/symfony/http-foundation/Request.php:30, one of several top-level `class_exists(X::class)` opcache-preload hints (AcceptHeader::class, FileBag::class, HeaderBag::class, HeaderUtils::class, InputBag::class, ParameterBag::class, ServerBag::class) used as bare file-scope statements outside any class/function — not yet fixed.
Evidence: cargo test -p elephc-magician --lib interpreter::tests::native_class_return_type_covariance: 4 red before the fix (a_get_iterator_narrowed_to_array_iterator_via_interface_declares_and_runs, a_get_iterator_narrowed_to_array_iterator_across_two_interfaces_declares, a_parent_class_method_narrowed_to_array_iterator_declares_and_runs, an_override_may_widen_a_parameter_type_the_interface_narrowed) then all 11 green after; full lib suite 1647 passed/2 failed (same 2 pre-existing failures as documented baseline, +11 net new passing); php -n $R/gate.php ia1 ia2 ia3 ia4 went 2/4 -> 4/4 identical; revert-sentinel reproduced the original 'class IA1 could not be declared' / 'class IA4 could not be declared' with the hunk stashed, then restored green.
