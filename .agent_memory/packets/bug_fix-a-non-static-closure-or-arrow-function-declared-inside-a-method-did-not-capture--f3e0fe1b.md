# A non-static closure or arrow function declared inside a method did not capture $this at a

> A non static closure or arrow function declared inside a method did not capture $this at all: EvalClosure recorded th…

A non-static closure or arrow function declared inside a method did not capture $this at all: EvalClosure recorded the lexical/late-static class scopes at its declaration site (set_declaring_class_scopes) but had no field for $this, because a closure's own `use (...)` list and an arrow function's inferred implicit capture list both deliberately exclude "this" (PHP's automatic $this binding is not a `use` capture). The fix adds EvalClosure::declaring_this, captured in eval_closure_expr via visible_scope_cell(context, scope, "this") and gated on !is_static (a static closure/arrow must keep refusing $this even when one is available in the enclosing scope). Capturing the value was only half the bug: the dispatch path an ordinary `$f()` variable call actually takes (eval_dynamic_call -> eval_callable -> EvaluatedCallable::Named -> eval_evaluated_callable_with_call_array_args's Named arm in array_dispatch.rs) called eval_closure_with_evaluated_args_and_bound_scope_ref_mode unconditionally, hardcoding this_object: None and folding called_class down to the closure's own lexical scope -- which is also why a closure declared in a parent class method but invoked on a child instance resolved static::class to the parent instead of the child. The Named arm now branches on closure.declaring_this(): when Some, it routes through eval_closure_with_evaluated_args_and_bound_this_scope_ref_mode (which derives the late-static class from the bound object's own runtime class via eval_closure_bound_object_class_name), otherwise it keeps the old scope-only path. eval_closure_with_evaluated_args in closure_execution.rs (execution.rs's Named arm, used by call_user_func-style dispatch) got the equivalent one-line fix: `this_object: closure.declaring_this()` instead of `this_object: None`. Closure::bind/bindTo/->call() were never broken (they already thread an explicit bound_this through the same _bound_this_scope_* helpers). NOT fixed, found during this work: (1) object_dispatch.rs's eval_named_callable_with_call_user_func_values/_args (used by call_user_func($closure)/call_user_func_array) still hardcode bound_scope: None when invoking a Named closure, losing BOTH $this and lexical scope even after this fix -- call_user_func($nonStaticClosureFromAMethod) still loses $this. (2) elephc's refusal of $this outside object context is a generic "Undefined variable $this" warning yielding null, never PHP's dedicated catchable `Error: Using $this when not in object context` -- no "not in object context" string exists anywhere in the interpreter. (3) FakeOps (the interpreter's Rust unit-test double) answers EvalStatus::UnsupportedConstruct for a property read on a null receiver (e.g. `$this->tag` when $this is undefined), where the real runtime warns and yields null -- this blocks testing PHP's undefined-$this-then-property-read shape directly through FakeOps; use `isset($this)` instead of a property read when a Rust unit test needs to observe whether $this got bound.
Evidence: git commit 14ab48a8a7 on reconcile/dirname-symfony; scratchpad/r200/sess_this_*.php probes measured against php -n 8.5.6 and the compiled r200/main eval-bridge binary before and after the fix
Verified by: cargo test -p elephc-magician --lib interpreter::tests::closure_implicit_this_capture (8/8 passed), full lib suite 1661 passed / 2 pre-existing unrelated failures matching baseline names, differential gate against php -n 8.5.6 (8/10 identical; 2 known-unrelated DIFFERS unchanged before/after), revert-sentinel showed the same UnsupportedConstruct panic returning on 5 tests
