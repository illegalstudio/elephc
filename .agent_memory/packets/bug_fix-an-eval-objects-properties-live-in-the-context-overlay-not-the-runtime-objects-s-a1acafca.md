# An eval object's properties live in the context overlay, not the runtime object's slots

> Reading a property through a reflector answered null for every property of a class the interpreter declared, and prod…

Reading a property through a reflector answered null for every property of a class the interpreter declared, and produced the value only on a SECOND read, after some reflected write had happened in between. Ordinary property access read the same property correctly the whole time. The symptom looks like a lookup miss and is not one.

There are two property stores for an object, and reflection was using the wrong one. When the interpreter allocates an eval-declared object it writes every declared default into the context's per-object overlay, and an ordinary read comes straight back out of that overlay. Reflection instead read the runtime object's slots, which for such an object nobody had ever written. The storage NAME was correct the whole time, including the mangling a private property gets; only the store was wrong. That is why the bug survives every variation you would try first: it is independent of visibility, of typing, of inheritance, of whether the reflector is chained off its own construction or held in a variable, of whether the object argument is built inline, and of the echo shape. Nine such shapes were measured and all nine failed identically.

The write half made it worse in a way that explains the second-read behaviour. It wrote the VALUE to the runtime slots while marking the property initialized in the overlay, so after one reflected write the slot finally held something and the next reflected read found it — while ordinary access still saw the old default, and an ordinary write stayed invisible to reflection. Two views disagreeing in both directions.

The fix is to route every reflected read and write through one pair of helpers that resolve exactly the way the ordinary path resolves: a by-reference alias first, then the overlay, then the runtime slot. The slot fallback is not dead code and the slot write is kept, because an eval-declared class can extend an AOT class whose properties genuinely do live in real slots. The overlay owns its cells, so a value is retained before being stored and any distinct replaced cell released, matching an ordinary assignment. Routing the declared, raw-value and dynamic-property paths through the same two helpers is the part that stops them drifting apart again; before, each of the six call sites had its own copy of the store choice.

The methodological lesson is the larger one. The brief handed to this work asserted that a particular suite fixture PASSED and that the bug was therefore some subtle discriminator between it and a minimal repro. That assertion was false: the fixture was already red, at the working base and at the parent commit, with a byte-identical diff. Hours can be spent hunting a discriminator that does not exist. Run the test that is claimed to pass before you believe it, and when a chain of hypotheses all fail to explain a difference, suspect the premise rather than inventing a subtler mechanism. The instrumented print that settled it took one build: it showed the registry HIT every time, which killed the handed-down hypothesis outright, and then showed the slot reporting itself uninitialized under the correct mangled name, which named the real one.

A second methodological point: the failing-name sets must be compared at the SAME tree, not against an assumption. Doing that here showed the change turned two reds green and introduced none, and it also showed that four remaining reds in the same file predate the work. One of those four fails by erroring out of execution rather than by a value mismatch, which marks it as a different mechanism worth its own investigation: the raw-value APIs reject a dynamic property because the target resolution insists the property be declared.
Evidence: Oracle is php -n 8.5.6. A one-class fragment declaring a public property with a string default and reading it through a reflector prints that string; the interpreter printed nothing. Reading the default, writing through reflection, reading that back ordinarily, then writing ordinarily and reading back through reflection prints s;w;w;z; where the interpreter disagreed at three of the four steps. A private typed default reads back its number and reports itself initialized; an inherited protected property read through a child instance returns the parent's default; the raw-value pair round-trips. Instrumentation proved the mechanism twice over: the reflector identity registry HIT on every call, ruling out the handed-down hypothesis, and the slot read then reported initialized=false under the correct mangled private name on the first call and true on the second. Filters compared at the same tree: builtins_class_metadata 90 passed 6 failed before, 92 passed 4 failed after, the two turning green being the property get/set fixture and the set-accessible no-op; classes:: 80 passed 1 failed unchanged; static_members 34 passed 2 failed unchanged; builtins_reflection_functions 12 passed 0 failed unchanged. The claim that the get/set fixture passed was checked against the parent commit and against the branch base and was false at both, with an identical failure diff.
