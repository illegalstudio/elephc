# The eval parser had an array append as a statement only, never as an expression

> In the eval parser, parse postfix in crates/elephc magician/src/parser/expressions/postfix.rs deliberately BREAKS out…

In the eval parser, parse_postfix in crates/elephc-magician/src/parser/expressions/postfix.rs deliberately BREAKS out of its loop when it sees an empty bracket pair, so the statement parser can claim a whole-statement append and build one of the eight dedicated EvalStmt append variants. The consequence nobody had written down is that an append existed ONLY as a statement: every position where PHP wants a value from it had no rule at all and stopped at the bracket with ExpectedSemicolon. That covers return position (return this->before[] = new X), the chain (dirs[] = paths[] = d), the parenthesised form, and an append used as a call argument. The diagnostic names a bracket the parser has no rule for, which reads like an index or array-literal bug and is neither.

The fix is a rule, not a repair: EvalExpr::ArrayAppendAssign, built in parse_assignment when parse_ternary stopped in front of a bracket pair followed by an equals sign. In PHP an append is an ordinary assignment expression whose value is the ASSIGNED value, which is exactly what makes a chain work: the inner append must evaluate to the value, not to the array and not to the new length, or the outer append stores the wrong thing. So a chain is the assertion worth writing; a single append proves much less.

Two rules learned about not breaking what already worked. FIRST: fold-then-unfold. Once the expression parser recognises the append, a whole-statement property append arrives at parse_property_like_stmt_tail already folded into one expression, and the tail never sees the bracket it used to consume. Left alone, that silently rerouted every statement append away from the dedicated PropertyArrayAppend and its dynamic and static siblings, which turned four existing parser expectations red. Those statements run through the property-aware eval_property_get_result / eval_property_set_result pair, so the tail now unfolds ArrayAppendAssign back into the dedicated statement and falls back to the expression only for a target with no dedicated statement. SECOND: decline the reference spelling. a[] = &b BINDS rather than assigns, so the append rule refuses when an ampersand follows the equals sign; accepting it into this node would silently copy. php accepts the syntax, so that is a pinned gap, not a rule.

Ownership: eval_array_append was split so the statement and the expression share one implementation. eval_array_append_result does the work and returns the assigned cell; eval_array_append drops it. The returned handle ALIASES the array's element exactly as EvalExpr::Assign returns the cell it stored, so the new variant belongs in eval_expr_result_aliases_storage alongside Assign, CompoundAssign and NullCoalesceAssign, and nothing releases it twice.

Side effect that is the same construct rather than a second one: this-rows-key-bracket-append (an append through an array ELEMENT of a property) used to be refused outright, because property_array_append_stmt rejects a non-property target and no other statement claimed it. It is Symfony's EventDispatcher::addListener and DebugClassLoader's static-method-table append.
Evidence: php -n 8.5.6 prints first;second;2;second / 1;1;/res;/res / 7;7;1 / same;4 / r1;1;3;3;1 / a;b;a,b on the six fragments, and elephc now prints the same. Sentinels: disabling the parse rule fails all six interpreter tests and three of the four parser tests; returning null instead of the assigned value fails exactly the six interpreter tests while the appends still land.
