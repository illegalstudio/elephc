# A literal string callback to a builtin was not a reference to that function, so `uksort($a, 'strnatcmp')` pulled in neither its prelude nor a diagnostic — it segfaulted

> THREE FIXES that only work together, all reached from one line of Symfony: uksort $paths, 'strnatcmp' in GlobResource…

THREE FIXES that only work together, all reached from one line of Symfony: `uksort($paths, 'strnatcmp')` in `GlobResource::getIterator()`.

1. `ast_usage::collect` recorded a literal string callable only for `function_exists`, `is_callable`, `call_user_func` and `call_user_func_array`. Every OTHER callback-taking builtin names its callback parameters in the shared contract catalog (`BuiltinContract::callback_parameter_names`), so the scan now reads the positions from there. Without it `uksort($paths, 'strnatcmp')` was not a reference to `strnatcmp` at all, and any prelude that implements it was never injected.

2. `strnatcmp()`/`strnatcasecmp()` did not exist. They are now BUILT (never parsed) in `src/strnatcmp_prelude.rs` and injected on reference. The backend has no natural-order comparator to expose — `natsort`/`natcasesort` are emitted as a tail-jump to the ascending INTEGER sort — so a PHP-level transcription is what gives the compiled and the interpreted side the same answer at no new runtime symbol.

   THE ALGORITHM IS php-src's `string_natural_compare_func`, not "natural order in spirit". Differential testing over 36 pairs against `php -n` 8.5.10 caught three places where the obvious reading is wrong: leading zeros are skipped only at the very START of each string (`leading` is cleared after the first iteration), so `strnatcmp('a02','a2')` is -1 and not 0; a digit run where EITHER side starts with `'0'` is "fractional" and compares LEFT-aligned (first difference wins) while every other run compares RIGHT-aligned (longest run wins, a difference is only a bias); and whitespace is skipped before EVERY comparison, which is what makes `strnatcmp('pic 5','pic05')` compare `'5'` against `'0'` and answer 1.

3. A builtin callback is invoked by the ENGINE, under PHP's COERCIVE parameter binding — the callback checks already run inside `with_internal_callback_binding`, which drops the caller's `strict_types` for exactly that reason — but they then called `check_known_callable_call`, which passes `coercive: false`. The synthesized argument types are the container's element or KEY types, and an array key is `int|string` at runtime however the array was inferred, so a comparator declared `strnatcmp(string, string)` has to accept the `Int` key an indexed array reports. `check_engine_invoked_callback_call` is that call with coercive binding on.

WHAT AN UNRESOLVED STRING CALLABLE DOES TODAY, still open: `usort` reports `usort callback string does not name a supported callable`, and `uksort` SEGFAULTS — it jumps through the unresolved descriptor with no guard. Worth a guard of its own.
Evidence: scratchpad/red20: a.php (uksort + string callable) went from SIGSEGV to PHP's answer; b.php (closure calling strnatcmp) from `Call to undefined function strnatcmp()`; c.php (usort + string callable) from `does not name a supported callable`. d.php diffs 36 strnatcmp/strnatcasecmp pairs against `php -n` 8.5.10 and is byte-identical. The coercive-callback change moved no test: error_tests 1363/97 and codegen_tests `sort` 133/16 both before and after.
Verified by: scratchpad/red20 differential against php -n 8.5.10; error_tests and codegen_tests sort slices against their own baselines.
