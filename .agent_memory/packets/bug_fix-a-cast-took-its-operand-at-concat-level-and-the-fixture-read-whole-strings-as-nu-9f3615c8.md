# A cast took its operand at concat level, and the fixture read whole strings as numbers

> Two independent defects that compounded into one silent wrong value, which is worse than any refusal: a refusal stops…

Two independent defects that compounded into one silent wrong value, which is worse than any refusal: a refusal stops the program and names a token, a wrong number reaches the page.

PRECEDENCE, an interpreter defect. parse_unary in parser/expressions/precedence.rs took a cast's operand with parse_concat, so the cast swallowed the whole concatenation chain and every additive term inside it. A cast is a UNARY operator in PHP and binds exactly as tightly as logical not, unary minus and the error-suppression operator, so its operand is another unary expression. The one direction unary does not win is the power operator, and parsing the operand with parse_unary preserves that automatically because parse_unary reaches parse_power on the way down: an int cast of the string 2.9 raised to 2 is 8 in php and in elephc, the power first and the cast truncating. A fix that dropped the operand to the primary level would give 4, so that case is worth pinning.

The parser test parse_fragment_accepts_scalar_cast_source PINNED the wrong shape under a docblock claiming PHP cast precedence. That is the worst place for a defect to live, because a reader auditing the tests concludes the behaviour is already right. When a docblock states a language rule, check the assertion against the language rather than trusting the sentence.

THE NUMERIC PREFIX, a FAKE-RUNTIME defect. The fixture's fake_numeric in interpreter/tests/support/conversions.rs parsed the WHOLE string with a float parse and fell back to zero, so an int cast of 34x answered 0 where php answers 34, and that reached every numeric use of a string rather than only casts. The compiled backend already answers php's way: tests/ir_backend_smoke_test.rs pins intval of 42xyz at 42 through the real runtime. Checking the real side before changing the fake is what tells you which layer to fix.

The two compounded exactly: the cast took the concatenated string and the fixture then made 0 of it, so fixing either alone still prints a wrong answer. Sentinels have to be run separately to show that, and neither sentinel fails the other's tests.

PHP's string-to-number rule, each part measured with php -n 8.5.6: leading whitespace skipped and trailing tolerated; sign, digits, optional fraction, optional exponent; anything not starting with a number is 0, hex notation NOT recognised; empty string 0; a float cast keeps the fraction.
Evidence: php -n 8.5.6 prints 34x;1x;12x, 35;5;-3, no, 8, 34;0;12;12;0;1000;0 and 3.5 on the six fragments and elephc now prints the same. Sentinels: taking the operand with parse_concat again fails the concatenation value test and the shape test; parsing the whole string again fails the three numeric-prefix tests; neither fails the other's tests.
Verified by: cargo test -p elephc-magician --lib with no skips: 1405 passed, 0 failed, 0 filtered (commit f368f634c3)
