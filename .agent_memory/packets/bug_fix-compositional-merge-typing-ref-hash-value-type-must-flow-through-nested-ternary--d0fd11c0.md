# Compositional merge typing: ref-hash value type must flow through nested ternary/??/match merges

> Conditional value merge typing for ref bearing array literals is COMPOSITIONAL, not syntactic. The mechanism in src/i…

Conditional-value merge typing for ref-bearing array literals is COMPOSITIONAL, not syntactic. The mechanism in src/ir_lower/expr/mod.rs: (1) `is_depacked_ref_hash_merge_type()` recognizes the marker VALUE type AssocArray{Mixed,Mixed} regardless of provenance (direct `ref_literal_desugar_yield_type` or an inner merge temp); (2) `materialized_expr_type_for_merge` has arms for ExprKind::NullCoalesce (`null_coalesce_merge_type_estimate`, mirroring the coalesce lowering's own result typing incl. the ArrayAccess-value isset form) and ExprKind::Match (`match_merge_result_type`), so nested `??`/match operands surface their already-computed merge value type instead of falling to the syntactic Mixed fallback; (3) `branch_merge_result_type` and `lower_match` gate their "trust the materialized branch types" path on the marker VALUE type, not on the desugar AST shape. Rationale: any merge that re-derives a syntactic fallback from the AST shape Mixed-boxes the de-packed hash on one path and tag-11 reference-bucket reads then print empty ($a ?? $b ?? ['s'=>&$v] read EMPTY before this). When adding a new conditional-value construct with a merge temp, type it through materialized_expr_type_for_merge and add its ExprKind arm there, or chained/nested composition with ref literals silently breaks.
