# A destructuring pattern is not an array literal and cannot be recovered from one

> The eval parser modelled a PHP list destructuring pattern as a list of optional variable NAMES, and in expression pos…

The eval parser modelled a PHP list-destructuring pattern as a list of optional variable NAMES, and in expression position it RECOVERED that list from an already-parsed array literal. A pattern differs from a literal in four ways and the model could express only the first. It may carry a HOLE where PHP allows a bare comma, and a literal cannot hold one at all, which is why the expression position had to stop converting and parse the pattern outright. Its slots are LVALUES, not variables: a property, an array element, a static property. It may name a KEY. And it NESTS. Fixing this is one type change plus one shared parse function used by the statement, expression and foreach positions, so those three cannot drift apart again.

A NON-ARRAY right-hand side is NOT fatal, and this was load-bearing rather than cosmetic. php gives every slot null and takes the right-hand side as the expression's value, warning only for a non-null scalar. The EXPRESSION path already did that while the STATEMENT path refused outright, and real code depends on the lenient behaviour: Symfony's LazyDecoratorTrait writes a destructuring assignment against a null-coalesced lookup precisely so the null case is reachable as a falsy condition. Two paths for one construct is where that kind of divergence hides.

The legacy list-parenthesis spelling is the SAME pattern between different delimiters. Parsing it as a function call is why it died on the equals sign; parameterising the pattern parser by its delimiters covers it, nested spellings included.

FOREACH binds its key and value to NAMES, so every other target shape must be bound to a hidden name and copied into place by a statement prepended to the loop body. A bracket pattern already worked that way; extending the same helper to any lvalue is what makes a property as the foreach KEY work without a special case per shape.

TEST DESIGN worth repeating: put the hole in the MIDDLE. A pattern that dropped holes instead of counting them still passes a leading-hole test, because dropping and skipping agree there.
Evidence: php -n 8.5.6 prints 12;ab;stat, w;pr, 12;123, acc;no, 12;a1 and 12 on the six fragments and elephc now prints the same. Sentinels: restricting slots to variables fails exactly the lvalue test; making a non-array right-hand side fatal again fails the condition test and one existing control-flow test; disabling the legacy spelling fails exactly its own test. Symfony measurement: 5 refused files become 3, PhpDumper.php and LazyDecoratorTrait.php parse in full, and the reducer corpus goes from 19 refusals of 37 to 14 with g10 through g14 all accepting.
Verified by: cargo test -p elephc-magician --lib with no skips: 1417 passed, 0 failed, 0 filtered (commit 0c74947f21)
