# serialize()/unserialize()/error_log() now run through the eval interpreter (crates/elephc-

> serialize /unserialize /error log now run through the eval interpreter crates/elephc magician/src/interpreter/builtin…

serialize()/unserialize()/error_log() now run through the eval interpreter (crates/elephc-magician/src/interpreter/builtins/core/{serialize,unserialize,error_log}.rs). Three reusable mechanisms worth knowing for any future builtin that touches declared-object properties or a raw I/O channel: (1) An eval-declared object's private/protected property values do NOT live in the runtime object's raw slot by default -- eval_dynamic_class_allocate_object() (crates/elephc-magician/src/interpreter/statements/class_resolution.rs, widened here from pub(super) to pub(in crate::interpreter) so builtins/core could reuse it) writes every declared property into the context-level dynamic-property overlay (context.set_dynamic_property_value, keyed by a "storage name" from eval_instance_property_storage_name: "\0DeclaringClass\0prop" for private, plain "prop" for protected/public) and mirrors ONLY public ones into the raw slot -- protected is deliberately left unmirrored because its storage name is unmangled and indistinguishable from public to a raw-slot walker like json_encode's object branch. unserialize()'s object hydration writes each payload property through this exact same combo (storage-name lookup via context.class_property(), conditional slot mirror, always-overlay via eval_store_dynamic_property_value, then context.mark_dynamic_property_initialized) rather than the generic RuntimeValueOps::property_set(plain_name), because property_set alone would create a dynamic public property beside a still-default private one -- this was verified as the FIRST test in builtins_unserialize.rs (unserialize_binds_an_unmangled_key_to_the_declared_private_slot), using a method DEFINED ON the fixture class to read $this->a/$this->b, since only a method on the class can legitimately read a private/protected value to prove which slot actually got written. (2) eval_debug_object_properties()/eval_debug_object_class_name() (crates/elephc-magician/src/interpreter/builtins/core/print_r.rs, already pub(in crate::interpreter)) are the SAME visibility-aware property-enumeration machinery print_r()/var_dump() use; serialize() reuses them directly instead of re-deriving visibility, and the property.visibility.kind enum (Public/Protected/Private(declaring_class)) maps 1:1 onto php's own NUL-mangling rule for the wire format. (3) A builtin needing a genuinely new I/O channel (error_log's fd-2 write) does not need a new FFI symbol or a runtime_hooks/ops.rs edit if the channel doesn't need to coordinate with the compiled runtime's own buffered state (echo's ob_start() stack does, error_log's stderr write does not) -- adding a RuntimeValueOps trait method WITH A DEFAULT BODY (plain std::io::stderr()) is correct for the production ElephcRuntimeOps for free, since fd 2 is a raw OS descriptor shared by the whole process regardless of which half of the hybrid binary writes to it; only the FakeOps test fixture needs an override, to capture bytes for assertions instead of writing real stderr. Also discovered and used: PHP's shortest-round-trip float formatting (serialize_precision=-1) coincidentally matches Rust's plain f64::to_string() bit-for-bit for every case measured (1.0->"1", 1.5->"1.5", 1/3->"0.3333333333333333" -- 16 threes in both) via a standalone rustc check, so serialize()'s float branch reuses the SAME values.string_bytes(float_cell) conversion json_encode() already reuses, only correcting the NAN/INF/-INF spelling on top -- but this was verified only through FakeOps's own to_string()-based fixture, not the production runtime's string_bytes, so whether the production float-to-string conversion also matches serialize_precision=-1 (vs. precision=14) is UNVERIFIED beyond the fake harness.
Verified by: cargo test -p elephc-magician --lib builtins_serialize/builtins_unserialize/builtins_error_log (30/30 green) and cargo test -p elephc-builtin-contract --lib (16/16 green); every php output re-measured with php -n 8.5.6; revert-sentinel confirmed the original refusal for all three functions
