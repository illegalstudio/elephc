# The interpreter's parser accepted only a bare variable as a by-reference source, and its refusal named neither file, line nor token

> Commit b5b322b264 30 files, +1008/ 103 . Two mechanisms, both generic PHP semantics, found while the Symfony web requ…

Commit b5b322b264 (30 files, +1008/-103). Two mechanisms, both generic PHP semantics, found while the Symfony web request died 116 s into the cold container build with the six-word message "Parse error: eval() fragment is invalid".

MECHANISM 1 — the grammar. The eval trace environment variable named the fragment in one line: vendor/symfony/cache/Adapter/TagAwareAdapter.php line 290, inside withSubNamespace(), the statement that binds a local by reference to the knownTagVersions property of this. The interpreter's parser — the one every eval() and every file included at run time goes through — accepted ONLY a plain variable after the by-reference assignment operator. Measured against php -n 8.5.6 through a runtime-include probe, of nine reference sources PHP accepts exactly ONE parsed: a plain variable accepted; a property of an object, a property of this, an array element, a static property, an indexed property, an indexed property of this, a string-keyed element and a call result were all refused. parse_var_store_stmt required the dollar-identifier token kind and returned ExpectedVariable, which surfaced at the caller as ExpectedSemicolon; the EvalIR statement it built, ReferenceAssign, carries a String target and a String source and is therefore variable-to-variable by construction. Four sibling sites (static-property, dynamic-static-property and property targets) carried the same String-source restriction. Only the array-element target already parsed a general source expression.

NOTHING NEW WAS NEEDED to honour a general source. eval_reference_source, through eval_call_arg_value, already resolves an EvalReferenceTarget for every storage shape PHP can alias — variable, array element, nested array element, object property, dynamic property, static property and their dynamic-name forms — because that is how a by-reference ARGUMENT is bound; and a foreach with a by-reference value already binds a scope name to one with rebind_reference plus set_reference_target. The parser simply could not reach it. The fix adds parse_reference_source_expr, which parses the source with the ordinary expression parser and then validates that the result names storage; the EvalIR statement VarReferenceBind, carrying a String target and an EvalExpr source; and eval_var_reference_bind, which binds the variable as a Borrowed view of the source's current cell plus the reference target that later writes travel back through — the same ownership bind_method_scope_args uses for a by-reference parameter resolved from the same helper. The four property and static-property targets reach the general source by desugaring to a hidden NUL-prefixed binding first, which is exactly what their executors want, since each resolves its source through scope.reference_target().

DO NOT collapse the plain variable-to-variable case onto the general path. It is a different PHP semantic, not a duplicate code path, and the measurement that decides it is: set a to 1, bind b by reference to a, set a to 2, echo b — php prints 2. Variable-to-variable aliasing is SYMMETRIC and permanent, which the scope's named-alias table (scope.set_reference) models; a one-way EvalReferenceTarget write-back would silently break it, because a StoreVar on the first name knows nothing about the second. A source that names no storage, such as a call result, is now reported as EvalParseError::UnsupportedConstruct rather than as a parse error: php accepts it (a by-reference return aliases, anything else warns and assigns by value), the interpreter can do neither, and a binding that silently degraded to a by-value assignment would be worse than a refusal that says so.

MECHANISM 2 — the refusal named nothing. The parse-error message was a constant in generated assembly, so it could never carry a file, a line or a token; the parser knew all three at the moment it gave up (the eval trace was already printing them) and threw them away. EvalParseDiagnostic now carries the failure with its fragment line and PHP's own description of the failing token; parse_fragment and parse_fragment_cached return it, and the two sides that own a call site render it byte for byte as php -n 8.5.6 does, on STANDARD OUTPUT with exit status 255. For an included file the shape is a leading newline, then the words Parse error, then the reason clause naming the unexpected token, then the file and the line. For an eval fragment php names the file and line of the eval CALL in parentheses, then a colon, then the phrase eval()'d code and the line inside the fragment. Standard output plus 255 is NOT a new convention: runtime/exceptions/uncaught_report.rs already writes its fatal report to file descriptor 1 with an uncaught exit status of 255 and a comment saying PHP writes this report to stdout, not stderr, measured. The eval bridge's three fatals were the outlier on file descriptor 2 with exit 1, and only the parse path was moved; the unsupported-construct and runtime-fatal messages remain on file descriptor 2 with exit 1, which is a recorded inconsistency.

Token descriptions are measured, not invented: identifier, variable, integer, floating-point number, and a generic form for operators. PHP names a RESERVED word with the generic form and a non-reserved one as an identifier — true and null are identifiers, return and else are not. End of file has its own wording. PHP's optional expecting clause is deliberately omitted: it comes from php's LALR item set, a recursive-descent parser has none, and emitting a DIFFERENT set is worse than emitting none.

Two details the diagnostic needs to be right rather than merely present. First, parsing runs on the bytes after the open tag, so a fragment line equals the file line only for the block that opens the file; eval_include_line_offset adds the preceding newlines back, which is what makes a template with leading inline HTML report php's line. Second, a recursive-descent rule can consume the whole right-hand side before discovering the target is not assignable, so Parser::fail and fail_at stamp the token php names — assigning to an integer literal reports the operator like php, not end of file from wherever the cursor stopped. The parser never backtracks, so exactly one error is created per fragment and the stamp is unambiguous.

STILL OPEN, measured: PHP 8 makes a parse error a CATCHABLE ParseError for BOTH eval() and include — a try/catch around either continues and the program exits 0 — where elephc kills the process; the printed text is only php's uncaught-throwable rendering. And php parses an included file whole before executing any of it, so a syntax error suppresses that file's leading inline HTML, which elephc has already echoed.
