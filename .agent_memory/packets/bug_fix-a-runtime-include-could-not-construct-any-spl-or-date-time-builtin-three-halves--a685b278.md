# A runtime include could not construct any SPL or date/time builtin: three halves were missing, and the constructor half failed because a runtime include is not an eval OP

> Constructing a builtin class from PHP text that arrives at RUN TIME an include / require whose path is not a literal,…

Constructing a builtin class from PHP text that arrives at RUN TIME (an `include`/`require` whose path is not a literal, executed by the magician through the eval bridge) needs THREE halves, and each missing one fails at a different depth. Measured on 2a67991fda with php -n 8.5.6 as the oracle.

HALF 1, the checker gate. `program_may_reference_spl` (src/types/checker/builtin_spl_classes/registry.rs) and `program_may_reference_datetime` (src/types/checker/builtin_types/datetime/gate.rs) read `usage.introspects` but not `usage.includes_runtime_php`, so the family was never registered. Symptom: `Fatal error: eval() runtime failed: could not construct class "ArrayObject"`, which comes from `values.new_object()` failing in crates/elephc-magician/src/interpreter/expressions/evaluation.rs:237 — the ALLOCATION failing.

HALF 2, the allocation table, needs NO new seed. Opening the gate alone was enough for `_classes_by_name`: with the gates open the message changed to a bare `Fatal error: eval() runtime failed` and `ELEPHC_EVAL_TRACE=1` reported `phase=native_constructor stage=signature class="DateTimeImmutable" details=Some((2, 2, 0, true))` then `phase=native_constructor_error stage=construct`. Signature known and bridge-supported; body absent. This corrects the older comments in both gate files, which said the eval bridge had no allocation metadata for these families — it does, via `runtime_referenced_class_names`, once the class is registered.

HALF 3, the constructor BODY in EIR, is what was really missing, and the reason is the same for both families: A RUNTIME INCLUDE IS NOT AN EVAL OP. It lowers to `Op::RuntimeCall(RuntimeCallTarget::DynamicInclude)`, not to any `Op::Eval*` and not to the `eval` language construct. The date/time family already had a forcing pass, `lower_eval_date_alias_methods_if_needed` (src/ir_lower/builtin_datetime.rs), but it was guarded by `eval_fragments_may_reach_dates`, which SCANS FOR EVAL OPS and therefore answered false. SPL had no forcing pass at all: `referenced_builtin_spl_methods` is purely reference-driven and there is no instruction to find, because the `new ArrayObject` lives in text that does not exist at compile time.

THE AUTHORITY TO READ IS `module.required_runtime_features.eval_bridge`, not a re-derived scan. `lowered_runtime_features` (src/ir_lower/program/runtime_features.rs) already sets it for every route into the interpreter: a bridge-requiring `eval`, `extract`, `spl_autoload_register`, and `RuntimeCall(DynamicInclude)`. Both passes now read it. The fix is: widen the two checker gates for `includes_runtime_php`, widen the date/time guard to the bridge flag, and add `push_eval_bridge_builtin_spl_methods` in src/ir_lower/program/spl_discovery.rs forcing exactly what the existing `new $c` (`Op::DynamicObjectNewMixed`) arm forces — the constructor plus `push_builtin_spl_metadata_methods`, the interface/vtable methods a constructed object needs even when nothing calls them by name.

WHY SPL IS THE ONE THAT MATTERS. A read-only audit of examples/symfony-app/vendor counted `new <Class>` per builtin class name: 12 of the 15 names reached are SPL, accounting for 66 of 95 instantiations. SplObjectStorage 16, DateTimeImmutable 15, RecursiveIteratorIterator 13, RecursiveDirectoryIterator 12, ArrayIterator 9. Vendor code arrives through the Composer autoloader, which is a non-literal include, so this is the route that decides whether autoloaded code can allocate at all.

THE BOUNDARY THAT REMAINS, and it is deliberate. The forced set is `is_dynamic_new_mixed_metadata_candidate` filtered by `is_supported_builtin_spl_method` (src/ir_lower/program/spl_support.rs), the same pair `new $c` uses. A class with no arm in that table cannot be forced because the on-demand SPL lowering has no body it is allowed to produce. SplObjectStorage is the notable casualty and is the single most instantiated builtin in the vendor tree; it constructs fine in AOT and through `new $c` (measured, prints `1;SplObjectStorage;done`) but from a runtime include it still reports `stage=construct`. Nesting is also still open: `new IteratorIterator(new ArrayIterator([7,8]))` inside an include printed the inner iteration and then died.

COST, measured on the reducer `<?php $p = __DIR__ . "/inc.php"; include $p;`: assembly 5,670,173 bytes at base, 11,447,081 with the gates alone, 20,321,847 with the forcing passes (3.58x); binary 5,654,536 to 7,811,624 (+2,157,088, +38.1%); class-name symbols 54 to 112. A program with no runtime include pays NOTHING: three no-include controls, including one naming ArrayObject, SplFixedArray, DateTimeImmutable and DateInterval directly, emitted byte-identical assembly (147,248 / 1,185,077 / 3,990,355 bytes) before and after, with identical sorted stderr.

Fiber and php_user_filter are the two remaining families whose gates read `introspects` but not `includes_runtime_php`. Measured and NOT widened: a runtime-included `new Fiber(function(){...})` still reports `could not construct class "Fiber"` — it fails at ALLOCATION, so it needs the gate opened before anything else can be judged.
Evidence: php -n 8.5.6 as the oracle on five reducers. Before: `include $p` of a file doing `new ArrayObject([1,2,3])` + `new SplFixedArray(2)` printed `Fatal error: eval() runtime failed: could not construct class "ArrayObject"` and exited 1 where php printed `3;a;done`; the DateTimeImmutable + DateInterval twin printed the same class of fatal where php printed `2020-01-02;2020-01-03;done`. After: both print exactly php's output and exit 0. ELEPHC_EVAL_TRACE=1 pinned the intermediate state (gates open, forcing absent) at `phase=native_constructor_error stage=construct`. Identity gate: three no-include control programs emitted byte-identical .s before and after (cmp clean) with identical sorted stderr. Test-set diff by NAME on the `include_` filter of codegen_tests, both runs on this same base: base 105 passed / 11 failed, with-fix 108 passed / 8 failed, the 8 being exactly the pre-existing subset of the 11 — zero new reds, three red-to-green. tests/error_tests spl_builtins, named by kage_risk as an uncovered co-change partner, was run on BOTH trees and gave an identical 38 passed / 4 failed with the same four names, so those four are pre-existing and not caused by this change.
Verified by: cargo test -j 2 --test codegen_tests include_ run on the reverted tree and on the fixed tree and compared by name; cargo test -j 2 --test error_tests spl_builtins run on both trees; five php -n 8.5.6 reducers; cmp of three control .s files; ELEPHC_EVAL_TRACE=1 traces
