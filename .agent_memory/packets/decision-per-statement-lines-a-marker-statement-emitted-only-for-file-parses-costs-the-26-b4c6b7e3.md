# Per-statement lines: a marker statement emitted only for FILE parses costs the 262 fragment expectations nothing

> An included file reported ONE position for all of it the line the include began on because entering the file called s…

An included file reported ONE position for all of it -- the line the include began on -- because entering the file called `set_call_site(file, dir, 1)` and nothing moved `call_line` again. Every reader of that position was wrong for the whole file: `debug_backtrace()` frames, a diagnostic's `on line N`, and the `FILE(LINE) : eval()'d code` spelling.

CRITICAL NON-CAUSE: `__LINE__` was already correct and is not part of this. The LEXER stamps the line into the token (`magic_const_token` in lexer/scan.rs builds `EvalMagicConst::Line(line)`) and `parse_source_file` keeps file-relative lines. A fix aimed at `__LINE__` would have changed nothing while looking plausible. Assert `__LINE__` beside the context-position readers so a test cannot pass on the half that already worked.

DESIGN THAT KEPT THE CHANGE SMALL. `EvalStmt` has ~58 variants and the parser tests contain 262 statement-shape assertions written against `parse_fragment`. Adding a `line` field to every variant, or wrapping statements, would break all 262 and bury the fix. Instead: one new variant `EvalStmt::SourceLine(i64)`, emitted by `Parser::parse_stmt` -- which is the SINGLE funnel every statement passes through (top level, loop/branch bodies, function/method/closure bodies), so one marker site reaches every statement list the interpreter walks, including inside declarations -- and gated on a `track_source_lines` flag that ONLY `parse_source_file` sets. Result: the 262 fragment expectations are untouched and exactly the four `parse_source_file` shape tests changed. The gate is principled, not a dodge: a fragment is a piece of a file whose position its caller already knows, and `__LINE__` is lexer-stamped either way.

Emit the marker only when the line MOVES, or a `for` written on one line emits one per clause.

Adding an `EvalStmt` variant breaks exactly two exhaustive matches, both outside the interpreter: `visit_static_var_declarations` in interpreter/dynamic_functions/closure_execution.rs and `eval_stmt_uses_this_property` in parser/statements/property_hook_analysis.rs.

A function body must RESTORE the caller's line when it returns (beside the `returns_by_ref` and `strict_types` saves already at those four sites), or a diagnostic raised later in the calling statement names wherever the callee stopped.

TWO SUPPRESSIONS THIS UNLOCKED, both of which had docblocks explaining themselves and both of which were correct until now:
- `note_eval_runtime_failure` (interpreter/throwables.rs) did `let line = (!context.executing_include()).then_some(line);` -- dropping the line whenever an include ran, because naming the top of a file for a failure forty lines down is worse than naming nothing. `EvalRuntimeFailure::clause`'s docblock even said "Giving EvalIR statements a line is what would close the rest."
- a nested `eval()` inside an included file kept the include's `__FILE__` override, so `eval_file_magic()` returned the include's plain path instead of `FILE(LINE) : eval()'d code`. `eval_nested_eval` must clear the override for the eval and restore it after.

Both are the general pattern: when a capability lands, grep for the docblocks that say "we cannot do this because X" and check whether X still holds.

STILL OPEN (reflection side, not this): `ReflectionClass::getFileName()` on an eval-declared class returns the AOT script path because `eval_reflection_aot_class_source_metadata` (interpreter/reflection/class_api.rs) reads `values.reflection_source_file()` rather than the class's recorded declaration file. The recorded string is now correct, so that fix gets the right number for free.
Evidence: Two tests in crates/elephc-magician/src/interpreter/tests/include_line_tracking.rs measured against php -n 8.5.6: `L:2;L:3;inL:5;bt0:11;bt1:13;clL:15;e:inc.php(19) : eval()'d code;after;` and, for a function declared in one included file and called from another, `f0:caller.php;l0:5;`. Sentinels: markers parsed but not applied fails both; the nested-eval override left in place fails exactly the one reading the eval spelling. The blast radius was measured, not assumed: only the four parse_source_file shape tests went red, and all 262 fragment assertions stayed green.
Verified by: cargo test -p elephc-magician --lib &lt; /dev/null -- 1484 passed, 0 failed, 0 filtered; cargo check --workspace --all-targets clean. Commit 19e97a85e3.
