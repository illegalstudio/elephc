# An instanceof probe resolved the OWNER's class key in the ASKER's own class table, so every relation about a cross-context eval object answered false

> Commit 99f98db775 échelon 34, branch reconcile/dirname symfony, on top of 4c645c3838 . MECHANISM: an object built ins…

Commit 99f98db775 (échelon 34, branch reconcile/dirname-symfony, on top of 4c645c3838). MECHANISM: an object built inside one eval context carries the class THAT context declared. `ElephcEvalContext::dynamic_object_class` looked the identity up in the OWNER's `dynamic_objects` registry (a `HashMap<u64, String>` keyed by identity, valued by a class-name KEY) and then resolved that key against `self.classes` — the ASKING context's table. The asker has usually never declared a class of that name, so the lookup returned None, `dynamic_object_is_a` answered `Ok(None)` ("no opinion"), and the caller fell through to `values.object_is_a`, i.e. the generated AOT metadata. For an eval-declared class the allocator (`eval_dynamic_class_allocate_object`) hands out a plain `stdClass` when `values.class_exists(name)` is false, so the AOT answer is false for EVERY target — the object's own class included. `get_class()` stayed correct the whole time because `dynamic_object_class_name` already had a SECOND fallback that reads `owner.dynamic_object_class(identity)`; that asymmetry (right class name, all-false relations) is the fingerprint of this bug. FIX: new `ElephcEvalContext::dynamic_object_declaring_class(identity) -> Option<(&Self, &EvalClass)>` returns the class TOGETHER with the context that declared it and asks the OWNER's table with the OWNER's key, ordered owner-last so a context that itself knows the object keeps deciding. Three relation sites now use it: `dynamic_object_is_a` in interpreter/builtins/symbols/is_a.rs (shared by `instanceof`, `is_a()` and `is_subclass_of()` — is_subclass_of.rs only re-enters `eval_builtin_is_a_relation`), plus the two sites that name the class of an OBJECT used as a dynamic `instanceof` target (`eval_instanceof_object_target_name` in interpreter/expressions/evaluation.rs and `execute_context_object_is_a_dynamic` in interpreter/mod.rs). The two object-target sites are load-bearing and were proved separately: with only the is_a change, `$v instanceof $evalObject` still answered `op` where php says `Op`/`oP`. NOT changed on purpose: `dynamic_object_class` itself, which has 31 other callers (method dispatch, property access, destructors) — widening it there is a separate, unmeasured blast radius. TRAP for the next session: the reducer only reproduces WRONG-FALSE answers. Reproducing the shape needs (a) the class file written at RUN time and included through a VARIABLE path (a decl file that exists at compile time gets different treatment), and (b) the asking function to really own an eval context — a literal `eval('$seed = 1;')` alone is NOT enough, the compiler folds it and `has_eval_context()` is then false, so the AOT `instanceof` path is emitted and answers false for a non-AOT target name without ever calling the bridge (that is a DIFFERENT, still-open gap). Forcing the slot took a `new <EvalDeclaredClass>(...)` in the same function. Also new: `ELEPHC_EVAL_TRACE` now prints identity, eval class, runtime class and `decided_by=eval-class|aot-metadata` on every `phase=object_is_a` line; the old line printed only the target and the answer, which is uncheckable because one target is asked about many receivers in a request.
Evidence: Reducer against `php -n` 8.5.6, classes written at run time and included through a variable path, read back from a function owning an eval context. Nine relations x 3 objects. BEFORE (HEAD 4c645c3838, measured by reverting the fix and rebuilding the magician): EvalOwnerArg:aicbrNop EvalOwnerRef:aicbrNop EvalOwnerChild:aicbrNop. AFTER: EvalOwnerArg:AIcbrNOpJk EvalOwnerRef:aicbRnoPjk EvalOwnerChild:aiCBrNopjK, identical to php -n. Symfony's ServiceLocatorTagPass::register() loop reduced to its decisions moved from sra=wrapped:0;sRa=wrapped:b;sRa=wrapped:k (an already-wrapped argument wrapped twice, a reference key stringified) to php's SrA=kept;sRa=wrapped:1;sRa=wrapped:k. Filter counts, all at their 4c645c3838 baselines with no new red: is_a 50/0, eval_bridge 13/0 (11 baseline + 2 new tests), destructors 44/0, references 62/2, runtime_gc 256/35, objects:: 305/17, reflection 191/158, instanceof 60/1 — the single instanceof red is test_instanceof_self_parent_and_late_static ("instanceof static" answers false where php says true), whose compiled program contains zero elephc_eval symbols (nm), so it predates and is untouched by this change.
Verified by: cargo test --test codegen_tests with filters is_a / eval_bridge / destructors / references / runtime_gc / objects:: / reflection / instanceof, plus two new tests test_eval_bridge_instanceof_answers_from_the_declaring_context and test_eval_bridge_instanceof_guards_the_service_locator_wrapping_loop; both fail at HEAD with the fix reverted and pass with it
