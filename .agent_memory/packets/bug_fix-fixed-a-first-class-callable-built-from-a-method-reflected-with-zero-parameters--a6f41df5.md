# FIXED: a first-class callable built from a METHOD reflected with ZERO parameters, and the parameter objects are built at ReflectionFunction CONSTRUCTION, not at getParameters()

> FIXED. new ReflectionFunction $obj ... answered getParameters === for an invokable object, and the same for $obj m ..…

FIXED. `new ReflectionFunction($obj(...))` answered `getParameters() === []` for an invokable object, and the same for `$obj->m(...)`, `Cls::m(...)` and `Closure::fromCallable($obj)`. `new ReflectionMethod($obj, '__invoke')` and `new ReflectionFunction(plain_fn(...))` were always correct, which is what made it look like a Closure problem rather than a lookup problem.

ROOT CAUSE. `$obj(...)` records an `EvalClosureObjectTarget::InvokableObject { object }` (or `ObjectMethod` / `StaticMethod`). Both resolution paths then search the FUNCTION tables -- `context.closure(name)`, `context.function(lookup_name)`, `context.native_function(lookup_name)` -- and `eval_reflection_closure_target_lookup_name` deliberately answers only for `Named`/`BoundNamed`, so a method-shaped target fell through to a fallback that builds the reflection object with `parameters: &[]` and `required_parameter_count: 0`.

TWO SITES, and fixing only one changes nothing visible. `eval_reflection_function_method_target` (`function_metadata.rs`) answers the lazily-queried metadata; `eval_reflection_function_new` (`function_construction.rs`) MATERIALIZES the `ReflectionParameter` objects into the reflection object's slots at CONSTRUCTION time, and `getParameters()` is an AOT-compiled slot read that never consults the interpreter again. Fixing `function_metadata.rs` alone left `getParameters()` at 0 while the target already reported 2 -- the measurement that proved where the answer actually comes from. The shared resolver is `eval_reflection_closure_target_method`, which maps the three method-shaped targets to (declaring class, method name) and hands them to `eval_reflection_method_metadata` / `eval_reflection_aot_method_metadata_with_signature_if_exists`.

WHY IT MATTERED. Symfony's `ArgumentMetadataFactory::createArgumentMetadata` does `$reflector ??= new \ReflectionFunction($controller(...)); foreach ($reflector->getParameters() as $param)`. Zero parameters means `ArgumentResolver::getArguments()` returns `[]`, so `$controller(...$arguments)` at `HttpKernel.php:188` bound nothing to a required parameter and the request died -- reported as `unsupported DynamicCall expression`, which names the CALLER's expression and not the refusal.

STILL WRONG, deliberately out of scope: `getName()` answers `__invoke` where PHP answers `Invoker::__invoke`. The recorded display name is also the registration key for the reflection function, so changing it is not a one-liner.
Evidence: scratchpad/red12/gen.php: before, `fn params:2 / invokable params:0 / method params:2 / closure params:2` and `r2 name:__invoke isClosure:1 num:0`; after, `invokable params:2 names:exception,code` and `fromCallable params:2`, matching `php -n` 8.5.10 except for the getName() note above.
Verified by: scratchpad/red12 reducer, then the Symfony --web request advancing past HttpKernel.php:188 into ErrorController::__invoke.

## Verification

scratchpad/red12/gen.php: before, `fn params:2 / invokable params:0 / method params:2 / closure params:2` and `r2 name:__invoke isClosure:1 num:0`; after, `invokable params:2 names:exception,code` and `fromCallable params:2`, matching `php -n` 8.5.10 except for the getName() note above.
