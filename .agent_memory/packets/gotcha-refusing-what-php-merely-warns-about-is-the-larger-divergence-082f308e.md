# Refusing what php merely warns about is the larger divergence

> parse declare stmt accepted only strict types and returned UnsupportedConstruct for every other directive, with a tes…

`parse_declare_stmt` accepted only `strict_types` and returned `UnsupportedConstruct` for every other directive, with a test pinning that refusal and a docblock arguing that accepting a directive and doing nothing would be a "silent divergence". Measuring with `php -n` 8.5.6 reversed the reasoning: php refuses almost nothing there. `declare(foo=1);` emits `Warning: Unsupported declare 'foo'` and the script RUNS ON; `declare(encoding='UTF-8');` emits `Warning: declare(encoding=...) ignored because Zend multibyte feature is turned off by settings` and runs on. Refusing turned a warning into a dead file, which is strictly worse than the divergence it was avoiding. The general lesson: before refusing a construct on "we do not model it", measure whether php refuses it -- a warning php recovers from must not become a parse error.

The ONE thing php refuses in that family is a block body on strict types: `Fatal error: strict_types declaration must not use block mode`.

Tick semantics, measured (not guessable): neither half does anything alone -- `declare(ticks=N)` with no registered handler runs nothing, and `register_tick_function()` with no directive runs nothing. With both: `declare(ticks=1);` at file scope makes the handler run after every statement from the registration onward -- the `register_tick_function()` call ITSELF ticks, and the `unregister_tick_function()` does not, because by the time the tick would fire there is no handler left. `declare(ticks=1) { … }` and `declare(ticks=1): … enddeclare;` scope to their body only. `declare(ticks=3)` over six statements fires TWICE, so the counter RESETS on each fire rather than testing a running total. Ticks also fire inside the body of a function declared in the same ticked file.

A tick handler must run with ticking suppressed (a `tick_running` flag), or its own first statement schedules another tick and the interpreter recurses until it runs out of stack.

ADDING A BUILTIN TO THE SHARED CATALOG: `eval_builtin!` panics at runtime, not compile time, with "eval builtin binding references unknown shared contract ID N from FILE" when the contract is missing from `crates/elephc-builtin-contract/src/catalog_data.rs`. Adding one there then fails THREE census assertions that guard catalog growth, and they must each be moved by the number added: `contracts().len()` in registry.rs, and `eval_registry` / `aot_registry` / `interpreter_adapter` in support.rs. `cargo check --workspace --all-targets` does NOT catch these -- only `cargo test -p elephc-builtin-contract` does, so run it after any catalog edit.

Adding a variant to `EvalStmt` breaks two exhaustive matches that are easy to miss because they are not in the interpreter: `visit_static_var_declarations` in interpreter/dynamic_functions/closure_execution.rs and `eval_stmt_uses_this_property` in parser/statements/property_hook_analysis.rs. Both must DESCEND into any statement body the new variant carries, not just return false for it.
Evidence: Nine tests in crates/elephc-magician/src/interpreter/tests/declare_directives.rs, every expectation measured with php -n 8.5.6. Three sentinels run and restored: without the tick firing four fail; without the block-scope restore exactly the two block-bodied ones; with ticks falling through to the generic directive arm all four tick tests. The catalog census failures and the two exhaustive-match breakages were each hit live during the change.
Verified by: cargo test -p elephc-magician --lib &lt; /dev/null -- 1471 passed, 0 failed; cargo test -p elephc-builtin-contract -- 16 passed, 0 failed; cargo check --workspace --all-targets clean. Commit 891dec3a5e.
