# An eval object's runtime class id is stdClass, so AOT metadata alone can never place it

> An object the interpreter builds carries the stdClass class id in its header whatever class declared it. Every genera…

An object the interpreter builds carries the `stdClass` class id in its header whatever class declared it. Every generated code path that decides something from that header is therefore wrong for an eval object, and each needs its own answer:

- `__elephc_eval_value_is_a` (src/codegen_support/runtime/eval_bridge/{aarch64,x86_64}_values_classes.rs) decided `instanceof` from `__rt_exception_matches` on the header alone, so an eval object failed EVERY object type hint on a compiled method's parameter. Fixed with the hook-slot pattern: `.comm _elephc_eval_object_relation_fn` (data/fixed.rs), installer wrappers in raw_object_helpers.rs (both arches), installed at `__elephc_eval_context_new`, called on a false metadata answer AND when the target name resolves to no AOT metadata at all.
  RE-ENTRANCY is why `crates/elephc-magician/src/ffi/object_relation.rs` wraps `__elephc_eval_object_is_a` rather than installing it directly: the interpreter's answer for an eval class with a NATIVE parent is `values.object_is_a(...)`, which calls straight back into `__elephc_eval_value_is_a`. A thread-local flag bounds the cycle at one level.

- Interface method dispatch (`emit_interface_dispatch_call`, lower_inst/iterators.rs) scans `_class_interface_ptrs[class_id]`, which for `stdClass` lists nothing, and its "defensive" miss answered ZERO. For a `(string)` cast that is a null string pointer the next runtime helper reads a length out of -- observed as an 8 GiB allocation, not an error. `InterfaceDispatchMiss::DynamicToString` now routes that miss to the runtime resolver.

- `serialize()` in AOT code STILL has this gap: it writes `O:8:"stdClass":0:{}` for an eval object. That is the current Symfony blocker (Symfony's `ConfigCache::write()` serializes the metadata resources), and it wants the same hook-slot treatment as `_elephc_eval_unserialize_object_fn`.
Evidence: Reduced to a 12-line probe using `Stringable` (an eval class implementing it, bound to a compiled method's `Stringable` parameter and cast to string there); regression test tests/codegen/eval.rs::test_eval_object_satisfies_native_interface_parameter_and_string_cast. The serialize gap is reproduced by scratchpad red32/b.php: cross-eval serialize is correct, AOT serialize of the same object is `O:8:"stdClass":0:{}`.
Verified by: cargo test --release --test codegen_tests -- codegen::eval::test_eval_object_satisfies_native_interface
