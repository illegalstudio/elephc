# Calling a generator function or method reached ONLY through the runtime eval bridge (an in

> Calling a generator function or method reached ONLY through the runtime eval bridge an include/require whose path is …

Calling a generator function or method reached ONLY through the runtime eval bridge (an include/require whose path is not a literal, or an eval()) failed with "Fatal error: eval() runtime failed: unsupported Call/MethodCall expression" even though the interpreter's own generator machinery (crates/elephc-magician/src/interpreter/generators.rs, generators/lowering.rs, context/generators.rs) was already complete and correct -- all 29 pre-existing fragment tests in crates/elephc-magician/src/interpreter/tests/generators.rs already passed. The mislabeling was the same class of bug as prior campaign defects: the actual failure was two static compile-time gates that each independently decide "can this program reach the builtin Generator class" by scanning ONLY the compiled entry file's own literal AST for a `yield` or the spelled name `Generator` -- src/types/checker/builtin_class_gate.rs::program_may_reference_generator (controls whether the type checker registers the Generator class + its `implements Iterator` at all) and src/codegen/runtime_metadata/classes.rs::runtime_referenced_class_names (controls whether the native `_classes_by_name` table used by `__rt_new_by_name` actually gets a Generator entry). Neither gate accounted for `usage.includes_runtime_php` / `module.required_runtime_features.eval_bridge` (a dynamic include hands the included file to the interpreter at runtime, and that file's `yield` is invisible to any static scan of the entry file) even though the THROWABLES gate right next to program_may_reference_generator already had this exact widening, and runtime_referenced_interfaces already widened ALL interfaces on eval_bridge -- Generator was simply the one place the precedent wasn't applied. Effect of the gap: values.new_object(\"Generator\") returned null (__rt_new_by_name found no registered class), eval_generator_new turned that into a bare EvalStatus::RuntimeFatal with no message, and the outermost Call/MethodCall expression's generic \"unsupported X expression\" labeling (crates/elephc-magician/src/interpreter/expressions.rs eval_expr, first-writer-wins message) picked it up, hiding the real cause completely. Fix: added `|| usage.includes_runtime_php` to program_may_reference_generator and `|| module.required_runtime_features.eval_bridge` to the Generator-insertion condition in runtime_referenced_class_names. This was the last identified blocker of the Symfony --web 404 (Kernel::doInitializeBundles() calls `foreach ($this->registerBundles() as $bundle)` where registerBundles() is a generator method reached only through the autoloader's dynamic include). After the fix, PROBE_FILE=sf404.php through the compiled bridge advances past bundle registration to a NEW, unrelated stopping point: \"unsupported DynamicNewObject expression\" inside the vendor Kernel.php (registerBundles() itself does `yield new $class();` -- the yield/Generator part now works, but dynamic `new $class()` reached only through the eval bridge appears to have its own analogous gap, not yet investigated). Separately, the interpreter's own FakeOps test fixture (crates/elephc-magician/src/interpreter/tests/support/object_ops/relations.rs fake_runtime_object_is_a) had no rule for Generator implementing Iterator/Traversable, so `$generator instanceof Traversable` and `instanceof Iterator` returned false in interpreter unit tests even though the real runtime (via the class_map fix above) gets this for free from Generator's `implements: vec![\"Iterator\"]` declaration in src/types/checker/builtin_iterators.rs.
Evidence: Wrote 2 failing integration tests (tests/codegen/generators/eval_bridge.rs) reproducing the exact reported fatal via a dynamic include (compile_and_run_files with `include $path`), confirmed red, applied the two one-line gate widenings, rebuilt, confirmed both tests green plus all 88 pre-existing codegen generator tests still pass. Reverted just the two fix hunks and reran: got back the byte-identical original \"unsupported Call/MethodCall expression\" fatals (sentinel), then restored. Rebuilt the release elephc compiler and the $R/main probe binary and confirmed `PROBE_FILE=$R/ver3.php $R/main` now matches `php -n` byte-for-byte (previously fatal), and gate.php reports ver3 IDENTICAL. Ran PROBE_FILE=$R/sf404.php $R/main and confirmed it advances past stage:request into a new, different fatal. Also added 5 new crates/elephc-magician interpreter tests (instanceof Generator/Traversable/Iterator, bare `yield;`, static generator method late static binding, uncaught throw from generator body reaching consumer's catch, $this property+method access inside a generator method across resumes) -- all green, 4 of 5 were already correct before any fix (only the instanceof one needed the FakeOps fixture fix). Full `cargo test -p elephc-magician --lib` after all changes: 1681 passed / 2 failed, same 2 pre-existing failing test names as the stated baseline (execute_program_catches_throwable_without_variable_inside_eval, execute_program_finally_return_overrides_uncaught_throw).
Verified by: cargo test --test codegen_tests generators (88 passed), cargo test -p elephc-magician --lib interpreter::tests::generators (34 passed), cargo test -p elephc --lib types::checker::builtin_class_gate (17 passed), cargo test -p elephc-magician --lib full suite (1681 passed / 2 pre-existing failures matching baseline), manual revert-and-restore sentinel, php -n vs PROBE_FILE=$R/main byte-identical comparison via $R/gate.php.
