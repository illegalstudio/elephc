# The opcache file cache is real, and its format was chosen by measurement that rejected the obvious option

> opcache.file cache now keeps elephc's PARSED form of dynamically included scripts on disk, so a cold process skips th…

`opcache.file_cache` now keeps elephc's PARSED form of dynamically included scripts on disk, so a cold process skips the read, the `<?php` scan and the parse.

THE FEASIBILITY WORRY WAS WRONG, and cheap to settle: the eval IR is 35 types whose only import is `super::*`, with no `Arc`, `dyn`, function pointers or raw pointers, so `#[derive(Serialize, Deserialize)]` compiled on the FIRST attempt. The segment layer needs serde's `rc` feature (segments hold `Arc<[u8]>` and `Arc<EvalProgram>`) and `EvalParseError` needs the derive too, because a stored parse failure is part of a cached script.

THE FORMAT DECIDES WHETHER THE FEATURE IS WORTH ANYTHING, and the obvious choice was the wrong one. Measured on macOS arm64 (`script_cache::format_bench`, an `#[ignore]`d test kept in-tree):

  source | parse   | serde_json      | bincode
  4 KB   | 1.32 ms | 2.01 ms (0.66x) | 0.25 ms (5.2x)
  64 KB  | 10.6 ms | 7.14 ms (1.48x) | 2.97 ms (3.6x)
  256 KB | 42.4 ms | 28.5 ms (1.49x) | 10.6 ms (4.0x)

serde_json — already a dependency of this crate — decodes a SMALL script slower than parsing it, and never beats 1.5x, at 3.8x the source size on disk. A cache like that would not repay its I/O. bincode is 3.5-5x at ~1.8x the source, which is why the dependency was added. Measure before building the store, not after.

CORRECTNESS IS THE HARD PART, because a stale entry means WRONG CODE EXECUTED and bincode is NOT self-describing: a payload written by a different IR shape can decode into a plausible-but-wrong tree rather than failing. Three independent checks, any failure treated as a miss rather than an error: the writer's directory (crate version + FORMAT_VERSION), the header's magic and format version, and the source's mtime, size AND canonical path. The path is checked because the file name is a 64-bit hash and two paths can collide — carrying the path in the header turns a collision into a miss.

`script_cache::format_guard` fingerprints the eval IR's own source and fails with instructions when the shape moves without FORMAT_VERSION. It over-invalidates on a comment edit, which is the safe direction: an unneeded bump costs one cold parse, a missed one costs correctness.

TESTING IT NEEDS TWO PROCESSES. No in-process state survives between two `Command` invocations, so running one binary twice over a shared cache directory is the only assertion that cannot pass without a real file cache; `contains()` asked BEFORE the include is what separates a cold first run from a warm second.
Evidence: Format numbers from script_cache::format_bench run on macOS arm64. Cross-process behaviour pinned by tests/opcache_file_cache_tests.rs (15 tests): the cache outlives the writing process, an edited source invalidates its entry, and read_only never creates one. Five file_store unit tests cover the staleness, path and read-only rules.
Verified by: cargo test --workspace --lib (3556 passed; the single failure was a known elephc-phar zipcrypto flake, 0 files touched there and green in isolation) plus all nine opcache suites and web_session_tests
