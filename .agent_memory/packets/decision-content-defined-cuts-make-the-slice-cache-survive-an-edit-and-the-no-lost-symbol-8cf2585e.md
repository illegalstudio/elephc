# Content-defined cuts make the slice cache survive an edit, and the "no lost symbols" gate only means anything against the UNSPLIT baseline

Commit 6575572618, src/linker/asm_split.rs. The size-balanced cut policy picks each cut near `total * part / jobs`, so the body's TOTAL byte count is an input to EVERY boundary: one edited line moves every cut and the slice cache misses on all of them. `ELEPHC_ASM_CUTS=stable` selects a content-defined policy instead — a candidate becomes a cut when the hash of ITS OWN symbol name falls in a residue class, so an edit moves no boundary but its own. DEFAULT REMAINS `balanced`; only the exact string `stable` opts in.

TWO GUARDS THAT ARE NOT OPTIONAL. (1) The stride is a POWER OF TWO near candidates/jobs, never the exact ratio — an exact ratio is itself a function of the candidate count, so adding one symbol would change the stride and move EVERY boundary, reintroducing precisely the instability the policy exists to remove. (2) A SIZE CAP at twice the ideal share, because a run of candidates that all hash the wrong way would otherwise yield one enormous slice and destroy the parallelism; a cap-forced cut is not stable but fires only on that run.

KNOWN LIMIT, pinned in a test rather than hidden: the stride is constant only BETWEEN powers of two, so a program growing across one (1000 -> 1100 candidates, straddling 128*8) changes stride and that build misses on every slice. Rounding makes it rare, not impossible.

THE MEASURED COST, counts not timings, so load-independent:
  freshprobe2 (34.9 MB .s): balanced 8 slices / 6,506 cross-slice locals; stable 17 slices / 14,924 (2.29x)
  Symfony --web (861 MB .s): balanced 8 slices / 46,839; stable 20 slices / 81,335 (1.74x)
That cross-slice count is the input to the `ld -r` recombination decision. Against it, the measured link time is FLAT in the cut count (1.39/2.16/1.53/1.08 s at N=1/2/4/8 with 46,839 published at N=8), so nothing yet says the linker notices — whether that still holds at 81,335 is the open measurement.

THE GATE-READING MISTAKE TO AVOID, which nearly cost me a false defect report. Comparing the two POLICIES' nm output on Symfony shows 18 additions and 10 LOSSES, against a standing gate of "losses must be 0". All 10 are `_elephc_xslice_` names — promoted temporaries that exist ONLY because some cut crossed them; under different cuts they no longer cross one, stay plain assembler locals, and never enter the symbol table. Net +8 matches the promoted count moving 5,831 to 5,839 exactly. THE "NO LOSSES" RULE IS ONLY MEANINGFUL AGAINST THE UNSPLIT BASELINE, whose symbol table contains no promoted names to lose. Re-run against unsplit for the verdict that counts: 315 additions all prefixed, 0 losses. Equally, two cut policies CANNOT produce byte-identical binaries — different object counts, different section padding, a different set of temporaries crossing a cut. Ask instead for identical `Section __text` (8,275,360 on the probe, 94,143,420 on Symfony, equal across every configuration and also the proof that a different number of -dead_strip atoms collects the same code), identical behaviour, zero losses against unsplit, and byte-identity across cold/warm/dirty WITHIN one policy.
Evidence: Two Symfony --web and five freshprobe2 builds with ELEPHC_ASM_CUTS balanced and stable, cache off then cold/warm/one-dirty: the build's own note giving slice counts and cross-slice locals; size -m giving equal __text on both inputs under every policy; nm diffs against the unsplit baseline giving 315 prefixed additions and 0 losses; cmp exit 0 for cold vs warm and cold vs one-dirty under the stable policy with reuse counts 17/17 and 16/17
Verified by: cargo test -j 2 -p elephc --bins linker:: 68 passed 0 failed 0 warnings, including a_stable_cut_set_does_not_move_when_one_function_changes_size and its deliberate contrast the_balanced_policy_moves_boundaries_the_edit_never_touched; crate-wide --bins 1867 passed / 19 failed, failing set unchanged
