# An eval-declared class extending a native Throwable-implementing class (e.g

> An eval declared class extending a native Throwable implementing class e.g. \LogicException AND implementing an inter…

An eval-declared class extending a native Throwable-implementing class (e.g. \LogicException) AND implementing an interface that itself extends \Throwable (Symfony's exact shape: final class FormatException extends \LogicException implements ExceptionInterface, where ExceptionInterface extends \Throwable) failed to declare with 'class X could not be declared', stage=validate_throwable_interfaces. Mechanism: validate_eval_class_does_not_implement_throwable_interfaces unconditionally rejected any class whose pending_class_interface_names (the transitive interface closure) contained 'Throwable', mirroring PHP's real rule ('Class X cannot implement interface Throwable, extend Exception or Error instead') but WITHOUT checking the one exception PHP actually applies: the rule only fires when the class's ancestry does NOT already implement Throwable. A subclass of a Throwable-implementing native or eval parent may legally implement an interface that merely restates a contract the parent already satisfies (verified: php -n 8.5.6, `class Sub extends LogicException implements ExtendsThrowableIface {}` declares fine and is instanceof Throwable). Fix: added eval_class_or_native_parent_is_throwable(parent, context, values), which checks context.class_is_a(parent, 'Throwable') for an eval-declared parent, native_class_is_a for a registered native-parent chain, and falls back to values.object_is_a(string_cell_of_parent_name, 'Throwable', false) for a bare native class name never itself eval-declared (LogicException as a raw extends target has no native_class_parent entry of its own) -- this is the exact mechanism is_a($nativeClassName, 'Throwable', true) already uses. validate_eval_class_does_not_implement_throwable_interfaces now only rejects when the parent does NOT already satisfy Throwable.
Evidence: sf404.php (real Symfony boot through vendor/autoload.php + Dotenv) progressed past FormatException's declaration and constructor entirely: the app now reaches and correctly formats an actual thrown LogicException from Dotenv's own parser, three stages further than the original class-declaration fatal
Verified by: tests/codegen/eval_native_method_retention.rs::test_eval_class_extending_native_and_implementing_a_throwable_interface_declares; revert sentinel reproduced the original 'class MyFormatException could not be declared' text; php -n 8.5.6 oracle

## Verification

sf404.php (real Symfony boot through vendor/autoload.php + Dotenv) progressed past FormatException's declaration and constructor entirely: the app now reaches and correctly formats an actual thrown LogicException from Dotenv's own parser, three stages further than the original class-declaration fatal
