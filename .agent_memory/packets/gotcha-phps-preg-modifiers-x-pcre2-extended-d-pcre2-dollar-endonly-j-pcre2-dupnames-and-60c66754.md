# PHP's preg modifiers x (PCRE2_EXTENDED), D (PCRE2_DOLLAR_ENDONLY), J (PCRE2_DUPNAMES), and

> PHP's preg modifiers x PCRE2 EXTENDED , D PCRE2 DOLLAR ENDONLY , J PCRE2 DUPNAMES , and n PCRE2 NO AUTO CAPTURE canno…

PHP's preg modifiers x (PCRE2_EXTENDED), D (PCRE2_DOLLAR_ENDONLY), J (PCRE2_DUPNAMES), and n (PCRE2_NO_AUTO_CAPTURE) cannot be requested through pcre2posix.h's regcomp()/REG_* cflag set at all — none of those four PCRE2_* options has any POSIX REG_* bit mapped to it (confirmed by reading the installed pcre2posix.h: only CASELESS/MULTILINE/DOTALL/UTF/UNGREEDY/UCP/LITERAL have POSIX bits). REG_NOSUB (0x0020) looked like a candidate for PHP's 'n' but is NOT PCRE2_NO_AUTO_CAPTURE: empirically (built a tiny C harness against host PCRE2 10.47), compiling with REG_NOSUB still gives the pattern its normal capture count (re_nsub unchanged) but makes regexec() report ZERO match positions regardless of requested nmatch — it would have silently broken $matches[0] for every match, not implemented auto-capture suppression. Fixed by rewriting elephc_pcre2_v1_compile() in src/native_deps/recipes/pcre2_shim.c to call pcre2_compile() directly (native options translated by hand, including four new Elephc-owned cflag bits above POSIX's range: 0x4000/0x8000/0x10000/0x20000 for x/D/J/n) instead of delegating to pcre2_regcomp(), then hand-building the same regex_t shape (re_pcre2_code, re_match_data via pcre2_match_data_create_from_pattern, re_nsub via pcre2_pattern_info CAPTURECOUNT) that pcre2_regexec()/pcre2_regfree() already accept — verified empirically that PCRE2's own regexec()/regfree() work fine on a manually-constructed regex_t, not just one regcomp() produced. S and X need no compile flag at all (both are real no-ops: S is a legacy PCRE1 study hint PCRE2's JIT replaced, X's stricter backslash rule is already PCRE2's unconditional default) — verified against php -n 8.5.6 that accepting them with zero behavior change reproduces PHP exactly. This C-level fix is scoped to the eval bridge only: the AOT/native codegen backend's own modifier parser (src/codegen_support/runtime/system/preg_strip.rs, function __rt_preg_strip) still only recognizes i/m/s/U/u/A and was NOT touched — it has the exact same x/D/J/n gap, unfixed, in the AOT-compiled (non-eval) path.
Evidence: Standalone C harness against /opt/homebrew/opt/pcre2 10.47 confirmed REG_NOSUB forces regexec() nmatch=0 and confirmed pcre2_compile()+pcre2_match_data_create_from_pattern()+manual regex_t works with the unmodified pcre2_regexec()/pcre2_regfree(); php -n 8.5.6 gate.php probes mod_lowx/mod_lown/mod_upS/mod_upD/mod_upJ/mod_upX all IDENTICAL after the fix.
