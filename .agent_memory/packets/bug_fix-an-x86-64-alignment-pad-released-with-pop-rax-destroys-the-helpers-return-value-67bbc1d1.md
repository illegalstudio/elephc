# An x86_64 alignment pad released with `pop rax` destroys the helper's return value

> On x86 64 a runtime helper that parks a callee saved register with push rbx + push rax the SysV 16 byte alignment pad…

On x86_64 a runtime helper that parks a callee-saved register with `push rbx` + `push rax` (the SysV 16-byte alignment pad) must release that pad with `add rsp, 8`, NEVER with `pop rax`. rax is the return register: the pop restores rax as it was on ENTRY and destroys whatever the helper computed, one instruction before `ret`. `__rt_spl_dll_shift` returns the removed Mixed cell, delete-mode iteration (`emit_iterator_delete_step_x86_64`) hands that result straight to `__rt_decref_mixed`, so the decref released whatever the caller left in rax.

Why it hid: the broken pop carried a CORRECT comment ("drop the alignment pad before restoring rbx") and it does drop the pad — the damage is a side effect the comment does not mention. And the whole family is green on AArch64: `emit_shift_aarch64` is frameless, parks nothing, has no pad, writes x0 once. Only the x86_64 arm needed rbx parked (a consequence of the rbx-preservation work on spike/runtime-ctx-register), so only the linux-x86_64 CI shard turned red, on a test whose name (`test_phase4_spl_doubly_linked_list_delete_iteration_modes`) named the mode but not the register.

The permanent guard is `no_x86_64_runtime_helper_drops_an_alignment_pad_into_rax` in src/codegen_support/runtime/sysv_call_alignment.rs: it walks every emitted linux-x86_64 helper in both feature profiles and fails on `pop rax`. The rule is FLAT, not "only helpers that return a value" — a pad drop and a genuine rax restore are the same two bytes, and whether a helper returns anything is a fact about its callers, so nothing in the epilogue distinguishes them. The exception door `ALLOWED_POP_RAX` exists because the first run found a real one: `__rt_pcntl_async_dispatch_preserving` is a safe-point wrapper that pushes all fifteen general registers plus flags and restores every one of them, so its `pop rax` IS the saved rax coming back. The list shrinks only — an allowlisted helper that stops popping rax must have its entry deleted, or the next helper to take that name inherits a waiver nobody granted it.

Generalization worth keeping: when a fix adds a callee-saved-register save to an x86_64 helper, it also adds a pad, and the pad's release is a second decision that the alignment audit did not previously cover. Check the epilogue of EVERY helper the save touches, not just the one that motivated it — three of the four DLL helpers changed here return void and were never broken, but they carried the shape that would have been copied into the next value-returning one.
Evidence: codegen::spl::classes::test_phase4_spl_doubly_linked_list_delete_iteration_modes was red on the linux-x86_64 CI shard and green on every AArch64 host. graft ask "spl doubly linked list offsetUnset delete shift storage compaction x86_64" surfaced emit_iterator_delete_step_x86_64, whose two instructions are `call __rt_spl_dll_shift` then `call __rt_decref_mixed`; reading __rt_spl_dll_shift's epilogue showed `pop rax` / `pop rbx` / `ret` with the ret commented "return removed Mixed cell". The new audit, on its first run, independently found the only other `pop rax` in the generated runtime (__rt_pcntl_async_dispatch_preserving) and it turned out to be legitimate, which is what the allowlist records.
Verified by: cargo test --bin elephc sysv_call_alignment (6 passed, including the new audit); cargo test --test codegen_tests -- spl:: (258 passed)

## Verification

codegen::spl::classes::test_phase4_spl_doubly_linked_list_delete_iteration_modes was red on the linux-x86_64 CI shard and green on every AArch64 host. graft ask "spl doubly linked list offsetUnset delete shift storage compaction x86_64" surfaced emit_iterator_delete_step_x86_64, whose two instructions are `call __rt_spl_dll_shift` then `call __rt_decref_mixed`; reading __rt_spl_dll_shift's epilogue showed `pop rax` / `pop rbx` / `ret` with the ret commented "return removed Mixed cell". The new audit, on its first run, independently found the only other `pop rax` in the generated runtime (__rt_pcntl_async_dispatch_preserving) and it turned out to be legitimate, which is what the allowlist records.
