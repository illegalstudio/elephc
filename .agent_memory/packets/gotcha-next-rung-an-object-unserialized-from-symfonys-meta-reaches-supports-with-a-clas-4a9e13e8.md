# NEXT RUNG: an object unserialized from Symfony's .meta reaches `supports()` with a class the runtime cannot name, and the binding refuses as a fatal instead of a TypeError

> OPEN, located to the argument. The Symfony web request now runs 2545 trace lines and dies in ResourceCheckerConfigCac…

OPEN, located to the argument. The Symfony `--web` request now runs 2545 trace lines and dies in
`ResourceCheckerConfigCache::isFresh`'s `foreach ($meta as $resource) { foreach ($this->resourceCheckers as $checker) { if (!$checker->supports($resource)) ...` — at
`ContainerParametersResourceChecker::supports(ResourceInterface $metadata)`.

WHAT THE ARGUMENT IS. The opt-in `phase=dynamic_method_bind_error` trace now prints tag, identity and class:
`arg_tags=["6:4427537744:<unresolved>"]`. Tag 6 means it IS an object, and `runtime_object_class_name` cannot name its class. That identity appears NOWHERE else in the trace, so it is not the object an earlier `supports()` succeeded on — the loop had already passed several resources (`object_is_a` resolved `FileResource` three times, then `ReflectionClassResource`, then `GlobResource`) before reaching this one.

WHERE IT COMES FROM. `$meta` is `safelyUnserialize($metadata)` over `var/cache/dev/*.meta`, so the object was minted by `unserialize`. The first suspects, in order: (a) a class in the meta that is neither compiled nor autoloadable at that moment — reference PHP answers `__PHP_Incomplete_Class` there, and Symfony's `safelyUnserialize` is written around that; (b) an object whose class id survived but whose class table entry did not.

WHY IT IS A FATAL AND NOT A TypeError: `bind_evaluated_method_args_with_ref_mode` cannot DECIDE `instanceof ResourceInterface` for a class it cannot resolve, so it refuses with `RuntimeFatal`. PHP would raise a TypeError, which Symfony catches. Making an undecidable nominal check answer "not an instance" instead of "cannot proceed" may be the whole fix on its own.

HOW TO CONTINUE: add the class NAME to the unserialize path's diagnostics (the key is already parsed there) and re-run `scratchpad/trace-req.sh`; `grep -n bind_error trace.log` is the one line that matters. The nested-foreach-over-a-generator shape alone does NOT reproduce it (scratchpad/red23 passes and matches `php -n`), so the reduction has to start from the serialized payload, not from the loop.
Evidence: scratchpad/trace.log line 2542: `phase=dynamic_method_bind_error method="Symfony\Component\DependencyInjection\Config\ContainerParametersResourceChecker::supports" status=RuntimeFatal arg_count=1 arg_tags=["6:4427537744:<unresolved>"] params=["metadata"] types=[Class("Symfony\Component\Config\Resource\ResourceInterface")]`. scratchpad/red23 reproduces the loop shape and passes, matching php -n 8.5.10.
Verified by: The Symfony --web trace with the argument tag/identity/class diagnostic added this session.
