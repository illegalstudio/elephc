# The eval stream-id flake was a temp-file name race, not the id allocator

> Two eval stream tests execute program numbers eval stream resources like php and execute program does not recycle a c…

Two eval stream tests (`execute_program_numbers_eval_stream_resources_like_php` and `execute_program_does_not_recycle_a_closed_eval_stream_id` in interpreter/tests/builtins_file_streams.rs) failed intermittently. Both assert ABSOLUTE resource ids (5,6,7 and 5,7), so both looked like the id allocator. The allocator was never the cause: `EvalStreamResources` lives on `ElephcEvalContext` and `execute_program()` builds a fresh one per call, so it is per-test.

The shared state was the TEMPORARY-FILE NAMESPACE. `php://memory` (and every wrapper stream, via `open_ephemeral_stream` in stream_resources/storage.rs) is backed by an unlinked temp file whose name came from `eval_tmpfile_path()` in stream_resources/types.rs: `elephc-magician-tmpfile-{pid}-{nanos}`, opened with `create_new(true)`. Threads of ONE process share the pid, so the clock was the only discriminator -- and two `SystemTime::now()` readings taken at the same instant are not guaranteed to differ. The loser's open failed with `AlreadyExists`, `open_ephemeral_stream()` returned `None`, `fopen()` returned false, and `get_resource_id(false)` was a RuntimeFatal. The two tests seen failing are simply the ones that open several such streams in quick succession.

Fix: add a process-wide `AtomicU64` sequence to the name. The clock reading STAYS as the cross-process half (two runs of the same binary reuse pids, so it separates their leftovers); the counter is the within-process half.

Measured: eight threads each running a three-`fopen` program two hundred times gave 23 failures out of 1600 before, and 0 after, four runs in a row. Sentinel with the counter dropped: 7 of 400 rounds wrong.

GENERAL LESSON, worth more than the fix: when a test asserting an absolute counter value flakes, the counter is the most visible suspect and usually the wrong one. Check what the operation TOUCHES outside the counter -- here, a filesystem name built from `pid + clock`, which is unique across processes and not within one. Any `pid + timestamp` name is a within-process race waiting for a parallel test runner; `cargo test` runs a crate's tests as threads of one process, so the pid is a constant, not a discriminator.

Method: reproduce before fixing. A throwaway `#[ignore]` probe that hammers the operation from N threads and counts mismatches turns "seen three times" into a number, and the same shape becomes the regression test at a size that fails on the old code most runs without slowing the suite (8 threads x 50 rounds here).
Evidence: Reproduced with a threaded probe: 23 failures out of 1600 before the fix, 0 after across four runs. Regression test concurrent_php_memory_streams_do_not_collide_on_a_temporary_file_name (8 threads x 50 rounds) added; sentinel with the sequence counter dropped from the name fails it with 7 of 400 rounds wrong.
Verified by: cargo test -p elephc-magician --lib &lt; /dev/null -- 1482 passed, 0 failed, three consecutive runs. Commit 9f91e013a5.
