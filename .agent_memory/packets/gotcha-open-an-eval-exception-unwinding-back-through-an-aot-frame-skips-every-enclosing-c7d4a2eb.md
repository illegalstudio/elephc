# OPEN: an eval exception unwinding back through an AOT frame skips every enclosing interpreter try, so a catch that should fire never runs

> OPEN, measured and NOT fixed. THE single remaining blocker of the Symfony web request, and it is ONE systemic bug, no…

OPEN, measured and NOT fixed. THE single remaining blocker of the Symfony `--web` request, and it is ONE systemic bug, not a ladder: every `%env(default:...)%` resolution in the app fails the same way. Proof that it is systemic: supplying `APP_RUNTIME_ENV` in the server environment moves the fatal to the very next variable, `SYMFONY_TRUSTED_HOSTS`, with an identical message and exit 255. So one fix unblocks all of them.

Symfony's `default:` env processor wraps the nested resolution in `try { $env = $getEnv($next); } catch (EnvNotFoundException) { }` (EnvVarProcessor.php:134-142). The inner resolution throws `EnvNotFoundException` exactly as PHP does -- normal control flow -- but the catch never runs and the request dies with `Fatal error: Uncaught ... EnvNotFoundException`, worker exit 255.

THE DECISIVE TRACE. Numbering each executed `try` at entry and pairing enter/exit makes the nesting unambiguous (ids assigned in time order; 1 encloses 2 encloses 3 encloses 4, since each was still open when the next was entered):
  try_enter id=1 catches=[EnvNotFoundException]
  try_enter id=2 catches=[ParameterCircularReferenceException]
  try_enter id=3 catches=[EnvNotFoundException]
  try_enter id=4 catches=[ParameterCircularReferenceException]
  try_exit     id=4 control=none            <- innermost finished normally
  try_uncaught id=2 pending=true catches=1  <- the throw surfaced HERE, skipping id=3
  catch_match  class=ParameterCircularReferenceException dynamic=None native=Some(false)
  try_exit     id=2 control=throw           <- re-raised; id=1 never sees it either
The throwable is NOT lost (`pending=true`). It is delivered to id=2 while id=3 -- an enclosing `catch (EnvNotFoundException)` that WOULD have caught it, still open, never exited -- is stepped over. Ordinary Rust `?` propagation cannot skip a live frame, so the unwinding is not going through the interpreter's own call stack.

THE BOUNDARY IS THE MECHANISM. The chain is eval -> AOT -> eval: the trace carries `native_method_error stage=invoke class="Symfony\Component\DependencyInjection\Container" method="getEnv" status=UncaughtThrowable`. On the AOT side `emit_eval_status_check` (src/codegen/lower_inst/builtins/eval/status.rs:13) routes EVAL_STATUS_UNCAUGHT_THROWABLE to `emit_eval_throw_current`, which publishes `_exc_value` and calls `__rt_throw_current` -- the NATIVE unwinder. That unwind walks AOT frames and lands at the nearest AOT try handler, which sits at id=2's level; the interpreter's Rust frame for id=3 is simply not on that path. The fix has to make a throwable raised by eval code reached THROUGH an AOT frame come back to the interpreter frame that made the call as a status, so normal Rust propagation reaches each enclosing `execute_try_stmt` in turn -- or install a bridge try handler per bridged call so the nearest handler is the right one. It touches codegen for every bridged call on every supported target, so it is a design change, not a patch.

RULED OUT, do not redo: the throwable is not lost (`pending=true`); `catch_types_match_thrown`'s `continue` (which skips the AOT `object_is_a` when the eval layer answers `Some(false)`) was removed experimentally, changed NOTHING, and was restored; all five AOT bridge call sites in eval/calls.rs, eval/dynamic_calls.rs and eval/introspection.rs already pop the class scope BEFORE the status check; `native_method_execution.rs` returns `Err(status)` correctly on the invoke path and swallows nothing. Four small reducers of the shape "eval try/catch around a call that leaves eval, re-enters eval and throws" all PASS, so the miniature shape is not sufficient -- reproducing this needs the real depth.

A CORRECTION KEPT ON PURPOSE: the preceding symptom (`Cannot access private property EnvVarProcessor::$loaders`) was first diagnosed as "a finally running after its own frame's scope was popped". That was WRONG. Dumping the WHOLE class stack plus `current_function` showed the innermost frame was the generated container's `load`, not `getEnv`: the real cause is one class-scope stack shared across nested calls leaving an unrelated class on top during a deep unwind. Binding `catch`/`finally` to the scope their `try` started under fixed it and exposed the boundary bug above. Print the whole stack, never just `current_class_scope()`.
Evidence: examples/symfony-app compiled `--web --timings --keep-symbols --heap-size=1073741824`, exit 0, ~60 s; cold request on 1 worker. Fatal: `Uncaught EnvNotFoundException: Environment variable not found: "APP_RUNTIME_ENV".`, exit 255, curl HTTP=000 curlexit=52. Re-run with APP_RUNTIME_ENV=dev in the server environment (no file changed): same fatal for `SYMFONY_TRUSTED_HOSTS`, proving the defect is systemic across every default: env resolution. Oracle: `php -n` 8.5.10 serving this same app returns HTTP 404, 39,315 bytes, containing "Welcome to Symfony!". try_enter/try_exit/try_uncaught/catch_match trace quoted above captured with ELEPHC_EVAL_TRACE=1 on a binary whose mtime was checked against the magician build. Focused regression slice with all landed fixes: `RUST_MIN_STACK=33554432 cargo test --test codegen_tests exception -- --test-threads=4` = 145 passed / 2 failed, both failures reproducing identically on the untouched tree (pre-existing reds).
Verified by: ELEPHC_EVAL_TRACE=1 on the compiled Symfony --web binary with per-try id instrumentation; the APP_RUNTIME_ENV substitution experiment; php -n 8.5.10 as the oracle for the expected 404 page
