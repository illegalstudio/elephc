# Centralising an ownership rule leaves the old release behind, and a no-op re-store turns it fatal

> When a retain/release rule is moved out of its callers into one helper, the callers' own releases must go with it. A …

When a retain/release rule is moved out of its callers into one helper, the callers' own releases must go with it. A caller that keeps one is not merely redundant: it gives the SAME cell back twice. This happened to eval_store_dynamic_property_value, the single writer for the dynamic-property overlay introduced by commit aed7242b3e. Five of the six callers dropped their hand-rolled halves; eval_property_set_result in interpreter/statements/instance_property_access.rs kept its release, which had been correct while that function did its own retain-and-displace and became a double release the moment the displace moved into the helper. Checking every other call site one by one is what proved it was a single drift point rather than a pattern.

What turns a double release into a whole-value loss is the helper's no-op guard: re-storing the cell the overlay already holds returns early, taking no reference and giving none back, because nothing was displaced. A caller that then releases what it saw beforehand gives back the overlay's OWN LIVE reference. An append into a nested property array is exactly that shape, because the array is mutated in place and the write re-stores the same handle. The value then survives only on the object's mirror slot, and the next write to that slot frees it: the WHOLE property reads back empty rather than one element going missing. php prints zero-7 n-3 count-1 for the reducer; elephc printed zero-MISS n-MISS count-0.

TESTING RULE this establishes, and the reason a green interpreter suite said nothing: an ownership defect in the overlay is INVISIBLE to FakeOps. The fixture's array_set always returns the same handle and its boxing keeps a second reference alive, so the extra release stays balanced there. Measured rather than assumed: private, protected, borrowed-source, replaced-value and unset-the-lender shapes all print php's answer and record zero over-releases, and a direct reference-count read of the displaced cell comes back at the value correct accounting would give. A refcount defect that only the real runtime can free belongs in a codegen test that compiles and runs the program, not in the interpreter suite.
Evidence: php -n 8.5.6 prints zero[7]n[3]count[1] for the reducer. The same program compiled and run through the eval bridge printed zero[MISS]n[MISS]count[0] before the fix and php's answer after it, same test and same command, so the sentinel is by construction rather than reconstruction. The interpreter suite is 1398 passed 0 failed with no skips both before and after, which is the point: FakeOps cannot see it. Measured separately: codegen::eval_dynamic_properties::test_eval_reflection_sees_the_same_dynamic_property fails with Fatal error eval() runtime failed both WITH and WITHOUT this change, so it is a different red.
Verified by: cargo test --test codegen_tests keeps_a_nested_property_append: red before, green after (commit 55597b331b); interpreter suite 1398 passed 0 failed 0 filtered
