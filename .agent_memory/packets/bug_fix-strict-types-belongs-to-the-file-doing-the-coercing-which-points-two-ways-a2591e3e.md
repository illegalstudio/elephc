# strict_types belongs to the file doing the coercing, which points two ways

> declare strict types=1 was a single ElephcEvalContext flag set when the directive executed and never restored. Two de…

`declare(strict_types=1)` was a single `ElephcEvalContext` flag set when the directive executed and never restored. Two defects followed: including one strict file left the ENTIRE rest of the program strict (Symfony's vendor tree is almost all strict, and an interpreted container includes it), and the flag decided a call by whoever last ran a directive rather than by who wrote the call.

php's rule, measured with `php -n` 8.5.6 across a lenient app.php including a strict vendor.php: `sf:6 mf:6 out:TypeError sret:TypeError nret:5 take:6 bad:TypeError`. The rule is that the directive governs the FILE CONTAINING THE CODE DOING THE COERCING -- and that one rule points two opposite ways, because an argument is coerced at the CALL and a returned value at the `return`:
- a function or method DECLARED in a strict file but CALLED from a lenient one coerces its arguments (the call site decides, not the declaration);
- a call WRITTEN inside a strict file is strict even when the callee was declared in a lenient file;
- a `return` obeys the file the BODY was declared in, so the same lenient caller gets a throw from a strict-declared function and a coercion from a lenient-declared one.

No global flag can produce all three answers -- a useful test-design point: assert all three in one run, because any two of them are individually satisfiable by a wrong implementation.

Implementation, without any IR/parser change: php requires `declare` to be a file's FIRST statement, and the interpreter does NOT hoist declarations (`execute_statements` in interpreter/statements/dispatch.rs runs statements in order), so when a `FunctionDecl` or `ClassDecl` statement executes, `context.strict_types()` ALREADY holds the declaring file's mode. Stamp it there: `EvalFunction::with_strict_types` and `EvalClass::with_strict_types` (which maps over its methods). Then an include frame saves/restores the flag, and each body-execution site sets the flag to the callee's stamp and restores the caller's.

THE TRAP: the restore must land AFTER `eval_declared_return_control_value` has run, not immediately after `execute_statements`. That call is what checks and coerces the declared return type, and the coercion belongs to the callee -- restoring before it made the two `return` cases silently keep the caller's lenient mode. The by-ref save/restore (`set_returns_by_ref`) sitting right there is a tempting template and is placed correctly for ITS purpose, which is why the wrong order looks natural.

Stamp fields are excluded from `PartialEq` on `EvalFunction`/`EvalClassMethod`, like `source_location`: two declarations of the same shape are the same declaration whatever file mode they were read under, and every parser-shape expectation compares shapes. Adding the field to the `EvalStmt::FunctionDecl` enum variant instead would have broken every one of those expectations, since that PartialEq is derived.

Four body-execution sites need the scoping: two in interpreter/dynamic_functions/closure_execution.rs and two in interpreter/statements/dynamic_method_execution.rs.
Evidence: Two tests in crates/elephc-magician/src/interpreter/tests/strict_types_scope.rs, both through the include entry point, expectations measured with php -n 8.5.6. Three sentinels run and restored: without the include restore both fail; without the function stamp three fail; without the class stamp the six-way one fails. The return-check ordering trap was found live -- with the restore before eval_declared_return_control_value the run gave sret:5 and bad:9 where php gives TypeError for both.
Verified by: cargo test -p elephc-magician --lib &lt; /dev/null -- 1464 passed, 0 failed, 0 filtered; cargo check --workspace --all-targets clean. Commit 752bf0dff0.
