# Object-to-string bound the STATIC class name, so `object`, subclasses and eval classes all "had no __toString"

> Four AOT lowering sites decided whether an object could become a string by looking its STATIC class name up in ctx.mo…

Four AOT lowering sites decided whether an object could become a string by looking its STATIC class name up in `ctx.module.class_infos` and asking for `__tostring`. When that lookup failed they emitted a raw stderr `write` + `exit`. The lookup fails for three different reasons and none of them means "this object has no __toString":

1. The DECLARED type `object` is spelled `PhpType::Object("")` in codegen. Every value typed `object` therefore missed, and the fatal printed an EMPTY class name: `Fatal error: Object of class  could not be converted to string`. This is the first form of the 2026-09-04 open packet.
2. A SUBCLASS that publishes `__toString` was refused because the STATIC type is a parent that publishes none (`function f(): Base` returning a `Child` with `__toString`).
3. An object that genuinely has none stops PHP with a CATCHABLE `Error` naming the class, not with an uncatchable exit.

The boxed-`Mixed` ladder in `emit_mixed_string_dispatch_from_result` had the same hole with NO name at all. It carries one arm per class the module saw declaring `__toString`, matched by class id, and anything else fell off its end into `Fatal error: Object could not be converted to string` — no class, no file, no line. That is verbatim what the Symfony `--web` request died with, and it reduces to three lines: an object without `__toString` reaching a string context through a runtime-included file (which elephc AOT-compiles as an `__elephc_include_variant_*` function, so the ladder is the AOT one).

FIX: all four sites now ask the OBJECT instead of the static type, through the existing `__rt_sprintf_mixed_to_string(tag=6, payload, eval_ctx)`. That helper already resolves `__toString` through the dense class-id-indexed `_class_tostring_ptrs` table (every AOT class, inherited entries included), falls through to `__elephc_eval_string_context` for synthetic NEGATIVE and out-of-range class ids, and otherwise throws PHP's catchable `Error` with the class name read from `_class_name_entries`. Its `sprintf` name records its first caller, not its scope. Both arches already return the pair in `abi::string_result_regs` (x1/x2, rax/rdx), so no shuffling is needed at the call sites. The eval context is passed NULL on purpose: the ladder is a per-module shared helper (`_eir_shared_mixed_to_string`) with no caller context in scope, and `__elephc_eval_string_context` documents null as supported — an eval-created object resolves through the context it is still registered with. Measured: a genuinely `eval()`-declared class with `__toString` now stringifies correctly in concat/cast/echo/sprintf with that null context.

STILL OPEN after this fix, both measured against `php -n` 8.5.6:
- The thrown `Error` is NOT caught by an enclosing `try` when the string-context operand is a plain VARIABLE. The AST exception-flow DCE (`src/optimize/control/dce/tries.rs::dce_try_stmt` -> `active_catch_reachability`) prunes the catch clause, and `dce_try_stmt` then returns the bare try body when no catch survives, so no `try_push_handler` reaches EIR at all. A FunctionCall or `new` operand keeps its handler; a Variable operand does not. `__rt_throw_current` then finds `_exc_handler_top` null and reports "Uncaught". The coarse `src/optimize/effects.rs::expr_effect` gives `ExprKind::Cast` the effect of its inner expression and `ExprKind::Variable` is `Effect::PURE`, so a string cast of a variable carries no `may_throw`.
- `get_debug_type($o)` answers `stdClass` for an eval-declared object where `get_class($o)` on the SAME value correctly answers its class. The class identity is NOT lost — only this one builtin is wrong. Cause: `lower_class_name_lookup` (src/codegen/lower_inst/builtins/types.rs) has a `PhpType::Mixed | Union if has_eval_context(ctx)` arm routing to `lower_eval_object_class_name`, and `lower_get_debug_type` (src/codegen/lower_inst/builtins/scalar_metadata.rs) has NO such arm — its object case calls `emit_mixed_object_class_name_from_value(.., "get_class")` directly. This is the second form of the open packet, and it is narrower than the packet states.
- `implode(',', [$o])` and `in_array($o, $strings)` still REFUSE at compile time: `unsupported EIR backend feature: implode array element PHP type Object("")`.
Evidence: Reduction of 7 receiver shapes x 10 string contexts against `php -n` 8.5.6: every `object`-typed row moved from a fatal with an empty class name to byte-identical output; every no-__toString row moved from a nameless/empty-named uncatchable fatal to the class-named Error. Symfony's verbatim message `Fatal error: Object could not be converted to string` reproduced in 13 lines (AOT object without __toString reaching a string context in a runtime-included file). Commit 4c645c3838.
Verified by: cargo test --test codegen_tests: tostring 16/0, concat 102/0, eval_bridge 11/0, destructors 44/0, reflection 191/158, runtime_gc 256/35, references 62/2, objects:: 305/17 — all at documented baselines, zero new reds. The 4 reds under string_conversion/stringable/interpol were reproduced at HEAD with the change reverted. New tests: test_declared_object_type_and_subclass_reach_tostring_in_string_contexts, test_declared_object_conversion_error_names_the_runtime_class.
