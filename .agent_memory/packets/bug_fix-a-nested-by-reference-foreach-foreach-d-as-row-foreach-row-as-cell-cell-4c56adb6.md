# A nested by-reference foreach (`foreach ($d as &$row) { foreach ($row as &$cell) { $cell =

> A nested by reference foreach foreach $d as &$row { foreach $row as &$cell { $cell = ...; } } lost the inner write in…

A nested by-reference foreach (`foreach ($d as &$row) { foreach ($row as &$cell) { $cell = ...; } }`) lost the inner write in the INTERPRETER only; the AOT compiler already handled it. Root cause: `write_back_method_ref_target`'s `Variable { scope, name }` arm in reference_writeback.rs stored the value straight into the named scope cell without checking whether that scope variable is ITSELF bound to a `reference_target`. The inner loop's by-reference subject resolves to `EvalReferenceTarget::NestedArrayElement { array_target: Box(Variable{scope,"row"}), index }`, so writing `$cell` back walks the chain down to `Variable("row")` and stopped there — but "row" is the OUTER loop's own by-reference variable, itself a `NestedArrayElement` into the source array `$d`, and nothing forwarded the write through it. The statement-level `$name = value;` (`StoreVar` in interpreter/statements/dispatch.rs) already checked `scope.reference_target(name)` and propagated before writing locally; the `Variable` arm of `write_back_method_ref_target` — used by every OTHER reference-writeback caller (nested array elements, method by-ref args, array_walk, `??=`) — did not have this check. Fix: added the same `scope.reference_target(name)` check + recursive `write_back_method_ref_target` call at the top of that arm, mirroring StoreVar, before the existing retain+set-Owned local-cell update. As a side effect this ALSO fixed 2 of 3 separately-reported by-reference closure-capture divergences (a captured array element `use (&$slot)` where `$slot = &$row["k"]`, and a self-replacing closure that overwrites its own captured slot) — same missing-propagation mechanism. It did NOT fix a plain `use (&$n)` scalar capture across two calls (`$n++` twice only advanced once) — that remains a separate, unfixed defect (likely in closure capture rebinding, not this reference-target chain). Verified with a 5-case matrix probe (single by-ref, outer-value/inner-ref, outer-ref/inner-value, both-by-ref, by-ref over a property array) identical to `php -n` on all 5 after the fix; only "both by-ref" diverged before. `cargo test -p elephc-magician --lib`: 1522 passed / 2 failed both before and after (same 2 pre-existing unrelated failures: execute_program_catches_throwable_without_variable_inside_eval and execute_program_finally_return_overrides_uncaught_throw, both showing Ok(1) vs Ok(6) — looks like shared global state across parallel test threads, not caused by this change).
Evidence: zsh scratchpad/r200/run.sh p0 identical php/elephc on all 5 lines after fix (bothref:X,Y/Z matched, was bothref:x,y/z before); target/release/elephc p0.php && ./p0 (AOT) unchanged/correct both before and after; cargo test -p elephc-magician --lib 1522/2 passed/failed identical failing-test names before and after the fix
