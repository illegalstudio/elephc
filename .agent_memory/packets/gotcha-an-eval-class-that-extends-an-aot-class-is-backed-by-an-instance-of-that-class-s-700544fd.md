# An eval class that extends an AOT class is backed by an instance of that class, so a property its native parent lacks has no slot and the write must be best-effort

> eval dynamic class allocate object allocates the nearest NATIVE parent and hangs the eval class's own state beside it…

eval_dynamic_class_allocate_object allocates the nearest NATIVE parent and hangs the eval class's own state beside it, so an interpreter-declared class that extends an AOT class is backed by an instance of that AOT class. Its slots were fixed when the binary was compiled. A property the eval class declares and the parent does not therefore has no slot to receive it, and a slot write for such a property answers with a status.

Any code that mirrors a property into the object's slots must treat that status as expected, not as a failure. Two write points do the mirroring, in interpreter/statements/class_resolution.rs at construction and in interpreter/statements/instance_property_access.rs on assignment, and making either a hard requirement aborts the allocation and then the constructor. Symfony's dumped container is exactly this shape: App_KernelDevDebugContainer extends Container and declares targetDir, parameters and getService plus promoted constructor properties, none of which are slots of the compiled Container, so every request that loaded a warm container died with the six-word eval runtime failed fatal before any service was built.

The overlay stays authoritative for reads, so a property in this position is unaffected for the ordinary read path; what it loses is visibility to the enumerators, which walk slots its backing object could never have held. A second, independent condition governs the same two writes: only a PUBLIC property is mirrored at all, because this interpreter mangles a private storage name but leaves a protected one plain, so a protected property in the slots is indistinguishable from a public one and json_encode would export it.

The failure MOVES between the two write points as each is fixed — allocation first, at the declared default, then the constructor's own write — which is the sign that they are one bug at two sites rather than two bugs.
Evidence: Reducer: an AOT-compiled class ProbeAotBase with a protected array property in the main file, and a runtime-included class ProbeExt extends ProbeAotBase declaring an untyped property, a typed array property with a default, a typed Closure property and a constructor promoting two more. php -n 8.5.6 prints declared;made;/t1/c0;done. elephc printed declared; then Fatal error: eval() runtime failed, and prints php's line after both writes are best-effort. In the Symfony binary the same bug appeared as phase=eval_class_new_error stage=allocation class=ContainerTvPT0Dp\App_KernelDevDebugContainer at 0.7 s into the request; afterwards the request runs to 8.8 s.
Verified by: the reducer against php -n 8.5.6, and a Symfony --web compile-and-curl before and after
