# Routing a state family to per-context storage costs four accessors and a table

> Routing a global state family to per context storage in elephc costs four functions and one table, NOT a pass over th…

Routing a global state family to per-context storage in elephc costs four functions and one table, NOT a pass over the call sites. Six families are routed this way now (exceptions, fibers+stack guard, GC counters, C-string scratch, output buffering+print_r, resource tables) — 38 of the runtime's 174 `.comm` symbols — and not one of the ~500 call sites changed.

The mechanism: fields in `_rt_ctx`, a name→offset table in ctx.rs (`per_context_symbol_offset`), and the four `abi::` symbol accessors consulting it. `data/fixed.rs` then stops declaring the legacy symbol in ctx builds, so any path still naming it fails the LINK instead of silently sharing state.

CORRECTION TO THE SUPERSEDED PACKET. It claimed a two-step access (`emit_symbol_address` into a scratch, then a bare load/store) would survive the link tripwire and keep writing the process-global cell, and that converting such sites was a correctness requirement. That is wrong. `emit_symbol_address` is itself one of the routed accessors, so it hands back the CTX field's address and the bare store follows it correctly. Measured: the GC family's 25 two-step sites, the output-buffering family's 100+, and the resource family's 117 all routed by adding table rows and nothing else. The only shape that genuinely cannot be routed is a store that names the symbol ITSELF (`mov QWORD PTR [rip + _exc_value], rax`); there were three, in math.rs, math/binary.rs and iterator_iterator.rs. Converting the twelve two-step exception sites was still worth doing for uniformity and auditability — it is not what made the routing correct.

THE ENCODING CONSTRAINT, learned at the fourth family. AArch64 `add xN, xM, #imm` takes a 12-bit immediate or a 12-bit one shifted left by 12, so a single instruction covers an offset below 4096 or an exact multiple of 4096, and nothing else. The context outgrew the first 4 KiB window once ten 512-byte output-buffer tables joined it. The answer is to widen `emit_ctx_address` (split a wide offset into its two encodable adds), NOT to pad the layout onto a 4 KiB grid — padding to suit an instruction encoding is how a struct becomes unmaintainable. `ldr xN, [x28, #imm]` is a separate budget: its immediate is scaled by 8, so 32760 for 64-bit loads, which every scalar is far below.

VERIFICATION SHAPE, same for every family: compile one fixture exercising the family, diff its output against `php -n` (not just against the legacy build), then check three things in the ctx build — ZERO references to the legacy symbol (grep with word boundaries; `_stack_limit` matches `__rt_stack_limit_init` otherwise, which cost three false positives in one session), the expected ctx-relative accesses at the field's offset, and that it LINKS, which is the tripwire reporting no missed path.

The per-context footprint is now pinned by assertion at 221,184 bytes. Three 64 KiB scratch buffers dominate it (concat, print_r capture, stream filter); scalars and every handle table together are under 15 KiB.
Evidence: Six families routed: each verified by a fixture matching php -n byte for byte, zero word-boundary-matched references to the legacy symbols in the ctx build against 64 in its legacy twin for the fiber fixture, and a successful link. Slices in ctx mode: exceptions 78, errors+spl+objects 626, fibers+generators 182, arrays+gc 1097, strings+io 1092, io+streams 686, output buffering 148, zval 72. Bin suite 1936 after every family. The assembler gate (whole runtime, every target) is what validates the widened emit_ctx_address encoding.
Verified by: cargo test --bin elephc (1936); ELEPHC_RT_CTX=on cargo test --test codegen_tests per slice; cargo test --bin elephc assembles (3)
