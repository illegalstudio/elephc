# Inverting the magic-method map cuts the prune phase 17% on magic-heavy code and NOTHING measurable on Symfony: the prune hot spot there is elsewhere

> seed instantiated magic methods src/optimize/reachability/graph.rs ran once per fixed point round and, for EVERY inst…

`seed_instantiated_magic_methods` (src/optimize/reachability/graph.rs) ran once per fixed-point round and, for EVERY instantiated class, scanned the whole of `checker_method_implementations` filtering on `visible_class == &class && is_magic_method(method)` — O(instantiated_classes x every_method_implementation_in_the_program) per round. The filter reads only the map built in `GraphState::new`, which is never mutated during the fixed point, so it is now inverted once into `checker_magic_methods_by_class` and each round does one lookup per class.

WHAT IT IS WORTH, and the second half is the part worth remembering. On a 300-class fixture whose classes each carry several magic and several ordinary methods, the prune phase went from 244.10 / 249.68 / 253.21 ms to 201.57 / 207.57 / 206.28 ms — median 249.68 to 207.57, −16.9 % — with the emitted assembly BYTE-IDENTICAL (sha256 76cf50e5…, 6,787,310 bytes on both sides). The pair is valid: the phases the change cannot touch agree within 3.4 % (type-check 138.90 vs 139.84 ms, lowering 120.18 vs 124.25, codegen 78.70 vs 76.17).

ON SYMFONY IT BUYS NOTHING MEASURABLE. `--web` pruning read 15.02 s before and 14.59 s after, a difference well inside what an unpaired run on a shared machine can produce, and the same build's assembling phase moved 49.80 s to 37.84 s on its own, which no change of mine can explain. So the honest billing is: correct, strictly less work, worth 17 % of the prune phase on code that exercises magic methods heavily, and NOT the route to the campaign's 15 s.

WHERE SYMFONY'S PRUNE TIME IS NOT: `seed_vtable_slot_families`, the other suspect, was ALREADY inverted by echelon 04 (commit 91fd0b420e) and its `live_descendants_by_root` is in the tree. So the two named O(n x m) products in that phase are both closed and 14.59 s remains. Locating the rest needs a profile of the phase, not another reading of it — anyone picking this up should sample the release compiler rather than re-derive candidates from the source.

The full Symfony phase profile at this commit, for whoever takes the next item: assembling 37.84 s (34.9 %), codegen 26.90 s (24.8 %), type-check 15.56 s (14.4 %), pruning 14.59 s (13.5 %), lowering 7.39 s (6.8 %), EIR opt 1.17 s, writing assembly 1.35 s, linking 763 ms, autoloaded-symbol discovery 815 ms, total 108.44 s.
Evidence: Paired three-run measurement on a generated 300-class fixture, release compiler, ELEPHC_ASM_CACHE=0: prune 244.10/249.68/253.21 ms before, 201.57/207.57/206.28 ms after, and 216.90/217.86/207.63 ms on an independent rebuild of the same change. The identity gate is the strong one: `--emit-asm` output is 6,787,310 bytes with sha256 prefix 76cf50e59477a82e in every run on both sides. Symfony `--web --heap-size=1073741824` from the worktree root: pruning 14.59 s with the change against 15.02 s recorded without it, total 108.44 s against 126.76 s — unpaired, and the assembling phase alone moved 12 s between them, so neither number is attributable. `cargo test -p elephc --lib reachability`: 93 passed, 1 failed, the failure being `prune_dynamic_globals_array_alias_widens_all_receiver_names` panicking at "fixture must parse" on an unsupported computed `$GLOBALS` key — a parse-level pre-existing red that cannot reach reachability code.
Verified by: cargo test -p elephc --lib reachability; two independent release builds of the change, each measured three times against a three-run baseline; sha256 of the emitted assembly identical on both sides

Symfony `--web --heap-size=1073741824` from the worktree root: pruning 14.59 s with the change against 15.02 s recorded without it, total 108.44 s against 126.76 s — unpaired, and the assembling phase alone moved 12 s between them, so neither number is attributable. `cargo test -p elephc --lib reachability`: 93 passed, 1 failed, the failure being `prune_dynamic_globals_array_alias_widens_all_receiver_names` panicking at "fixture must parse" on an unsupported computed `$GLOBALS` key — a parse-level pre-existing red that cannot reach reachability code.
