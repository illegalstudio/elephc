# `EXPR(...)` first-class-callable syntax on a variable (not a literal function name, `$obj-

> EXPR ... first class callable syntax on a variable not a literal function name, $obj method , or Class::method parses…

`EXPR(...)` first-class-callable syntax on a variable (not a literal function name, `$obj->method`, or `Class::method`) parses to the SAME `InvokableCallable { object }` EvalIR node no matter what EXPR's runtime value turns out to be -- PHP cannot know which callable shape it is until it evaluates it. The interpreter's `eval_invokable_callable_expr` (crates/elephc-magician/src/interpreter/expressions/calls/first_class.rs) used to always wrap the evaluated value in an `EvalClosureObjectTarget::InvokableObject { object }` target regardless of its actual type. That is correct only when the value is a genuine object with `__invoke`. When the value was ALREADY a Closure (itself a closure-vessel stdClass object with a registered `EvalClosureObjectTarget`), dispatching the new wrapper asked the runtime for the WRAPPED object's own native class via `runtime_object_class_name`, which is the placeholder `stdClass` every closure vessel is allocated as -- never `Closure` -- so calling the result raised `Error: Object of type stdClass is not callable`. When the value was an array callable `[$obj,"method"]` or a string function name, `InvokableObject` has no dispatch case for a non-object receiver at all, and calling the result failed with `Fatal error: eval() runtime failed: unsupported DynamicCall expression`. One mechanism explained both symptoms.

Fix: `eval_invokable_callable_expr` now normalizes the evaluated value through `eval_callable_from_scope` (crates/elephc-magician/src/interpreter/builtins/registry/callable.rs) -- the exact same normalization `Closure::fromCallable()` already used in `eval_closure_from_callable` (crates/elephc-magician/src/interpreter/statements/closure_binding.rs) -- then converts the result with `eval_closure_object_target_from_callable` and builds the closure with `eval_closure_object_from_target`. Both of those two functions had to move from `pub(super)` to `pub(in crate::interpreter)` (and get an explicit named re-export added in `crates/elephc-magician/src/interpreter/statements.rs`, since `use closure_binding::*;` there was a private glob, not a re-export) so `expressions::calls::first_class` could reach them. If `eval_callable_from_scope` fails with `UnsupportedConstruct` and the value is an object, `eval_invokable_object_precheck` is still called to produce PHP's exact "Object of type X is not callable" diagnostic -- never a wrong object.

One known, accepted, PRE-EXISTING and out-of-scope side effect: because `Closure::fromCallable()` itself already builds a NEW closure vessel with a copied target rather than returning the exact same object, `$e = $closureVar(...); var_dump($e === $closureVar);` now answers `false` where php 8.5.6 answers `true` (measured directly: `Closure::fromCallable($c) === $c` is `true` in php, `false` in elephc, on HEAD before AND after this fix -- this fix does not change that, it only reuses the same existing imperfect mechanism). Nothing in this defect family's acceptance probes depends on identity/`===`/`spl_object_id`, only on `get_class()` and calling the result, so this was left alone deliberately.

Regression tests: crates/elephc-magician/src/interpreter/tests/dynamic_calls/first_class_callable_values.rs (interpreter, FakeOps harness) and a new test in tests/codegen/include_paths.rs (`test_runtime_dynamic_include_first_class_callable_syntax_on_variable_values`, full AOT-compiled + eval-bridge path via a runtime-only-known include). Both cover the three broken forms (Closure variable, array-callable variable, string-callable variable) plus the five already-working forms (plain function, `$obj->m(...)`, `Cls::s(...)`, `$obj(...)` on an invokable, `strtoupper(...)`) in one assertion each, so a fix that repairs one by breaking another cannot pass silently.

SEPARATE, NOT fixed here, blocking Symfony's real EventDispatcher::optimizeListeners() replica (scratchpad/r200/p4.php) from matching php even after this fix: a nested by-reference `foreach` over an array whose TOP-LEVEL key set was built via TWO OR MORE SEPARATE auto-vivifying appends (e.g. `$this->listeners[$event][$priority][] = $listener;` called more than once with different `$priority`) loses/corrupts the OUTER loop variable on its second-or-later iteration -- the inner foreach's subject reads back as NULL (EVAL_TAG_NULL, raw pointer 0), producing `Fatal error: eval() runtime failed: unsupported Foreach statement`. This reproduces with a completely minimal, callable-free, class-free, property-free fragment: `$listeners = []; $listeners["evt"][10][] = "a"; $listeners["evt"][5][] = "b"; foreach ($listeners["evt"] as &$group) { foreach ($group as &$item) { $x = 1; } unset($item); } unset($group);` -- php prints nothing wrong, elephc fatals on the SAME construct. A CONTROL with the identical final array shape built as ONE literal assignment instead (`$listeners = ["evt" => [10 => ["a"], 5 => ["b"]]];`) works correctly, isolating the trigger to HOW the array was built (repeated auto-vivifying append vs. a literal), not to nesting depth, by-reference foreach shape, or anything callable-related -- commit 90c3d5a5ec's nested-by-ref-foreach fix did not cover this. This needs its own dedicated session with its own reduction; do not conflate it with the first-class-callable defect family above.
Evidence: Measured with ELEPHC_EVAL_TRACE=1 and php -n 8.5.6 on scratchpad/r200/p5.php, p6.php, p7.php (all 8 forms byte-identical after the fix); sentinel revert reproduced the exact original failure text on both new tests; cargo test -p elephc-magician --lib: 1524 passed / 2 failed (same two pre-existing failures by name, zero new); the separate nested-by-ref-foreach bug was isolated via a 6-step bisection (preduce4.php through preduce11.php) down to a minimal callable-free repro, with a literal-array control that passes.
Verified by: RUST_MIN_STACK=33554432 cargo test -p elephc-magician --lib; zsh scratchpad/r200/run.sh p5 p6 p7 (identical to php); cargo test --test codegen_tests test_runtime_dynamic_include_first_class_callable_syntax_on_variable_values
