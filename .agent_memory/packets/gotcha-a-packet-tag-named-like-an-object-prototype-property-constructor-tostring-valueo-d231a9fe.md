# A packet tag named like an Object prototype property (constructor, toString, valueOf, hasOwnProperty, __proto__) breaks every Kage index build with "map[key].includes is not a function"

> Kage's index builder buildPacketIndexes → addToIndex in the kernel uses plain JavaScript objects as maps keyed by tag…

Kage's index builder (buildPacketIndexes → addToIndex in the kernel) uses plain JavaScript objects as maps keyed by tag, path and type: `if (!map[key]) map[key] = []; if (!map[key].includes(id)) …`. A tag whose lowercase form is an Object.prototype property name — "constructor" in the échelon 44 packet about SPL and date/time constructors — resolves to the inherited function instead of a fresh array, so `.includes` is not a function and EVERY Kage operation that rebuilds indexes fails: kage_context, kage_risk, kage_learn, kage_refresh, the CLI refresh and even `kage doctor` all print only that message with no file named. Diagnosis that worked: call kernel refreshProject directly from node with Error.stackTraceLimit raised (the CLI's top-level catch hides the stack), read the frame, grep the packets for a quoted prototype name in their tags. Fix: rename the tag (constructor → constructors) in both the YAML frontmatter and the kage-state JSON block of the packet, then refresh. Rule for packet authors: never use constructor, toString, valueOf, hasOwnProperty, __proto__, prototype, or any other Object.prototype name as a tag (paths are safe in practice because they contain a slash or a dot). Moving indexes/, graph/, observations/ or review/ aside does not help because the failure is in reading the packets themselves.
Evidence: 2026-09-06 07:55-08:00: every kage MCP tool and the CLI (refresh, doctor) failed with "map[key].includes is not a function"; stack from a direct refreshProject call: addToIndex kernel.js:3778 ← buildPacketIndexes :7329 ← buildGraphIndexes :7481 ← indexProjectDetailed :7538 ← refreshProject :7650; grep found the tag "constructor" in exactly one packet; after renaming it to "constructors" the same direct call returned ok and quiet_refresh true.
Verified by: Coordinator, direct node call of kernel.refreshProject before and after the rename, 2026-09-06 08:00
