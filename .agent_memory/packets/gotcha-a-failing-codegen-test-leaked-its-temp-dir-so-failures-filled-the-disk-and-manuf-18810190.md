# A failing codegen test leaked its temp dir, so failures filled the disk and manufactured more failures

> compile and run and its eleven siblings in tests/codegen/support/compiler.rs deleted their temporary directory on the…

`compile_and_run` and its eleven siblings in tests/codegen/support/compiler.rs deleted their temporary directory on the way out (`let _ = fs::remove_dir_all(&dir);` as the last statement). Any panic BEFORE that -- a compile refusal, an assembler or linker failure, an assertion inside the harness -- skipped it and left the `.s`, `.o` and linked binary behind.

This is a FEEDBACK LOOP, not untidiness: once the disk is short, compiles that would have passed start failing for want of space, and each of those leaks another directory. Measured during one full `codegen::eval` run: 3092 leftover `elephc_test_*` dirs in TMPDIR, free disk 20 GiB -> 7, and the failure rate climbing from 3% early to 49% by the end.

THE REAL COST IS MEASUREMENT. A census taken under those conditions says nothing about the code. Three runs of this suite on this machine have reported 190, 200 and 543 failures; the spread is plausibly this artefact rather than three different code states. Before trusting ANY codegen census: purge dead-pid `elephc_test_*`, check `df`, and do not run it concurrently with another compile-heavy lane.

FIX: a `TestDirGuard` whose `Drop` removes the directory, so it goes away however the test leaves. `ELEPHC_TEST_KEEP=1` keeps it and prints the path for inspecting a genuinely failing case. Insert the guard BESIDE the existing `let dir = ...; fs::create_dir_all(&dir)` and delete the trailing manual removal -- do not rewrite every `&dir` use, which is a far larger and riskier diff for the same effect.

TRAP WHEN WIDENING THIS: a bulk regex over all `let _ = fs::remove_dir_all(&dir);` in tests/ is WRONG. `compile_and_run_in_dir` (tests/codegen/support/projects.rs) RETURNS the directory for the caller to inspect, and its ~18 callers in tests/codegen/io/stat_ext.rs alone remove it themselves after their assertions. Deleting those removals deletes cleanup doing a different job. That family still leaks on a failing assertion and needs the guard RETURNED to the caller -- a separate change.

PURGING SAFELY: only remove `elephc_test_<pid>_*` whose pid is dead (`os.kill(pid, 0)` / ProcessLookupError). Never touch a live suite's dirs -- deleting one under a running test destroys the .s/.o it is about to assemble. Note `elephc_test_runtime_<pid>` is a per-process shared cache with a NON-numeric first segment, so a naive `split("_")[0].isdigit()` filter skips it and hundreds accumulate; parse the pid after `runtime_` to reclaim those too.

SENTINEL SHAPE for a cleanup fix: run the SAME test set twice and count directories. Here, 17 tests (10 pass, 7 fail) gave +1 with the guard and +16 with `Drop` made a no-op.
Evidence: 3092 leftover elephc_test_* dirs found after one codegen::eval run, disk 20->7 GiB, failure rate 3%->49% across the run. Sentinel: the same 17 tests (7 failing) leaked +1 dir with the guard and +16 with Drop made a no-op. Passing tests leak nothing (8/8 green, no new dirs). ELEPHC_TEST_KEEP=1 prints `[elephc-test] kept /…/elephc_test_15157_ThreadId(2)_0`. Purging dead-pid dirs recovered 9 GiB (7 -> 16 free).
Verified by: cargo test -p elephc --test codegen_tests with filters, in a second CARGO_TARGET_DIR. Commit 6c42b8465c.
