# The autoload project root was found by a LEXICAL ancestor walk, so compiling the same file from a different directory silently produced a ten-times-smaller program

> nearest autoload manifest root src/autoload/index.rs walked Path::ancestors of the entry file's parent directory. anc…

`nearest_autoload_manifest_root` (src/autoload/index.rs) walked `Path::ancestors()` of the entry file's parent directory. `ancestors()` is pure string work: for the RELATIVE `public` it yields `["public", ""]` and stops, so the project root one real directory above is never visited, no `composer.json` is found, and `AutoloadIndex::from_project_root` returns an EMPTY index. Name the same directory from one level up — `examples/symfony-app/public` — and it yields four ancestors, finds the manifest, and indexes everything.

The consequence is not a diagnostic but a DIFFERENT PROGRAM, produced silently with exit code 0. Measured on examples/symfony-app with `--web --heap-size=1073741824`:
- from the worktree root, `examples/symfony-app/public/index.php` → 108,317,352-byte binary, 631 `_class_name_` symbols, 126 s;
- from inside examples/symfony-app, `public/index.php` → 11,023,640-byte binary, 122 symbols, 6 s.
An absolute path works from EITHER directory, which is what proves the axis is neither the cwd alone nor the path form alone but a relative path with too few components for the lexical walk.

Minimal reducer, three files outside examples/: a `composer.json` with a PSR-4 `App\` → `src/` mapping, `src/Thing.php` declaring `App\Thing`, and `web/entry.php` doing `new Thing()`. Compiled from inside the project as `web/entry.php` it fails `error[5:6]: Undefined class: App\Thing`; from the parent as `cwdproj/web/entry.php`, or from inside with the absolute path, it prints `thing;done`.

PHP HAS NO SUCH BEHAVIOUR — it resolves `__DIR__`, `dirname(__DIR__)` and the composer files from the script's real path, so where the shell stands is invisible to it. The fix absolutises the entry directory before the walk: `canonicalize()` first (it also resolves symlinks and `..`), falling back to `current_dir().join(entry_dir)` when the directory cannot be canonicalised.

THE FIX IS BEHAVIOUR-PRESERVING FOR CONFIGURATIONS THAT ALREADY WORKED, which is the thing to check when a path becomes absolute: the emitted include paths and the retained class set could have moved. They did not. The root-relative Symfony build is 108,317,352 bytes with 631 class-name symbols before AND after, and the previously broken inside-relative spelling now produces exactly the same 108,317,352 / 631.

A LESSON ABOUT WHERE THIS HID: every gate that had ever been run on this fixture used the same spelling, so the fault was invisible to the whole suite. It surfaced only because two agents ran the same command from different directories and got binaries an order of magnitude apart.
Evidence: Symfony `--web --heap-size=1073741824`, four spellings of one entry file. Before the fix: root+relative 108,317,352 bytes / 631 symbols; inside+relative 11,023,640 / 122; inside+absolute 108,317,352 / 631; root+absolute 108,317,352 / 631. After the fix all four give 108,317,352 / 631, so the working configurations are unchanged and the broken one is repaired. Three-file reducer outside examples/: `Undefined class: App\Thing` from inside before the fix, `thing;done` from all three spellings after. Unit test `a_relative_entry_directory_finds_the_same_root_as_an_absolute_one` asserts the relative and absolute spellings of one directory return the same lookup; `cargo test -p elephc --lib autoload -- --test-threads=1` gives 12 passed / 0 failed.
Verified by: cargo test -p elephc --lib autoload -- --test-threads=1 (12 passed); four paired Symfony --web compiles before and after; a three-file reducer compiled from three positions
