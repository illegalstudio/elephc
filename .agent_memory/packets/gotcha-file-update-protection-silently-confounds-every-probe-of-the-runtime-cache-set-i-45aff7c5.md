# file_update_protection silently confounds every probe of the runtime cache — set it to 0 first

> Any experiment that asks "did reference PHP cache this file?" is INVALID unless opcache.file update protection=0 is p…

Any experiment that asks "did reference PHP cache this file?" is INVALID unless `opcache.file_update_protection=0` is passed. Its default is 2 seconds, and a fixture written by the same shell command that runs PHP is younger than that, so it is refused for its AGE. The refusal is indistinguishable, from the outside, from the refusal being studied: `opcache_is_script_cached()` answers false and the file is absent from `opcache_get_status()['scripts']` either way.

This cost real rework while implementing `opcache.blacklist_filename`. A probe appeared to show that a blacklist entry's `*` crosses `/` (`<dir>/*deep.php` seemed to block `<dir>/sub/deep.php`). Both halves of the reading were wrong: the subdirectory file was being refused for its age, and the `blacklist_misses = 1` on that run belonged to the MAIN SCRIPT, which also matched the pattern. A clean probe — `file_update_protection=0`, plus a main script whose name cannot match — shows the opposite: NEITHER `*` NOR `?` crosses a directory separator. The wrong conclusion had already been written into the module docs and pinned by a passing unit test before a differential corpus (34 paths x 26 patterns, compared against reference) caught it.

TWO GENERAL LESSONS, both cheap to apply:
1. When probing "was this cached", neutralise every OTHER admission rule first: `opcache.file_update_protection=0` and `opcache.max_file_size=0`. Also make sure the MAIN SCRIPT cannot match whatever pattern is under test, because it goes through the same compile path and inflates the counters.
2. A hand-written unit test only pins what you believed when you wrote it. A differential test against reference over a generated corpus pins what reference actually does, and is what caught both this and the `libc::asctime` class of error. Prefer it whenever reference PHP can be driven to answer the same question.

A related trap in the same area: `eval('$x = 1;')` is a CONSTANT fragment, so elephc const-folds it, emits no bridge call, and nothing installed at eval-context setup ever runs — the blacklist load and the `opcache.file_cache` startup validation included. An end-to-end fixture must use an eval that cannot be folded, e.g. `eval('require __DIR__ . "/lib.php";')`. `tests/opcache_file_cache_tests.rs::a_const_folded_eval_never_reaches_the_validation` pins that behaviour; I re-hit it anyway and lost a debugging cycle to it.
Evidence: Reference PHP 8.5.10. Confounded probe: `<dir>/*deep.php` with a just-written `<dir>/sub/deep.php` reported cached=false, blacklist_misses=1. Clean probe with file_update_protection=0 and a non-matching main script: xdeep.php cached=false, sub/deep.php cached=TRUE, blacklist_misses=1. Differential corpus of 34 paths x 26 patterns: 0 mismatches after the correction, 1 mismatch before it.
Verified by: A differential harness comparing the shipped matcher (included verbatim) against reference PHP's own caching decisions, plus 15 unit tests and 8 end-to-end tests, all passing.
