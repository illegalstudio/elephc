# A boxed value can reach a callable-typed property slot (??= on a Closure property)

> ??= reads the property and evaluates the default in two branches that meet at ONE value, so both sides are boxed into…

`??=` reads the property and evaluates the default in two branches that meet at ONE value, so both sides are boxed into a `Mixed` cell and that cell is what the assignment writes back. Property stores had an unbox adapter for object and array slots and none for a callable one, so `self::$make ??= self::make(...)` (Symfony `DependencyInjection\Container::get()`) had no representation to write and the backend refused the whole compile. Fix (commit ef81b967dc, `src/codegen/lower_inst/property_values.rs` `can_unbox_mixed_to_callable_property` / `emit_mixed_callable_for_property_store`, shared by the static path in `static_properties.rs` and the instance path): a descriptor slot holds one pointer, so the unboxed low word IS the value, retained through `emit_retain_current_descriptor` like a directly typed callable store; any other payload raises a catchable PHP `TypeError` (assigning a non-callable to a `\Closure` property is an error in PHP too), NOT the silent null the object adapter normalizes to. This Mixed/Union-into-Callable combination could not reach the store dispatch before (every other rule requires a different slot representation; the null-sentinel rule only admits Void or a literal ConstI64 0), which is why disabling the adapter leaves the `static_propert` filter's 12 failures identical.
Evidence: Backend inventory refusal `store_static_property … Container::$make … Callable` at Container.php:204 gone after the change; `self::$make ??= …` and `$this->format ??= strtoupper(...)` fixtures print what php -n prints; `static_propert` filter 12 failures identical with and without the adapter.
