# OPEN: the Symfony --web request dies on an EnvNotFoundException raised OUTSIDE any default: try, and the AOT-longjmp explanation for it is DISPROVED

> OPEN, measured and NOT fixed, and this packet exists mainly to RETRACT a wrong explanation before someone builds on i…

OPEN, measured and NOT fixed, and this packet exists mainly to RETRACT a wrong explanation before someone builds on it.

THE SYMPTOM. After the builtin-Throwable inheritance fixes and the try-scope fix, the `--web` request dies with `Fatal error: Uncaught Symfony\Component\DependencyInjection\Exception\EnvNotFoundException: Environment variable not found: "APP_RUNTIME_ENV".`, worker exit 255. It is SYSTEMIC, not one variable: supplying APP_RUNTIME_ENV in the server environment moves the fatal to `SYMFONY_TRUSTED_HOSTS` with an identical shape, so one mechanism gates every `%env(default:...)%` in the app.

WHAT I WRONGLY CONCLUDED, and what disproved it. From a trace showing four `try` statements entered and the throwable surfacing at the second while the third (an enclosing `catch (EnvNotFoundException)`) produced no event at all, I concluded that `__rt_throw_current` longjmps past live interpreter frames, abandoning them. That is WRONG. Bracketing the Rust->AOT extern call in `method_call_out` (crates/elephc-magician/src/runtime_hooks/ops/collection_calls.rs) with enter/leave prints showed EVERY enter has its matching leave, including the failing `getEnv`:
  native_call enter method="getEnv" ... native_call leave method="getEnv"
  native_method_error stage=invoke class="...Container" method="getEnv" status=UncaughtThrowable
  try_uncaught pending=true catches=1
Control returns to the Rust frame normally and the throwable propagates as an ordinary `Err(EvalStatus::UncaughtThrowable)`. No frame is abandoned and no longjmp steps over anything. An earlier packet of mine asserting the longjmp mechanism should not be trusted on that point.

WHAT THE EVIDENCE ACTUALLY SAYS. The `Err` propagates through, in order: `native_method_error stage=invoke Container::getEnv` -> `call_arg_error index=0` -> `assign_error stage=value value=NewObject { class_name: "Symfony\Bundle\FrameworkBundle\Secrets\SodiumVault", ... }` -> `statement_error` -> `dynamic_method_end App_KernelDevDebugContainer::load success=false`. So the `getEnv` resolution that escapes is an ARGUMENT of `new SodiumVault(...)` inside the generated container's `load()`, which is lexically OUTSIDE the `default:` processor's try. The enclosing tries that WOULD catch it (`catch (EnvNotFoundException)`) belong to other, already-completed getEnv invocations. Nothing is skipping a catch; there simply is no catch on this path.

SO THE REAL QUESTION IS UPSTREAM, and it is where the next session should start: why does this app resolve APP_RUNTIME_ENV through a path with no `default:` wrapper, when `php -n` 8.5.10 serving the SAME app (same vendor, same var/cache fixture) returns HTTP 404 with the welcome page and never raises this? Two concrete leads, neither yet tested: (1) the known container-freshness defect -- the compiled binary rebuilds the container on EVERY request (see the packet on KernelTrait::initializeContainer and its empty `catch (\Throwable)`), so the cold path resolves env vars a warm container would have baked in; (2) whether `%env(default:kernel.environment:APP_RUNTIME_ENV)%` keeps its `default:` prefix through OUR container dump, i.e. compare the generated var/cache/dev container our binary writes against the one php writes, because the fixture's committed cache is what php regenerates. Diffing those two container dumps is cheap and would settle it.

INSTRUMENTATION THAT EARNED ITS KEEP, and what to re-add temporarily: `phase=property_access_error` (property_validation.rs) prints the declaring class, the visibility and the CURRENT class scope, and cracked the preceding bug; `phase=try_uncaught`, `phase=try_bypass` and `phase=catch_match` (exceptions.rs) are exceptional-path only and show whether a try consulted its catches at all. Deliberately NOT kept, re-add only while hunting: a push/pop trace in `push_class_scope` (runs on every eval method call), a per-`try` enter/exit id trace, and enter/leave brackets around the extern call in `method_call_out` -- all three sit on hot paths and cost even with tracing off.
Evidence: examples/symfony-app compiled `--web --timings --keep-symbols --heap-size=1073741824`, exit 0, 61-73 s across runs; cold request, 1 worker. Fatal `Uncaught EnvNotFoundException ... "APP_RUNTIME_ENV"`, exit 255, curl HTTP=000 curlexit=52. APP_RUNTIME_ENV=dev in the server environment (no file changed) moves it to SYMFONY_TRUSTED_HOSTS, proving it systemic. Oracle: `php -n` 8.5.10 on the same app returns HTTP 404, 39,315 bytes, containing "Welcome to Symfony!". The disproof is the enter/leave bracketing quoted above. Two further hypotheses were tested on the real binary and each changed NOTHING, so both are ruled out: removing the `continue` in `catch_types_match_thrown` that skips the AOT `object_is_a` when the eval layer answers Some(false); and emitting eval callable descriptors WITH the native exception boundary (`emit_runtime_callable_invoker_with_exception_boundary` at eval_callable_helpers.rs:1043 instead of the plain form). Both were reverted rather than shipped unvalidated. Regression slice with the three landed fixes: `RUST_MIN_STACK=33554432 cargo test --test codegen_tests exception -- --test-threads=4` = 145 passed / 2 failed, both failures reproducing identically on the untouched tree.
Verified by: ELEPHC_EVAL_TRACE=1 on the compiled Symfony --web binary with enter/leave bracketing of the Rust->AOT extern call; the APP_RUNTIME_ENV substitution experiment; php -n 8.5.10 as the oracle

## Verification

examples/symfony-app compiled `--web --timings --keep-symbols --heap-size=1073741824`, exit 0, 61-73 s across runs; cold request, 1 worker. Fatal `Uncaught EnvNotFoundException ... "APP_RUNTIME_ENV"`, exit 255, curl HTTP=000 curlexit=52. APP_RUNTIME_ENV=dev in the server environment (no file changed) moves it to SYMFONY_TRUSTED_HOSTS, proving it systemic. Oracle: `php -n` 8.5.10 on the same app returns HTTP 404, 39,315 bytes, containing "Welcome to Symfony!". The disproof is the enter/leave bracketing quoted above. Two further hypotheses were tested on the real binary and each changed NOTHING, so both are ruled out: removing the `continue` in `catch_types_match_thrown` that skips the AOT `object_is_a` when the eval layer answers Some(false); and emitting eval callable descriptors WITH the native exception boundary (`emit_runtime_callable_invoker_with_exception_boundary` at eval_callable_helpers.rs:1043 instead of the plain form). Both were reverted rather than shipped unvalidated. Regression slice with the three landed fixes: `RUST_MIN_STACK=33554432 cargo test --test codegen_tests exception -- --test-threads=4` = 145 passed / 2 failed, both failures reproducing identically on the untouched tree.
