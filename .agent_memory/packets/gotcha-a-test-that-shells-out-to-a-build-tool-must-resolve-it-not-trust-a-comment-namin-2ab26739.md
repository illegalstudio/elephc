# A test that shells out to a build tool must resolve it, not trust a comment naming it

> A test that shells out to a build tool must resolve that tool, never name it on the strength of a comment. Three comm…

A test that shells out to a build tool must resolve that tool, never name it on the strength of a comment. Three comments in one session asserted a toolchain property nobody had executed, and each cost a CI round.

1. `runtime/assembles.rs` called `clang` because a comment said "the compiler already requires clang to link". It does not: `linker::assembler_command` reaches for clang only on non-macOS Apple targets and everything else goes through `target.assembler_cmd()`. The linux CI images carry no clang at all — verified by running `command -v clang cc gcc` inside `elephc-test-linux-x86_64` and `elephc-test-linux-arm64`: both have `cc` and `gcc` only. Two shards red with `No such file or directory`.
2. The replacement passed `-masm=intel` with a comment saying "the flag is ignored elsewhere". True of clang, false of gcc, which REJECTS it: `cc: error: unrecognized command-line option '-masm=intel'`. The aarch64 shard stayed red one more round. The flag was redundant anyway — `emit_text_prelude` writes `.intel_syntax noprefix` into every x86_64 runtime, so removing it removed a whole class of driver incompatibility instead of special-casing an arch.
3. The docblock then claimed the reduced-coverage skip note made the degradation "visible". `cargo test` captures stdout for PASSING tests, so in a green CI run nobody ever reads it. Coverage is a property of the matrix (each shard checks its host target), not of one run.

The shape to keep: resolve a candidate list (`ELEPHC_TEST_ASSEMBLER`, `clang`, `cc`, `gcc`), probe `--version` once and cache it, decide capability from the banner (only clang takes `-target`), pass no arch-specific flags, and assert in-source any property the simplification now depends on — the gate asserts the x86_64 runtime starts with `.intel_syntax noprefix` rather than assuming it a third time.

Also: a negative control needs a paired positive. The `movzx rsid` probe was hand-written without `.intel_syntax noprefix`; under clang's `-masm=intel` it failed for the right reason, under `as` it would have failed over SYNTAX and `assert!(result.is_err())` would still have passed — on exactly the driver the fallback had just introduced. The probe now carries the directive and a sibling assertion requires `movzx esi, …` to ASSEMBLE, so the rejection is known to be about the register name.

Cheap oracle worth remembering: `elephc-test-linux-arm64` reproduces the linux-aarch64 shard's toolchain exactly and runs NATIVE on an Apple Silicon host — about ten minutes cold, no emulation, versus a 40-minute CI round trip.
Evidence: CI job logs on PR #958: `clang is required to assemble the runtime … Os { code: 2, kind: NotFound }` on both Non-Codegen shards, then `cc: error: unrecognized command-line option '-masm=intel'` on Non-Codegen (linux-aarch64). Toolchain confirmed by `command -v clang cc gcc` inside both test images: clang MISSING, cc and gcc present (Alpine gcc 15.2.0).
Verified by: cargo test --bin elephc assembles inside elephc-test-linux-arm64 (native, no clang): 2 passed, printing `assembler driver cc does not take -target, so these were not assembled on this host: MacOS/AArch64, Linux/X86_64`; plus 1935 passed on the macOS host where clang covers all three targets
