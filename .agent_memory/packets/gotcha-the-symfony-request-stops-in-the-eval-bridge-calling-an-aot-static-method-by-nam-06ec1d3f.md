# The Symfony request stops in the eval bridge calling an AOT static method by name: the invoking context has no signature for it, and five reducers rule out every simpler explanation

> The web request dies inside class exists running Symfony's autoload chain, at the moment the bridge invokes the AOT c…

The `--web` request dies inside `class_exists()` running Symfony's autoload chain, at the moment the bridge invokes the AOT-compiled `ClassExistenceResource::throwOnRequiredClass`. Five opt-in trace points added along that path name it exactly:

  phase=static_method_dispatch class="…ClassExistenceResource" method="throwOnRequiredClass" context_owns=false args=1
  phase=native_static_call … owner="…ClassExistenceResource" signature=false args=1
  phase=native_static_call stage=called … outcome=RuntimeFatal

So the context doing the invoking owns no eval declaration of the class AND has no recorded native static-method signature for it, and the generated by-name dispatcher then refuses. It is NOT a missing descriptor: `strings` on the compiled binary contains the emitted callable name `…ClassExistenceResource::throwonrequiredclass`, so codegen did emit the case.

DO NOT REPEAT THESE FIVE HYPOTHESES — each was reduced and each prints php's exact line, so none of them is the cause: the interpreted twin of the method registered as a string callable and driven by class_exists; an AOT class whose static method is registered as a string callable from a runtime-included file; a callback registered in one eval context and invoked from another (two functions that each perform an include give two contexts, because the context handle lives in a frame slot, so this shape is easy to build); a defaulted parameter omitted at the call; and a mixed-case static method name.

What is left, and where the next attempt should start, is what the trace shows and no reducer yet models: the refusal happens inside a NESTED autoload — the chain for one class walking several owner contexts through `eval_spl_autoload_class_in_owner` — and the context that ends up invoking the callback has never been given that class's AOT metadata. `signature=false` is that statement.

A METHOD LESSON: reading a method's body and inferring which call in it fails is not evidence. `debug_backtrace()` was inferred that way from `throwOnRequiredClass`'s source, implemented, and changed nothing about this request; the diagnosis only moved once traces were added and the binary was asked.
