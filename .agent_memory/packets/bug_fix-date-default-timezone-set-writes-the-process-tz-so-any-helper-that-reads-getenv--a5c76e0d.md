# date_default_timezone_set() writes the process TZ, so any helper that reads getenv('TZ') poisons itself

> elephc's date default timezone set WRITES the process TZ environment variable — rt date default timezone set drives l…

elephc's `date_default_timezone_set()` WRITES the process `TZ` environment variable — `__rt_date_default_timezone_set` drives libc through `putenv("TZ=<id>")` + `tzset()` on purpose, because the binary carries no tzdata and lets libc resolve offsets and DST from the system database. Reference PHP does NOT do this: under reference, `getenv('TZ')` stays `false` no matter how many times you call the setter.

CONSEQUENCE, and it bit: any generated helper that resolves "the system timezone" by reading `getenv('TZ')` will read back elephc's own writes on its second and later calls. `__elephc_opcache_system_timezone()` did exactly that, so `opcache_get_status()['scripts']` formatted its FIRST entry's `last_used` in local time and EVERY OTHER ENTRY IN UTC — the first call restored the PHP default (`date_default_timezone_get()` is "UTC" unless configured) and left `TZ=UTC` behind. The fix is to memoize the lookup so it resolves once, before any of the helper's own writes exist.

TWO TRAPS AROUND THE FIX:
1. `static $memo = null;` types the static `Mixed` and the EIR backend refuses to store a `Str` into it: `unsupported EIR backend feature: store_static_local assigning PHP type Str to static local $memo with PHP type Mixed`. A static local must keep ONE PHP type for its whole life, so use a separate Bool "resolved" flag beside a Str memo rather than a null sentinel.
2. The pre-existing test `last_used_is_formatted_in_the_system_timezone` passed throughout, because its fixture has exactly ONE script and it reads only the first `last_used=` line — it could not observe entries disagreeing with each other. Any test of a per-entry property needs MORE THAN ONE ENTRY and must compare them; asserting the first entry is right is not the same claim.

RESIDUAL, still true: the TZ write is observable in ways reference is not (`getenv('TZ')` changes; child processes inherit it), and the opcache helper turns an unset `TZ` into `TZ=UTC` because `date_default_timezone_set()` cannot express "unset". That is a property of the runtime's tzdata-free design, not of the OPcache surface.
Evidence: Three-script fixture, elephc before the fix: main.php 22:08:22, a.php 20:08:22, b.php 20:08:22; reference PHP 8.5.10 on the same fixture: all 22:08:22. After the fix elephc matches reference both with no TZ and with TZ=America/New_York. The new test `every_scripts_entry_agrees_on_the_timezone` was checked to FAIL without the fix, reporting ["22", "20", "20"].
Verified by: A side-by-side comparison against reference PHP 8.5.10, plus a regression test verified to fail when the memo is disabled and pass when it is restored.
