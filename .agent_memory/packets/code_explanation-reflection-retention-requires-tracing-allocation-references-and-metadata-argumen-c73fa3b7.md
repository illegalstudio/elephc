# Reflection retention requires tracing allocation references and metadata argument roles

> Reflection owner creation has several independent ownership boundaries. The generated helper allocates an object and …

Reflection owner creation has several independent ownership boundaries. The generated helper allocates an object and boxes it with __rt_mixed_from_value, which retains its payload; the allocation reference must then be released on both architectures. Metadata array insertion borrows keys and retains values, so fresh builder keys and elements need matching releases. Callable and constant Reflection owners install their type after common construction: their member-array argument must not first be stored in the shared __type field. That incorrect parameter-type mapping retains a boxed parameter array which the later type overwrite strands. Debugger tracing established these mechanisms, but their fixes do not close the entire eval retention test. Assignment expressions are a separate open edge: eval_assign asks write_location to retain a value for its expression result, while eval_expr_result_aliases_storage classifies assignment results as borrowed. Keep that disagreement and condition-temporary cleanup open until focused lifetime tests pass.
Evidence: A CLI differential regression compares one and sixteen inspections with identical argument counts and equal-length mode strings. Latest full fixture is still red: 110 live blocks and 11552 bytes versus 1460 blocks and 146432 bytes. A reduced direct getter followed by ordinary local cleanup grows only two cells and 96 bytes per extra call; moving its assignment into a negated if condition restores large object-graph retention. LLDB observed a ReflectionMethod freed at refcount one while its parameter array stayed alive; an incref breakpoint identified the parameter-array input being retained into __type before later overwrite. Initial argc-based measurement was corrected because extra argv entries themselves retain heap cells. The sibling ReflectionAttribute boxing path remains unaudited by a passing lifetime regression and still needs its corresponding allocation-reference fix.
Verified by: CLI differential probes and LLDB reference-counter tracing; full lifetime gate explicitly still failing
