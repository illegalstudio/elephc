# A `switch`-driven state machine inside a method never changed state when the case labels a

> A switch driven state machine inside a method never changed state when the case labels and/or the assigned values wer…

A `switch`-driven state machine inside a method never changed state when the case labels and/or the assigned values were class constants (`self::STATE_A`/`self::STATE_B`) — the state got stuck in the first case, or made exactly one transition then stuck in the second. Root cause: `eval_class_like_constant_cell` (crates/elephc-magician/src/interpreter/statements/enum_declarations.rs) and `eval_static_property_get_result` (crates/elephc-magician/src/interpreter/statements/static_property_access.rs) hand out the SAME cached RuntimeCellHandle on every fetch of a class constant / static property, exactly like a scope variable read (LoadVar) hands out the scope's own cell. But `eval_expr_result_aliases_storage` (crates/elephc-magician/src/interpreter/expressions.rs), the predicate every assignment/ownership-transfer call site consults to decide whether a value needs an independent copy before a new owner takes it, only recognized `LoadVar` and a few assignment-shaped expressions — NOT `ClassConstantFetch`/`DynamicClassConstantFetch`/`DynamicClassConstantNameFetch`/`StaticPropertyGet`/`DynamicStaticPropertyGet`/`DynamicStaticPropertyNameGet`. So `$state = self::STATE_B;` bound the local directly to the class constant's shared cell instead of copying it; the local's NEXT reassignment then released that shared cell as though the local had owned it (values.release on a handle the class-constant cache still referenced), corrupting the constant for every later read. This is exactly Symfony's `Dotenv::doParse()` shape (`switch ($state) { case self::STATE_VARNAME: ...; $state = self::STATE_VALUE; break; ... }`), and was the direct cause of the `--web` campaign's 404 blocker (\"Missing = in the environment variable declaration\"). Fixed by adding those six EvalExpr variants to `eval_expr_result_aliases_storage`. Two OTHER call sites had independently drifted, narrower duplicates of the same check that bypassed the shared predicate entirely and needed their own fix: `EvalStmt::StoreVar` in crates/elephc-magician/src/interpreter/statements/dispatch.rs (the plain-statement assignment path, as opposed to `eval_assign`'s expression path) checked only `matches!(value, EvalExpr::LoadVar(_))`, and `eval_generator_kept_expr` in crates/elephc-magician/src/interpreter/generators.rs (what a `yield` keeps) had the identical narrow check. Both were switched to call `eval_expr_result_aliases_storage` instead of duplicating the logic. Verified with `php -n` 8.5.6 as the oracle on three discriminating variants (case labels AND assigned values both constants with a call in the body; case labels literal but assigned values constants; case labels AND assigned values both constants with no call) — tests in crates/elephc-magician/src/interpreter/tests/switch_class_constant_state.rs. Reverting the fix reproduces a `RuntimeValueOps` FakeOps panic: \"released a fake cell nobody owned: handle N reached count -1\" at the class constant's cell, confirming the mechanism is a premature release/double-free of shared constant storage, not a scoping or comparison bug.
Evidence: cargo test -p elephc-magician --lib switch_class_constant_state: 3/3 pass after the fix, all 3 fail (double-release panic) with the fix reverted. Full suite: 1636 passed, same 2 pre-existing failures as baseline. Differential oracle: php -n $R/gate.php sw1 sw2 dot_parse dot_trace all IDENTICAL. Symfony sf404 probe now progresses past stage:dotenv and stage:kernel to a new (unrelated) blocker: ParameterBag class declaration failure.
Verified by: cargo test -p elephc-magician --lib; php -n gate.php differential harness against php 8.5.6; manual revert/restore sentinel
