# One builtin-parent table, two walks, only the class-side walk used it

> A PHP builtin interface has no eval declaration, so any parent walk over eval metadata stops at it and reports that i…

A PHP builtin interface has no eval declaration, so any parent walk over eval metadata stops at it and reports that it extends nothing. The context has one table for this, in context/normalization.rs, and TWO walks consult parents in context/class_metadata.rs. collect_class_interface_parent_names already fell back to the table, which is why a class implementing Iterator was correctly seen as a Traversable. collect_interface_parent_names did not, so the interface-side walk still reported Iterator as having no parents. A table used by one of two walks is worse than no table, because the half that works makes the other half look impossible.

The visible symptom was far from the cause: an IteratorAggregate whose getIterator return type is narrowed to Iterator -- php's own covariance and the spelling Symfony writes throughout -- was refused at CLASS DECLARATION with a fatal, before any method could run. Two separate reasons had to be fixed. First the interface walk needed the table fallback, for a narrowed type that is an EVAL-DECLARED interface extending a builtin one. Second, eval_return_class_type_is_a in interpreter/return_type_compat.rs only reached its interface branch when has_interface recognised the name; a builtin name is neither an eval-declared class nor an eval-declared interface, so it fell past both branches and out of the function returning false. Each half covers different inputs and needs its own sentinel: removing one turns a different subset of tests red.

Generator belongs in that same table even though it is a builtin CLASS rather than an interface: it implements Iterator, and getIterator narrowed to Generator failed identically. The table was therefore renamed from builtin_interface_parent_names to builtin_class_like_parent_names -- naming it after interfaces while it carries a class is a lie a later reader pays for.

Related gap left standing and worth knowing: ArrayIterator is a NAME in the known-class list in interpreter/constants.rs with no implementation behind it, so new ArrayIterator with an array argument builds an object that has no rewind, valid or current. Any test that reaches for it as a convenient inner iterator will fail for that reason and not for the reason under test.
Evidence: php -n 8.5.6 prints p=1;q=2;{"p":1,"q":2};T for the narrowed Iterator case, {"g":3} for the narrowed Generator case, and 0 for an eval-declared interface extending Iterator; elephc now prints the same. Sentinels: dropping the new tail in eval_return_class_type_is_a fails the two undeclared-atom tests and leaves the eval-interface one green; dropping the builtin fallback in collect_interface_parent_names fails all three.
Verified by: cargo test -p elephc-magician --lib with no skips: 1391 passed, 0 failed, 0 filtered (commit c478232882)
