# Fixed `static $x; $x ??= <default>;` init_static_local Void-vs-T EIR backend error via a n

> Fixed static $x; $x ??= <default ; init static local Void vs T EIR backend error via a narrow ir lower fold in lower …

Fixed `static $x; $x ??= <default>;` init_static_local Void-vs-T EIR backend error via a narrow ir_lower fold in lower_block (src/ir_lower/stmt/mod.rs): when a StaticVar with synthesized/explicit-null init is immediately followed by `$x ??= <default>;` in the same statement list, collapse the pair into a single lower_static_var(name, default, span) call — reusing the already-working typed-static Op::InitStaticLocal machinery instead of hitting the Void-slot-then-widened-to-T mismatch. lower_block is now pub(crate) and top-level function/method bodies route through it too (src/ir_lower/function.rs lower_body_into_function), not just nested control-flow bodies, since the idiom commonly sits at method-body top level (e.g. Symfony ContractsTrait::doGet).

CRITICAL discovery during GC-safety verification: Op::InitStaticLocal's codegen (codegen_ir/lower_inst/static_locals.rs lower_init_static_local) only guards the FINAL STORE into the persistent .comm slot behind the once-flag branch — the value-producing instructions for <default> are separate straight-line instructions emitted BEFORE Op::InitStaticLocal and execute UNCONDITIONALLY on every call (only the first call's result ever gets stored). This is invisible for ordinary `static $x = <const-expr>;` because PHP requires compile-time-constant initializers there (nothing observable to re-run), but the ??= fold makes arbitrary expressions representable as static inits for the first time, exposing this gap. Verified empirically with --heap-debug: a side-effecting constructor's echo printed 3x across 3 calls instead of once; closures with captures leaked heap blocks (live_blocks=9 after 3 calls) even with no observable side effect since PhpType::Callable isn't in is_refcounted()'s cleanup lattice; NewObject leaked too (live_blocks=3) despite Object being is_refcounted (leak source there not fully root-caused). ArrayLiteral/ArrayLiteralAssoc of side-effect-free elements tested clean (is_refcounted()-covered). Given this, the fold's whitelist is gated by THREE checks in src/ir_lower/stmt/mod.rs: static_var_default_never_null (literals + arrays only — Closure/NewObject/Closure::bind deliberately excluded even though individually non-null), static_var_default_side_effect_free (delegates to newly-exposed crate::optimize::expr_has_side_effects, re-exported via `pub(crate) use control::expr_has_side_effects;` in src/optimize.rs since prune::expr was previously unreachable outside src/optimize/), and static_var_default_leak_safe (recursively requires scalar-literal-only array elements). Final shipped subset: int/float/string/bool literals and arrays thereof. Closure literals, Closure::bind(...), and new Foo() are excluded and correctly fall back to the loud pre-existing error — this satisfies the campaign's "loud under-accept OK; silent-wrong forbidden" law but means the ContractsTrait/Closure::bind acceptance target is NOT reached in the shipped state (deliberate, documented trade-off).

Separately fixed (independently useful, verified --heap-debug clean): ensure_static_local_type_supported (codegen_ir/lower_inst/static_locals.rs) now accepts PhpType::Callable for static locals — it wasn't in the accepted list before even for a directly-typed `static $c = function(){...};` (a legal PHP static initializer since closures are compile-time-representable). Also widened two is_refcounted()-only gates to also cover PhpType::Callable: lower_store_static_local's incref-before-store gate, and codegen/abi/symbols.rs emit_store_result_to_symbol's release-previous-on-restore gate (both reuse the existing callable_descriptor::emit_retain_current_descriptor/emit_release_current_descriptor helpers that emit_incref_if_refcounted/emit_decref_if_refcounted already dispatch Callable to).

Separately found, NOT fixed (out of scope, pre-existing, unrelated to this fold): typed static arrays with in-place `$x[] = ...` mutation do NOT persist growth across calls (`static $x = [1,2,3]; $x[] = count($x);` returns the same [1,2,3,3] every call in elephc vs a growing array in PHP) — reproduced even without any ??= involved. Root cause not investigated.

Also found: `__rt_closure_bind` (src/codegen/runtime/callables/closure_bind.rs) requires the source closure to capture EXACTLY one thing named "this" — a captureless closure (`static function(...){...}`, no `use` clause) ALSO hits "Fatal error: Closure::bind requires a closure that captures only $this", not just closures with extra `use` captures. This is the pre-existing, documented, intentionally-not-fixed frontier for the ContractsTrait shape.
Evidence: Empirically verified with php -n baselines and elephc compile+run diffs across an 11-case persistence matrix (int/string/array literal ??= defaults, function/method scope, two statics in one fn, typed-static and explicit-null regressions, bare is_null probe) — all MATCH. --heap-debug clean (0 leak) for the accepted subset. Confirmed leaks via --heap-debug for excluded cases (closure-with-capture: live_blocks=9; new Counter() with side-effecting ctor: live_blocks=3, and observable ctor echo ran 3x instead of once). error_tests: 1311 passed (4 unrelated failures — 2 explicitly named as pre-existing KNOWN BASELINES in the task spec, 2 from a concurrently-active unrelated Reflection-feature agent in the same shared worktree). runtime_gc: 128/128 passed. ir_backend_smoke_test: 256/256 passed. git diff --check clean, cargo build zero warnings from these files.
