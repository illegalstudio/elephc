# PHP array unpacking is two key rules at once, and the eval parser only knew the token elsewhere

> The eval lexer produces an Ellipsis token and three of the four places PHP allows it were already handled call argume…

The eval lexer produces an Ellipsis token and three of the four places PHP allows it were already handled -- call arguments in parser/expressions/callables_arrays.rs and parameter lists in parser/statements/parameters_types.rs -- but the ARRAY LITERAL element list was not. That asymmetry is what hid the gap: the token is known, so the refusal looks like a precedence problem rather than a missing element shape. When a token is refused in one position but accepted in another, check whether the element or argument list at that position enumerates its own shapes.

Array unpacking is TWO rules at once and an implementation that gets one right and the other wrong passes any test that only spreads a list. INTEGER keys are RENUMBERED from the literal's own running counter, and that counter is SHARED with the elements around the spread, so a bare value written after a two-element spread lands at key 2 rather than key 0 where it would silently overwrite. STRING keys are carried through untouched since PHP 8.1, and a later write wins over an earlier one, so putting the spread before or after a duplicate key gives different answers. Both rules fall out of writing through array_set, because a string key promotes an indexed container to an associative one: spreading a string-keyed array yields a hash, spreading an integer-keyed one yields a LIST regardless of the source keys. json_encode is the reader that distinguishes those two shapes, so it is the one worth asserting against.

The operand may be any Traversable. The three shapes to cover are the same three foreach distinguishes: an eval generator (drained eagerly, since unpacking materializes the whole operand rather than suspending), an IteratorAggregate whose getIterator hands over another traversable, and an Iterator driven through rewind, valid, current, key and next. Anything else is php's fatal Only arrays and Traversables can be unpacked, which catch Throwable does NOT catch, so a refusal rather than an exception is the right shape.

TWO NEIGHBOURING GAPS surfaced while testing the aggregate arm, and both would have been mistaken for unpacking defects. ArrayIterator does not work in the eval interpreter at all: it is a NAME in the known-class list in interpreter/constants.rs with no implementation behind it, so the object built has no rewind, valid or current. And getIterator with a narrowed Iterator return type -- php's own covariance, and the spelling Symfony uses -- is REFUSED at class declaration with a fatal, because eval_return_class_type_is_a in interpreter/return_type_compat.rs resolves the declared return atom against eval-declared classes and interfaces only; a BUILTIN interface reaches neither branch, gets no parents, and so fails to be a Traversable.
Evidence: php -n 8.5.6 prints 1,2,3,4;4;2 and the json shapes for the string-key, duplicate-key, renumbering, shared-counter, empty, generator, iterator and aggregate fragments, and elephc now prints the same. Sentinels: disabling the parse arm fails all nine interpreter tests and both parser tests; preserving the operand's keys instead of renumbering fails exactly the five tests that spread integer keys; giving each spread its own counter starting at zero fails exactly the shared-counter test. Symfony measurement: 8 refused files become 7 with FrameworkExtension.php parsing in full; the reducer corpus goes from 22 refusals of 37 to 21.
Verified by: cargo test -p elephc-magician --lib with no skips: 1388 passed, 0 failed, 0 filtered (commit e6c40db210)
