# A full-suite run fills the disk and reports thousands of failures that are not failures

> Running the whole codegen suite in one process fills the disk and reports thousands of failures that are not failures…

Running the whole codegen suite in one process fills the disk and reports thousands of failures that are not failures. Measured: `cargo test --test codegen_tests` (about 9000 tests) ran 90 minutes and reported "2660 passed; 6241 failed". The disk was at 100% with 358 MB free. Every codegen test compiles and links a real binary into TMPDIR, so the suite's own scratch is what exhausts the volume, and from that point every remaining test fails for want of space. The failures name real test paths and carry ordinary-looking assertions, so the report reads exactly like a mass regression.

The tell is the shape, not any single message: thousands of failures spread across unrelated families at once. A genuine regression in one state family or one emitter does not fail zval, xml discovery and stream filters together.

How to disprove it in one minute rather than chasing it: check `df -h` and re-run ONE of the failing slices on its own. `codegen::zval::` had dozens of failures in that run and passed 72/72 immediately afterwards on a healthy disk, same binary, same ctx mode.

So run the suite SLICE BY SLICE, clean between slices, and stop before the disk is gone. The cleaning has a rule of its own: elephc's scratch directories are named `elephc_test_<pid>_ThreadId(...)_<n>`, so a sweep must check each PID with `os.kill(pid, 0)` and delete only the dead ones — removing a live suite's directories makes ITS tests fail the same way, which is the trap in the other direction. A script doing exactly that removed 152 dead directories and kept every live one (scratchpad/clean_tmp.py, and scratchpad/ctx_slices.sh for the slice runner with a 2 GB floor).

The big consumers on this machine, in order: `target/debug/deps` (9 GB, needed), `target/debug/incremental` (4 GB, pure cache — `rm -rf` is safe when no cargo is running and buys the most per second), the TMPDIR scratch above, and Docker volumes. Do NOT blanket `docker volume prune`: the named oracle volumes (elephc-x86-ctx, elephc-arm64-ctx) hold 35-minute emulated builds, and `act-*` volumes belong to the user's local GitHub Actions runner.
Evidence: ELEPHC_RT_CTX=on cargo test --test codegen_tests reported "2660 passed; 6241 failed" after 5405s, with df showing 358 MB free on a 460 GB volume. The same binary, same ctx mode, ran codegen::zval:: to 72/72 once 152 dead scratch directories and target/debug/incremental were reclaimed. Targeted slices run before the disk filled were all green in ctx mode: exceptions 78, errors+spl+objects 626, fibers+generators 182, arrays+gc 1097, strings+io 1092, io+streams 686, output buffering 148.
Verified by: df -h /System/Volumes/Data before and after; ELEPHC_RT_CTX=on cargo test --test codegen_tests -- zval:: (72 passed)
