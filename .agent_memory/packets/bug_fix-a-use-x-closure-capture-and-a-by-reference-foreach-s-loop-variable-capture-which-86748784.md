# A `use (&$x)` closure capture (and a by-reference `foreach`'s loop-variable capture, which

> A use &$x closure capture and a by reference foreach 's loop variable capture, which shares the same code path bound …

A `use (&$x)` closure capture (and a by-reference `foreach`'s loop-variable capture, which shares the same code path) bound the NAME `$x` in the caller's scope, not the CELL `$x` named at capture time. `eval_call_arg_value`'s `EvalExpr::LoadVar` arm in crates/elephc-magician/src/interpreter/dynamic_functions.rs always manufactured a fresh `EvalReferenceTarget::Variable { scope: caller_scope as *mut _, name }` node, even when `name` was ALREADY itself a reference (bound via `$x = &$arr[];` or a by-reference `foreach`). Write-back (`write_back_method_ref_target`'s `Variable` arm, fixed by 90c3d5a5ec to chase `scope.reference_target(name)`) then re-resolved that shallow target by NAME at call time instead of holding the terminal cell captured at closure-creation time. Two severities from ONE mechanism: (1) if the alias's owning scope is a function/method activation that returns before the closure is ever invoked (the exact `EventDispatcher::optimizeListeners()` shape: `$closure = &$this->optimized[$eventName][]` inside a private method, invoked later from a different call), the raw `*mut ElephcEvalScope` pointer embedded in `Variable` dereferences freed Rust stack memory -> SIGSEGV, no output, exit 139. (2) if the owning scope survives (top-level script), a later rebind of the alias name (a new loop iteration doing `$x = &$other[]` again) or an `unset($x)` silently redirects -- or loses -- a write the FIRST closure already earned, because write-back re-reads `scope.reference_target(name)` at call time and gets whatever the name currently resolves to, not what it resolved to at capture time. A third symptom (an unnamed `Fatal error: eval() fragment uses an unsupported construct` from re-invoking a closure that should have self-replaced) was a downstream consequence of the SAME mechanism, not a separate one -- it disappeared once the write-back target was fixed. The fix mirrors 90c3d5a5ec on the read/capture side: in `eval_call_arg_value`'s `LoadVar` arm, check `caller_scope.reference_target(name)` FIRST and use that (already-resolved, self-contained: `ArrayElement`/`NestedArrayElement`/`ObjectProperty` targets never carry raw scope pointers) as the captured `by_ref_target`, falling back to a fresh `Variable{scope,name}` only when `name` has no existing reference_target (a genuinely bare local). This is safe for ordinary by-ref call arguments too since argument evaluation happens synchronously with no user code between eager and lazy resolution; it only changes behavior for a reference that OUTLIVES the call that created it (closures, and any capture stored for later use). A SEPARATE, NOT fixed here: `bind_closure_captures` seeds a closure's captured-by-reference local from `EvalClosureCaptureBinding.value()`, a snapshot taken ONCE at closure-creation time, on EVERY invocation -- so a closure capturing a genuinely PLAIN local by reference (never itself an alias, e.g. `$n=1; $bump=function()use(&$n){$n++;}; $bump(); $bump();`) and called more than once never sees the previous call's own write-back; php prints `capture:3`, elephc still prints `capture:2` after this fix (probe p9, first line) -- this is a DIFFERENT mechanism (stale bind-time read, not wrong write-back target identity) and was deliberately left unfixed to keep this fix scoped to capture-target construction. Also confirmed via a rigorous three-way before/after diff (revert-only-the-fix, rebuild, rerun) that ~5 unrelated codegen_tests failures under the `include_` filter (compile-time `ExprKind::IncludeValue` resolver panics, heredoc interpolation, function-variant specialization) and all 3 `destructors` failures and all 50 `runtime_gc` failures are byte-identical whether this fix is present or reverted -- pre-existing, unrelated to reference/closure capture, already broken on HEAD before this session.
