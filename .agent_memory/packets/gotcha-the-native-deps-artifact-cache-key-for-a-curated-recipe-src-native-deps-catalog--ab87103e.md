# The native_deps artifact cache key for a curated recipe (src/native_deps/catalog.rs Packag

> The native deps artifact cache key for a curated recipe src/native deps/catalog.rs PackageVersion is package, version…

The native_deps artifact cache key for a curated recipe (src/native_deps/catalog.rs PackageVersion) is (package, version, recipe_revision, source tarball sha256, target) — it does NOT hash the embedded shim source text (e.g. pcre2::SHIM_SOURCE, an include_str! of pcre2_shim.c). Editing src/native_deps/recipes/pcre2_shim.c (or zlib's equivalent) WITHOUT bumping recipe_revision in catalog.rs silently keeps dispatching and reusing whatever was already cached under the old revision's identity: no integrity error, no rebuild, the edit simply never takes effect for anyone (including the editor's own worktree) who already has that revision cached. This worktree had exactly this trap: pcre2 recipe_revision was already at 4 (bumped in a prior session for elephc_pcre2_v1_name_count/group_name) when a new session rewrote elephc_pcre2_v1_compile() — rebuilding the probe binary right after the edit produced a binary in under a second with no visible PCRE2 configure/make log lines, which is the tell that the STALE revision-4 artifact was reused rather than rebuilt. Confirmed by `nm` on the cached libelephc_pcre2_shim.a: it still referenced pcre2_regcomp, not the new pcre2_compile call. Fix: any edit to a curated native shim's C source MUST bump that package's recipe_revision in catalog.rs AND add the new revision to built_in_recipe()'s match arm in src/native_deps/recipe.rs (which is a fixed compiled-in dispatch table, not derived from the catalog automatically) AND extend the previous_pcre2_recipe_revisions_are_not_dispatched-style regression test. Verify success by checking the artifact cache path .../<package>/<version>/r<new-revision>/... has a FRESH mtime and that `nm` on the rebuilt archive shows the new symbols/call sites, not the old ones.
Evidence: nm on the pre-bump cached libelephc_pcre2_shim.a showed an undefined pcre2_regcomp reference; after bumping recipe_revision 4->5 and rebuilding, the lockfile recorded recipe = 5, a fresh artifact directory appeared with a same-minute mtime, and nm showed pcre2_compile_8 undefined with pcre2_regcomp gone.
Verified by: Rebuilt $R/main after the bump; nm -gU / nm on the new libelephc_pcre2_shim.a confirmed the new call sites; native_deps unit tests (cargo test -p elephc --lib native_deps) 58/58 passed including current_catalog_recipe_revisions_have_dispatchers and previous_pcre2_recipe_revisions_are_not_dispatched.

## Verification

nm on the pre-bump cached libelephc_pcre2_shim.a showed an undefined pcre2_regcomp reference; after bumping recipe_revision 4->5 and rebuilding, the lockfile recorded recipe = 5, a fresh artifact directory appeared with a same-minute mtime, and nm showed pcre2_compile_8 undefined with pcre2_regcomp gone.
