# OPEN, found while verifying the named-group + x/n/S/D/J/X modifier fix against Symfony's c

> OPEN, found while verifying the named group + x/n/S/D/J/X modifier fix against Symfony's compiled route matcher shape…

OPEN, found while verifying the named-group + x/n/S/D/J/X modifier fix against Symfony's compiled-route-matcher shape (probe p11.php in the r200 harness), NOT fixed — two separate gaps in the eval bridge's preg_match(): (1) PCRE2's (*MARK:name) / (*:name) backtracking control verb is not implemented at all: php -n populates $matches['MARK'] with the winning branch's mark name (e.g. pattern '{^(?:/foo/(?P<id>[^/]++)(*:23)|/(*:63))$}sDu' against '/' gives $m['MARK']==='63'), elephc never sets that key. This matters because Symfony's compiled UrlMatcher uses exactly this MARK-per-route-alternative trick to know which route matched. (2) A pattern that fails to COMPILE (e.g. '{^(?|(?P<a>x)|(?P<b>y))$}', a branch-reset group giving two different names to alternative-numbered captures without J) makes php emit a warning and return false from preg_match(); elephc's eval bridge instead raises a hard EvalStatus::RuntimeFatal ('unsupported Call expression' from the caller's perspective) for ANY regex compile failure, with no warn+false path at all. This is pre-existing and general (applies to every malformed pattern, not just this one), not introduced or worsened by the named-groups/modifiers fix — eval_preg_regex has always propagated Err via ? straight out of preg_match()/preg_match_all()/etc. Both gaps are orthogonal to the two defects that were fixed and were left alone; they need their own dedicated sessions.
Evidence: php -n 8.5.6 gate.php on scratchpad/r200/p11.php: 'mark' step differs (php prints mark:1:63, elephc prints mark:1:-); 'invalid' step differs (php prints invalid:false, elephc raises Fatal error: eval() runtime failed: unsupported Call expression).
