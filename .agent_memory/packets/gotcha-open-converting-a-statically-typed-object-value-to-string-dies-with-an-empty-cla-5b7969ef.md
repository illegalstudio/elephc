# OPEN: converting a statically typed `object` value to string dies with an EMPTY class name, and an object built by a runtime-written factory reports `stdClass`

> A value whose STATIC type is the bare object keyword loses its class identity at every boundary that needs the class …

A value whose STATIC type is the bare `object` keyword loses its class identity at every boundary that needs the class name, and the failure is a fatal with a hole where the name should be. `function f6(): object { return new B(); }` (B has `__toString`) then `"x" . f6();` stops with `Object of class  could not be converted to string` — note the two spaces: the runtime composed the message from the fragments in src/codegen_support/runtime/data/mod.rs around a class name it did not have. The same expression is CORRECT when the return type is the concrete `B`, when the function is untyped, or when the object goes through a local variable first, so the defect is in the `object`-typed path only, not in string conversion generally. Same family, same root: an object produced by a factory whose PHP source was WRITTEN AT RUNTIME and then included answers `stdClass` to `get_debug_type()` (lowered in src/codegen/lower_inst/builtins/scalar_metadata.rs) instead of its real class — the instance works, only the nominal identity is gone. When you touch this, fix the producer that drops the class, not each consumer: the AOT side must carry the class through the `object`-typed slot, and the interpreter side has its own message and its own `__toString` binding in crates/elephc-magician/src/interpreter/dynamic_functions/method_binding.rs (the `Object of class {} could not be converted to string` format there, plus eval_runtime_object_string_context_value / eval_runtime_object_has_interpreter_tostring), so a fix on one side leaves the other wrong. Still OPEN as of 2026-09-04 and the current Symfony `--web` blocker; do not assume a passing string-conversion test covers it — none of the tree's tests exercise a bare `object` return type.
Evidence: Probe pass W1/W2/W4 of 2026-09-02: every form measured `php -n` against elephc with the probe files under the session scratchpad and examples/symfony-app/. `"x" . f6()` with `function f6(): object` returning a `B` that has `__toString` printed the empty-name fatal; `(string)` on a `: B` return, on an untyped function and on a local variable were all identical to php. The dynamic-factory case compared `get_debug_type()` (php `App\Svc`, elephc `stdClass`). From the session note dated 2026-09-02; the message fragments and the interpreter's own copy of the message were re-read in the tree at HEAD f7a17151de on 2026-09-04.
Verified by: Reduced probes diffed against `php -n` (session note dated 2026-09-02); cited code paths re-read at HEAD f7a17151de on 2026-09-04. No test in the tree pins the behavior.
