# An integer-key array write past the packed length must promote to a hash, not pad with nulls — one condition missing at three independently-duplicated call sites

> PHP promotes any integer key write whose key is negative or not the next packed index into a hash entry appended in i…

PHP promotes any integer-key write whose key is negative or not the next packed index into a hash entry appended in insertion order; elephc's array-write runtime helpers instead grew the packed indexed representation to size key+1 and zero-filled the gap, so `$a[$p] = "x"` on an empty array with $p=10 (a runtime int, not a literal) answered count=11 keys=0..10 where php answers count=1 keys=10. This is exactly what blocked Symfony's --web request: EventDispatcher::addListener does `$this->listeners[$event][$priority][] = $listener` with priorities 10, 5, 1, and the resulting phantom null slots reached a nested foreach as `unsupported Foreach statement`. Root cause is ONE missing condition (promote when index<0 or index>current_length, exactly matching what __rt_array_set_mixed_key already implemented correctly) that had to be added independently at THREE call-site families because this codebase hand-duplicates every array-write shape rather than sharing a generic setter: (1) __rt_array_set_int/_str/_refcounted/_mixed, reached from lower_array_set for a variable integer key into a locally Array(T)-typed array — each needed a NEW branch: check destination heap-kind up front, an already-hash destination inserts via __rt_hash_set directly (hash_set does its own COW split), a still-packed destination whose index is out of range promotes via __rt_array_to_hash (preserves insertion order and the existing value_type) then __rt_decref_array releases the superseded packed container; (2) __rt_array_push_int/_str/_refcounted (the `$a[]=` append helpers) — appending onto an array a prior write had already promoted was STILL broken after fixing (1): count came back right but the appended value silently vanished, because append always wrote at the packed length; fixed by delegating to the pre-existing __rt_hash_append (already computes max(int keys)+1) when the destination kind is already 3; (3) __rt_mixed_array_set and __rt_mixed_array_get_for_write (the boxed-Mixed-container path used for bare `array` properties and for every write reached through the eval bridge, since __elephc_eval_value_array_set dispatches here unconditionally) — these ALREADY promoted correctly on a negative key but not on a sparse one; each needed only 2-4 lines extending the existing comparison to reuse the existing __rt_mixed_cell_promote_to_hash branch. CRITICAL PITFALL discovered mid-fix: moving the sparse/negative check into __rt_array_set_str's already-hash fast path initially inserted a garbage value, because __rt_str_persist (which copies a possibly-transient string into owned heap storage) was only being called on the indexed-path branch; the already-hash branch skipped it and inserted the raw, possibly-transient pointer. Fix: call __rt_str_persist unconditionally BEFORE the kind dispatch, not after it. A literal integer key (`$a[10] = "x"`) is NEVER affected by any of this: it lowers straight to a hash op (Op::HashSet) at IR-build time and never reaches this machinery at all — confirmed empirically by diffing generated assembly for `$a[10]="x"` (literal, calls __rt_hash_set directly) vs `$a[$p]="x"` (variable, calls __rt_array_set_str) for otherwise-identical source. This means naive manual testing of `$a=[]; $a[10]="x";` even through a `show(array $a)` function-boundary wrapper gives a FALSE NEGATIVE (looks correct) for this whole defect family — only a non-literal index (a plain int variable, even one trivially constant-foldable like `$p=10;`) exercises the buggy runtime path. Separately: `count()`/`array_keys()`/`json_encode()` called DIRECTLY on a local whose static type stays a non-Mixed Array(T) after a runtime hash-promotion read WRONG values (count/keys show the pre-promotion packed shape) even though the underlying array is now correctly a hash — but the SAME values read correctly once the array crosses an `array $a`-typed function parameter or return-type boundary (which forces __rt_array_to_mixed, whose reader already checks the runtime kind). This is a separate, pre-existing READ-path gap (not touched by this fix) that must be routed around when writing tests: wrap in a `show(string $label, array $a)`-style parameter to get a reader that respects runtime-promoted storage. Also found via json_encode specifically: even THROUGH an array-to-mixed-converted value, json_encode() on a promoted hash still emits nonsense like `[2]` for `{"10":"x"}` (confirmed via foreach/var_dump on the same value working correctly) — a third, still-uninvestigated read-path gap isolated to json_encode's own Mixed-hash serialization, also not touched. Also confirmed via kage_risk/git history query: `$a[0] = 3` on a hash literal (`["x"=>1,"y"=>2]`) SIGSEGVs identically byte-for-byte before and after this fix under this repo's `compile_and_run` test harness (fixed 8MiB heap) — that shape is an AssocArray-typed local going through the hash setter directly, never touching any file this fix changed, so the crash is a separate pre-existing defect, neither fixed nor regressed. And p4.php (the full Symfony EventDispatcher::optimizeListeners replica) no longer dies on `unsupported Foreach statement` after this fix, but now SIGSEGVs further in — consistent with the ALREADY-DOCUMENTED separate nested-by-reference-foreach-over-auto-vivified-append defect flagged in commit db17c07f39's own message as needing its own session; not chased further here.
