# Reuse the visible-property builtin for foreach, and give the overlay an insertion order

> Iterating a plain object was not implemented at all: the foreach object arm handled the two Iterator interfaces and t…

Iterating a plain object was not implemented at all: the foreach object arm handled the two Iterator interfaces and then returned a fatal, so any object that implemented neither simply could not be looped over. The fix worth remembering is not the arm itself but where it gets its data. PHP iterates the properties visible from the CALLING scope, which is exactly the rule the get-object-vars builtin already implements, so the new arm calls that builtin instead of re-deriving the set. Visibility, ordering and dynamic-property handling are then decided in one place, and the loop cannot disagree with the builtin about the same object. Re-deriving would have meant a fourth copy of a rule that had already drifted three times in this area.

By reference needs its own arm, because the loop variable must alias the PROPERTY rather than the copy sitting in the snapshot. It draws its names from the same snapshot and binds each one through the object-property reference target, so a body that multiplies the loop variable writes back to the object. That case had been refused outright by a guard in the dispatch, which is worth checking for whenever a feature looks unimplemented: the refusal may be a deliberate guard rather than a missing branch.

The ordering half is the deeper lesson. Dynamic properties lived in a hash map, and an earlier pass had sorted the names to stop the answer being arbitrary. Sorting looks like a fix and is not one: it trades an arbitrary order for a wrong one, and it silently passes any test whose fixture happens to be alphabetical. The reference reports dynamic properties in CREATION order, so the context now carries an insertion-order index beside the overlay — a first write appends, a removal drops, and rewriting does not move. Every enumerator reads its order from there. The test that actually proves this creates three dynamic properties out of alphabetical order; with an alphabetical fixture, both the broken and the fixed implementation pass.

Two visibility corrections fell out of testing, both self-inflicted by the previous echelon's write-side fix, and both instructive. Mirroring declared properties into the object's slots so the enumerators could see them is safe only for PUBLIC properties: the JSON encoder exports public properties by walking those slots, and this interpreter mangles a private storage name but leaves a PROTECTED one plain, so a protected property in the slots is indistinguishable from a public one and gets exported. Filtering on the name alone cannot fix that — the mangling convention is not uniform, and that asymmetry is the trap. Restricting the mirror to public properties then broke the dump builtins, which had been reading declared values from the slot; they now read alias, then overlay, then slot, which makes them independent of the mirror rather than dependent on it. The general rule that keeps falling out of this area: a reader should consult the authoritative store directly, and a mirror should be treated as an optimisation nobody relies on.

Process note that paid for itself twice here. Two tests went red after this work; measuring the parent commit showed one was a genuine regression from the visibility guard and the other had been failing all along on an arm this change never touched. Without that measurement the pre-existing one would have been chased, or worse, the real regression would have been dismissed alongside it. Do not include a filter in an after-sweep unless it was in the before-sweep too — the previous echelon's sweep had omitted the one that turned out to hold the pre-existing failure.
Evidence: Oracle is php -n 8.5.6, with the dynamic-property creation deprecation going to stderr and so absent from stdout expectations. On a class with a private, a protected and a public property plus three dynamic ones added in the order zeta, alpha, mid: foreach from outside yields pub then zeta then alpha then mid; from inside a method it yields secret, prot, pub then the same three; a child method sees the parent's protected property and not its private one; get-object-vars gives pub, zeta, alpha, mid and the JSON encoding lists them in that same order. Rewriting a dynamic property after others were created leaves it in its original position. A by-reference loop multiplying each value by ten leaves the object as a is 10, b is 20, c is 30. A class carrying a private, a protected, a public and a dynamic property encodes as only the public and the dynamic one, while print_r shows the private and protected ones with their visibility markers and their values. Filters compared at the same tree by reverting and re-running: builtins_debug_output 5 passed 0 failed both before and after, builtins_json 10 passed 0 failed both times, control_flow 33 passed 1 failed both times with the same name. builtins_class_metadata 96 passed, classes:: 81 passed, builtins_symbols 17, expressions 74, core:: 41, dynamic_property_store 5, reflection_property_store 5, include_reflection 4 and lexer 64 all zero failures; static_members unchanged at 34 passed 2 failed and parser::tests at 255 passed 11 failed. Six new foreach tests pass.
