# An array append handed a consuming sink the same reference a promoted property also retained

> A method that a appends one of its arguments into $this prop and b also hands that same argument to a freshly constru…

A method that (a) appends one of its arguments into `$this->prop[]` and (b) also hands that same argument to a freshly constructed object of another class (e.g. a promoted-property constructor param), called as a discarded statement, corrupted memory: `values.array_set` (backed by `__rt_mixed_array_set`) CONSUMES the value pointer it is handed on every path -- it stores it outright on success and releases it itself when the write cannot be applied -- but `eval_array_append_result`, `eval_property_array_append_result`, `eval_property_array_set_value` (shared by the static-property indexed-set variant), `eval_static_property_array_append_result`, `eval_non_object_array_append_var_stmt`, and `eval_non_object_array_set_var_stmt` all evaluated the appended/assigned value expression and handed the raw `eval_expr` result straight to `array_set` without checking `eval_expr_result_aliases_storage` first, the way `eval_assign` already does before writing an aliasing source into its target (`values.copy_value` there). When the value expression aliased storage (a `LoadVar` reading a parameter, a re-used property read), the array got the SAME physical reference the parameter's call-argument cleanup (`release_owned_bound_args`) still meant to release and that a sibling write (a promoted property assignment, which retains twice for a dynamically-declared class: once for the native-slot mirror in `eval_property_set_result`, once for the interpreter's own overlay in `eval_store_dynamic_property_value`) also counted on. The array ended up under-owning its element by exactly one reference, so releasing either the constructed object or the call argument left the array pointing at freed memory (measured `discarded_other_class:,discarded_other_class:` instead of `discarded_other_class:a,b`, i.e. the PHP oracle `a,b` for `implode(',', $r->seen)` after two `$r->import(...)` calls). Separately, `eval_non_object_array_append_var_stmt` had a WORSE bug for a fresh, non-aliasing temporary (e.g. `$arr[] = new Foo();`): it explicitly released the value again after `array_set` had already consumed it, destructing the object one statement early (measured `dafter:1` instead of `after:1` for `$arr[] = new Foo(); echo \"after:\" . count($arr);` with `Foo::__destruct` echoing `\"d\"`) -- a genuine double-consume, not merely a missing retain. The fix is a single shared helper, `eval_expr_value_for_consuming_store` in `crates/elephc-magician/src/interpreter/expressions.rs`, which evaluates the expression and calls `values.copy_value` on the result only when `eval_expr_result_aliases_storage` is true, then is used at every one of those six call sites in place of a bare `eval_expr` call feeding `array_set`; the old post-store conditional release in `eval_non_object_array_append_var_stmt` was removed entirely since `array_set` already owns the value on both its success and failure paths. Verified via a counted `FakeOps` fixture where a dynamic-object property write is now known to retain TWICE (native-slot mirror + overlay), which must be accounted for before trusting any refcount assertion in this family of test: `crates/elephc-magician/src/interpreter/tests/discarded_call_new_object_shared_argument.rs` asserts exact refcounts (a wrong value is 1 short of correct, not negative, so `FakeOps`'s over-release panic alone does not catch this shape of bug) plus `over_releases().is_empty()`. Confirmed end-to-end against the compiled eval-bridge binary: `gate.php ro4` differs from `php -n` before the fix and is IDENTICAL after (`discarded_other_class:a,b` / `ro4done`), with `ro5`, `d1`-`d4`, `t24`, `ro1`-`ro3` unaffected (still IDENTICAL) and the `elephc-magician --lib` suite unchanged at 1672 baseline passes plus the new tests, same two pre-existing failing names. Separately (found, NOT fixed by this change): the Symfony `--web` boot probe (`sf404.php`) still stops at the identical `stage:request` / `unsupported MethodCall expression in .../src/Kernel.php on line 113` point after this fix, because `ELEPHC_EVAL_TRACE=1` shows the REAL failure is earlier and unrelated -- `Kernel::doInitializeBundles()`'s `foreach ($this->registerBundles() as $bundle)`, where `registerBundles()` is a zero-argument generator method (`yield new FrameworkBundle();`). Reduced to a minimal repro that fails even without any bundle-registration logic at all: `$k = new K(); $gen = $k->registerBundles(); foreach ($gen as $x) {...}` already refuses at the `$gen = $k->registerBundles();` assignment with `unsupported MethodCall expression`, and the same shape fails for a plain top-level generator FUNCTION too (`unsupported Call expression` calling `fn()` directly where `fn` contains a bare `yield`), while a non-generator function used the same way (`foreach (plainFn() as $v)`) works fine -- so the gap is specifically about invoking/consuming a Generator-returning call (function or method) that is not first bound through whatever narrower path the existing generator-method machinery (`eval_body_is_generator` / `eval_generator_new` in `dynamic_method_execution.rs`) expects, not about `foreach` itself, ownership, arrays, or by-ref args (a by-ref `array &$registered` param made no difference to the repro). This is a distinct, substantial, pre-existing gap unrelated to the array-append-consuming-sink family above.
Evidence: cargo test -p elephc-magician --lib: 1677 passed (1672 baseline + 5 new tests), same 2 pre-existing failing names (execute_program_catches_throwable_without_variable_inside_eval, execute_program_finally_return_overrides_uncaught_throw). php -n $R/gate.php ro4 ro5 d1 d2 d3 d4 t24 ro1 ro2 ro3 sa1 sa2 sa3 sa4 sa5 sa6 sa7 sa9 sa10 sa11 sa12: all IDENTICAL after rebuilding libelephc_magician.a and main.php.
Verified by: cargo test -p elephc-magician --lib; php -n gate.php differential against php 8.5.6 and the compiled eval-bridge binary, before and after the fix
