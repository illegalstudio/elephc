# Symfony --web now dies on a WRONG instanceof answer, not on string conversion

> After commit 4c645c3838 fixed the nameless object to string fatal, the Symfony web request advances and dies further …

After commit 4c645c3838 fixed the nameless object-to-string fatal, the Symfony `--web` request advances and dies further along with a NAMED diagnosis, verbatim on stdout:

    Fatal error: Uncaught Error: Object of class Symfony\Component\DependencyInjection\Argument\ServiceClosureArgument could not be converted to string

(worker exit status 255, HTTP 000, curl exit 52; previously the message was `Fatal error: Object could not be converted to string` with exit status 1.)

This is NOT a remaining string-conversion bug. It is a WRONG `instanceof` answer, and the proof is structural, from Symfony's own source rather than from a trace:

`vendor/symfony/dependency-injection/Compiler/ServiceLocatorTagPass.php::process()` lines 73-88 is the only `(string)` cast that can meet a loop value there:

    foreach ($values as $k => $v) {
        if ($v instanceof ServiceClosureArgument) { $services[$k] = $v; continue; }   // line 74
        if ($i === $k) {
            if ($v instanceof Reference) { $k = (string) $v; }                        // line 81
            ++$i;
        } elseif (\is_int($k)) { $i = null; }
        $services[$k] = new ServiceClosureArgument($v);
    }

`ServiceClosureArgument implements ArgumentInterface` and does NOT extend `Reference`; `Reference` is a standalone class with no relation to it. So for elephc to reach line 81 with a `ServiceClosureArgument`, TWO `instanceof` answers must both be wrong on the same value: line 74 answered FALSE (no early `continue`) and line 81 answered TRUE. In PHP the conversion is unreachable, which is why php returns HTTP 404 / 39,315 bytes / "Welcome to Symfony!" for this request.

Do NOT mistake this for the catch-pruning gap. The trace's last probe before the fatal is `phase=object_is_a target="Exception" ... result=Ok(false)` — a catch-match test that correctly refuses an `Error`. PHP would not catch it there either; PHP simply never converts.

`ELEPHC_EVAL_TRACE=1` on ONE request produces 44,065 trace lines, of which 31,456 (71%) are `phase=object_is_a` — every `instanceof` in the container build goes through the eval bridge under `--web`. 12,424 lines carry `owner_lookup=missing`, i.e. the bridge could not find the object's owning eval context and fell back to the caller's. `instanceof ArgumentInterface` answered 4,029 false / 442 true across the request. The trace logs the object identity only on the `owner_lookup=missing` lines, not on the result lines, so the trace ALONE cannot pin which object got which answer — the source argument above is what proves the defect, not the trace.

Next step for whoever picks this up: instrument `object_is_a` to log the object identity on the RESULT line too, then look at whether `owner_lookup=missing` correlates with the wrong answer. Start from `lower_eval_object_is_a` (src/codegen/lower_inst/builtins/eval/introspection.rs) and the bridge's owner-context resolution, the same `dynamic_object_owner_context` fallback that `eval_string_context_inner` uses.
