# Moving a reserved register's value to a stack slot can silently land on an occupied one

> Migrating a value out of a reserved register into a stack slot is NOT the same risk as renaming it to another registe…

Migrating a value out of a reserved register into a stack slot is NOT the same risk as renaming it to another register, and this branch paid for treating it as such. A register rename is safe by construction: the assembler refuses a name that does not exist, and a register is either visibly free or visibly in use within a few lines. A stack slot has neither property — nothing rejects an already-occupied offset, and the other owner of that offset can be hundreds of lines away in the same helper.

Measured: `__rt_str_looks_like_int_for_coercion` kept its integer-significand flag in r14 on main. The ctx-register work reserved r14 and moved the flag to `[rsp + 840]`, which the exponent saturation threshold already owned (written `mov [rsp+840], rax`, read by `cmp rax, [rsp+840]`). The two then destroyed each other on any value carrying an exponent. `1e-2` stopped parsing as numeric, so `ksort(["0.1"=>…, "1e-2"=>…])` fell back to byte ordering and returned `0.1` first — and `krsort` returned the mirror, which is the signature of a comparator that went lexical rather than one that got the numbers wrong. Red on the linux-x86_64 shard only; the AArch64 arm still holds the flag in a register.

Two reusable techniques came out of it.

1) A SWEEP for siblings across a whole branch: for each file the branch touched, collect the stack slots appearing on ADDED diff lines, subtract those on removed lines, and check whether `git show origin/main:<file>` already mentions the remaining ones. A slot that is new on both sides is fine; a slot main already used is a candidate collision. Run against HEAD it printed exactly `[rsp + 840]` and nothing else, so the bug was unique — and against the fixed tree it printed nothing, which is the negative control.

2) A PERMANENT per-helper guard: parse the emitted helper and flag any slot that is both written with a literal (the flag shape, `mov QWORD PTR [slot], 0`/`1`) and used to carry a computed value (`mov [slot], rax`, `cmp rax, [slot]`). Two owners, one slot, reported by name. That rule is deliberately not applied runtime-wide: initialising a slot to 0 and later assigning it from a register is a common and correct single-owner pattern, so a global version would false-positive. Scoped to the helper where the collision happened, it is exact.
Evidence: codegen::arrays::assoc_helpers::test_assoc_key_sorts_compare_negative_exponent_keys_numerically failed on real linux/amd64 with left "0.1:tenth,1e-2:hundredth,|1e-2:hundredth,0.1:tenth," against right "1e-2:hundredth,0.1:tenth,|0.1:tenth,1e-2:hundredth," — the exact mirror-image pair a lexical fallback produces. git diff -w origin/main...HEAD on str_to_number.rs showed the only substantive change was r14 -> [rsp + 840] on four lines, while [rsp + 840] was already the threshold slot on main. Restoring the collision makes the new guard fail and name [rsp + 840]; the fix makes it pass.
Verified by: cargo test --bin elephc (1935 passed, including the new the_numeric_parsers_flag_and_threshold_use_different_stack_slots); the branch-wide slot sweep reporting [rsp + 840] on HEAD and nothing on the fixed tree
