# PHP's bare `array` contract is lowered to the INDEXED repr, so a hash crossing that boundary is misread

> A PHP value declared with the bare type array parameter or return is lowered to PhpType::Array Mixed the INDEXED arra…

A PHP value declared with the bare type `array` (parameter or return) is lowered to `PhpType::Array(Mixed)` -- the INDEXED array repr. When the runtime value is actually a hash (associative array), `coerce_container_to_return_type` in src/ir_lower/stmt/return_coercions.rs deliberately restamps it with a bare `Op::Move` rather than converting it, on the reasoning that "converting the hash itself to indexed storage would discard string keys and change iteration order". The runtime container is indeed preserved, but the STATIC type now lies: it says indexed while the heap object is a hash.

Consumers split into two camps. Kind-aware ones stay correct: `count`, `array_keys`, `array_values`, `var_export`, `isset`, key access, `foreach` (in the parameter case), and `emit_box_current_value_as_mixed`, which routes `PhpType::Array(_)` through `__rt_mixed_from_array_kind` precisely to preserve the runtime shape. Static-type-trusting ones are wrong: `json_encode` prints raw slot words (`{"a":1,"b":2}` becomes `[12,5]`), `serialize` emits `a:2:{i:0;i:12;i:1;i:5;}`, `print_r` shows `Array([0]=>12[1]=>5)`, and `in_array` SEGFAULTS (exit 139). `PhpType::Iterable` already shows the intended pattern -- `emit_json_encode_iterable` in src/codegen/lower_inst/builtins/json.rs dispatches on `__rt_heap_kind` (2=indexed, 3=hash, 4=object).

The fix direction is to represent the bare `array` contract with the HASH repr (`AssocArray{Mixed, Mixed}`) rather than the indexed one: a hash is a lossless superset. Measured proof -- when the value is STATICALLY a hash, every consumer already matches php -n 8.5.10 exactly, including list detection: a hash with sequential int keys json_encodes as `["a","b"]` (not `{"0":"a"}`) and serializes as `a:2:{i:0;s:1:"a";i:1;s:1:"b";}`. `Op::ArrayToHash` already exists for the list-to-hash direction (used today only for `Array(Never)` sources) and would need widening to any `Array(_)`.

This is Symfony's HeaderBag/ParameterBag/InputBag shape (`public function all(?string $key = null): array`), and it is why the compiled `--web` 404 response emits five malformed numeric headers (`10000:`, `0:`, `-128:`, `-255:`, `-1000:` -- listener priorities read out of hash buckets) and drops `Cache-Control` and `Content-Type`, where php -n sends `Cache-Control: no-cache, private`, `Content-Type: text/html; charset=UTF-8`, `X-Robots-Tag: noindex`.
Evidence: Reduced from the Symfony `--web` response to a 14-line pure-PHP file with no classes and no parameters: a function declared `: array` with one `return []` branch and one `return $this->headers` branch (assoc) returns `[14,15]` under elephc where php -n prints `{"x-foo":["bar"],"x-baz":["qux"]}`. The EIR shows the restamp directly: `v4: Heap(Hash) php=array<mixed, mixed> = prop_get v3 data[0]` then `v5: Heap(Array) php=array<mixed> = move v4`. A matching reduction on the parameter side (`function dump(array $h): string { return json_encode($h); }`) fails identically. A control where the value stays statically a hash matches php on all of json_encode, serialize, in_array and list detection.
Verified by: php -n 8.5.10 differential on scratchpad reducers v1-v12; elephc --emit-ir on the reducer; curl against the compiled Symfony --web binary compared with php -S on the same app
